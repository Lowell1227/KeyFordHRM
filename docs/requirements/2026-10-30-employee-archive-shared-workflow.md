# 员工档案整理与助手：统一流程及当前进展

更新日期：2026-10-30。适用于当前初始化整理，以及“Agent 助手”会话规划的员工档案助手。本文是共同建设入口，不另建初始化审批系统或外部助手档案库。应用发布的独立证据保存在本机 `C:/Users/lwei/kayford-releases/archive-shared-workflow-20261030/`：只有存在实际 `deployment-proof.json`、`external-resource-proof.json` 及真实角色验收记录时，才可据此确认上线状态。

## 已确认的业务边界

- HR 共同维护全体员工的档案。员工仍在原钉钉 OA 提交入离职和信息变更申请；档案助手首先服务 HR，整理已提供资料和已批准的变更结果，不替代 OA 审批。
- HRM 是正式人员、组织、任职、合同和权限的唯一业务存储；钉钉、千问办公、WorkBuddy 是资料和交互入口。外部入口是否已接通必须另以真实证据确认。
- 本次初始化以用户提供并确认的最新花名册为权威。明确、无冲突的源数据可以直接生效，用户已明确无需再次等待姚瑶逐项审核。此授权仅用于本次初始化，不是永久关闭日常审核。
- 对有歧义、身份冲突或资料缺失的条目，保留“待确认”或“待完善”，由 HR 核实；不猜测公司主体、员工身份、工号或在离职状态。
- 兼职和实习表的人员先收录为待核资料，暂不认定在职，不创建正式账号或占用新工号。仅姓名相同不自动绑定旧身份。
- 普通员工可见范围、HR 编辑/审核能力及绩效冻结关系沿用现有规则；模型和渠道适配器不能自行授予权限、确定审批身份或改写正式数据。

## 一条共享业务流程

`HR 提供资料或接收已批准的变更 → 校验来源与权限 → 匹配身份 → 生成标准档案变更与问题项 → HR 核对/确认 → 既有档案服务应用 → 审计与结果反馈`

初始化和后续助手复用同一条流程，只在本次初始化的确认策略上有明确授权差异：

| 环节 | 本次初始化 | 日常档案助手 |
| --- | --- | --- |
| 来源 | 已确认的最新花名册 | HR 提供的资料、已批准的 OA 变更等获授权来源 |
| 身份和差异 | 匹配现有 UUID、当前/历史工号及来源，不复制同名身份 | 相同规则 |
| 无冲突内容 | 用户已授权本批初始化直接应用并审计 | 生成变更建议，由有权限的 HR 最后确认，沿用现有审核策略 |
| 冲突和缺项 | 保留问题项及源证据，HR 人工确认，不猜填 | 相同规则 |
| 正式写入 | 复用现有档案应用服务，记录真实维护操作人和初始化授权 | 复用同一服务，不允许渠道或模型直接写表 |
| 结果 | 反馈成功、待补、待确认和失败，重复操作不重复新增 | 相同规则 |

“资料整理”“HR 确认”“正式生效”是同一业务链的不同状态，不再额外增加一层 AI 审批。HR 确认事实的动作与既有系统审核权限须对应，不能通过更换渠道绕过权限。

## 复用已有实现

- `EmployeeImportBatch` / `EmployeeImportRow`：文件来源、解析、预检、源行和批次状态。当前公开花名册导入入口按用户此前要求保持关闭；本次受控初始化不等于重新开放通用上传入口。
- `EmployeeDataChangeRequest`：草稿、基准值、拟变更值、来源标识、版本、审核状态及验证问题。初始化、手工维护和后续助手都汇入这些记录。
- `EmployeeArchivesService`：新建员工草稿、档案变更提交等业务入口；不为助手再造保存逻辑。
- `EmployeeDataReviewsService`：正式档案应用、任职/合同历史保护及审计。初始化授权可以由受控作业调用，不伪造姚瑶人工签字，不改变正常请求的权限规则。
- 已有人员列表、档案抽屉、人事办理草稿和待审核页面：继续作为 HR 工作入口，不建设另一套同名页面或第二份人员列表。
- 已有 `validationWarnings`、来源信息及档案提醒：优先扩展成可确认的问题项，不另建初始化专用审批表。

## 统一问题项和浮层

每个问题项至少包含稳定标识、字段、问题类型、来源坐标、源值、当前值、待核原因、状态及确认人/时间。对敏感字段沿用现有查看权限与脱敏，不在日志或建设文档保存个人敏感值。

- 员工档案与待核草稿都复用同一问题展示组件：`待确认 N项`，点击打开浮层，手机同样可操作。
- 浮层展示“原资料值 / 系统当前值 / 为什么待确认 / 需要 HR 核实什么”，不只给一句泛化错误。
- HR 可以先进入现有维护流程修正资料，再确认问题；若当前值正确，可以明确确认保留当前值并留下审计。确认标记本身不能悄悄修改其他业务字段。
- 缺项与冲突分开处理：缺少状态不能默认为在职；未确认的同名候选不能被当成已匹配身份；重复来源工号不能覆盖已经分开的两个人。
- 确认前校验当前版本，避免用旧浮层覆盖其他 HR 的新维护结果；已确认问题重复点击应不重复写入。

共用接口沿用现有 HR 权限，不增加一套助手角色：

| 接口 | 用途 | 权限 |
| --- | --- | --- |
| `GET /employee-archives/issues/employee/:userId` | 查看正式员工的来源问题 | 现有档案维护或审核权限 |
| `GET /employee-archives/issues/request/:requestId` | 查看同一草稿/请求的问题 | 现有档案维护或审核权限 |
| `POST /employee-archives/issues/:requestId/:issueId/confirm-current` | 明确确认保留当前事实；不改正式档案 | 现有档案维护权限，且问题满足可确认条件 |

确认动作携带当前事实指纹；事务内重读，资料变化或并发冲突返回 409，要求 HR 重新核对，不自动替用户重试确认。历史已确认状态绑定同一来源观察，不因后来正常调岗、字段更新或无关版本递增而重新出现；新来源内容有变化时重新核对。只读 HR 只能查看，缺项和同名身份候选不能一键消除。

来源标识由服务端建立并保留，文件来源和后续获授权的非文件事件都使用同一草稿保存机制。新渠道上线时在同一个受控来源集合登记，不另造问题表、确认接口或保存实现；本文件不授权渠道自行添加 HR 权限。

## 已知待补及共用服务风险

1. 原 `8654684` 共用服务在资料应用时会重写未变合同的来源元数据；源码已修复，本批作业已使用并验证该修复。此修复与共享问题确认能力一起发布，处理后续同类请求前需核实实际在线版本已包含该修复。
2. 原表复合公司及一份新增转签需要 HR 核定主体；重复来源工号沿用已分开的现有身份和当前分配号；历史部门及主管无法唯一对应时留证据待核，不重建猜测的组织关系。
3. 共用浮层及草稿空值修复已在源码实现；电脑、平板和手机的 50 项模拟接口浏览器回归及 Web 构建通过。测试没有连接生产 API/数据库，也没有触发迁移和 seed；后端全量、隔离真实 HTTP、提交和发布证据须单独记录，不能称为已经上线。状态、用工类型、组织归属和试用月数的显式空值不会默认回填；待核草稿可保存，必填事实未核实不能提交。
