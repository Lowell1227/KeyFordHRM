# 员工档案变更审核减负：个人信息字段免审直改

- 日期：2026-11-11
- 状态：需求已确认，待排期实现
- 主题：人员档案 / 员工档案（一次只打磨本主题）

## 1. 现状与痛点

当前"员工档案"域的审核现状（2026-11-11 梳理）：

- 员工档案全部变更（新建、改档、任职变更含离职、仅绩效上级）都走 `EmployeeDataChangeRequest` 审核，审核通过在事务内写正式数据。
- 组织架构（部门/岗位）全部变更走 `DepartmentChangeRequest` / `PositionChangeRequest` 审核。
- 基础资料中仅"岗位"走审核；合同主体、工作地点、职系为字典类，直接生效 + 审计日志。
- 转正走独立审批流，不经档案审核。

痛点：一次只改员工的手机号、学历、紧急联系人等纯个人信息，也必须提交审核、等人通过才生效。审核队列被大量低风险变更占满，HR 审核成本高、员工信息更新滞后。

已确认的优化方向（A：减负，收窄审核范围），用户决策：

| 决策项 | 结论 |
|---|---|
| 第②档个人信息字段 | 免审，直接生效 + 审计日志 |
| 中间档（社保/公积金状态与日期、工作地点、职系） | 保留审核 |
| 仅改"绩效直属上级" | 保留审核（独立审核轨不变） |
| 免审变更留痕 | 审计日志即可，不做直改记录列表 |

## 2. 需求目标

改档提交时按字段分级自动拆分：

- **免审字段**（第②档）：事务内直接写入正式数据，写审计日志（操作者、时间、字段级新旧值），不生成审核单。
- **审核字段**（其余）：维持现有审核流不变。
- 一次提交混合两类字段时：免审部分直接生效，审核部分照常生成审核单，前端明确提示两部分各自结果。
- 全部字段均为免审字段时：不生成任何审核单，直接生效。

## 3. 字段分级清单

### 3.1 免审字段（第②档，共 20 项，全部位于 EmployeeProfile）

`phone`、`gender`、`birthDate`、`ethnicity`、`education`、`professionalTitle`、`school`、`graduationDate`、`major`、`maritalStatus`、`childrenStatus`、`childrenCount`、`politicalStatus`、`nativePlace`、`householdType`、`idAddress`、`currentAddress`、`emergencyContactName`、`emergencyContactRelation`、`emergencyContactPhone`

说明：

- `phone` 同时存在于 `users.phone` 与 `employee_profiles.phone`，直改时两处同步。
- `idAddress`（身份证地址）列入免审，但它与敏感证件相关，实现前请用户最终确认；若保留审核则仅去掉这一项。
- 邮箱（`users.email`）不在档案编辑范围内，本需求不涉及。

### 3.2 保留审核字段（不变）

- 员工段：姓名、工号、部门归属、岗位、职级、任职类型、入/转/离日期、试用期、所属公司原文、合同主体、绩效直属上级、员工状态。
- 档案段：社保/公积金状态及起始日期（中间档）、身份证号（加密）、开户行、银行账号（加密）。
- 合同段：全部（含条款与附件增删改）。
- 新建员工、任职变更（含离职）、仅绩效上级变更、花名册导入：全部维持现有审核流。

## 4. 业务规则

1. **拆分时机**：在现有改档提交链路（`persistArchiveChangeWithClient`）内完成拆分，不打断草稿/提交/审核的既有状态机。
2. **直改事务**：免审字段在同一事务内写 `employee_profiles`（upsert）及 `users.phone`（如涉及），写 `auditLog`（动作如 `employee_profile_direct_update`，detail 含字段级新旧值，不含敏感完整值）。
3. **在审单不冲突**：员工存在 submitted/pending 审核单时，免审直改不得导致该审核单审批时被误判"基准漂移"。实现采用：直改在提交事务内先写正式数据并同步内存快照，随后 diff 自然只覆盖需审核字段；同时把在审单 `baseValue` 中被直改的字段刷新为新值（`applyDirectProfileChanges` + `baseValueWithDirectChanges`）。免审字段的值在提交入口按审核生效路径同一套规则归一化（手机号去空白、空串存 null；出生日期/毕业日期严格校验，非法格式直接拒绝），归一化后写回输入，避免原始值进入审核差异。
4. **并发保护**：直改仍走档案现有的乐观锁（baseVersion / requestVersion），不引入新的并发窗口。
5. **权限**：直改与今天发起改档一致，需 `employee_archive_edit` 能力（hr / system_admin 全权，hr_user 需被授予）。
6. **无实际变更**：整单均无实际变更时维持现有拒绝行为，不产生空审计。
7. **员工可见性不变**：员工本人仍看不到审核中/直改过程，只读正式数据。

## 5. 前端交互

- 档案编辑保存后，按后端返回的拆分结果提示，例如：
  - 全部免审："已直接生效"。
  - 混合："手机号、学历已直接生效；部门、岗位已提交 HR 管理员审核"。
  - 全部审核字段：维持现有"已提交审核"提示。
- 免审字段保存后即时反映在详情中；审核字段在通过前维持原值显示（现状不变）。
- 变更历史（EmployeeChangeHistory）不变，仅展示审核单；免审直改不进该列表（审计日志兜底）。

## 6. 非目标（本轮不做）

- 合同附件单独补传免审（待后续确认）。
- 组织架构、基础资料（岗位/字典）审核规则不变。
- 自审自批、hr_user 权限三处不一致等梳理中发现的其他问题，另行立项。
- 不做"直改记录"查询页面。

## 7. 验收标准

1. API：新增/调整针对性测试——纯免审提交（直改生效、无审核单、有审计）、混合提交（两部分各自正确）、与在审单并存（直改不冲掉在审单）、敏感字段（身份证/银行卡）永不直改、免审日期非法格式在提交入口拒绝、手机号归一化与审核路径一致、权限校验（无 edit 能力 403）、并发乐观锁。已实现于 `api/src/employee-archives/employee-direct-apply.spec.ts`（8 项）。
2. `npm run build` 通过；相关既有测试不回退。
3. Web：`npm run type-check` 通过；生产构建通过；覆盖原问题的 Playwright 用例（直改保存、混合保存提示）。
4. 真实角色验收：HR 管理员（可直改+可审）、仅授权 edit 的 hr_user（可直改不可审）、无 edit 能力者（不可直改）。
5. 证据分级：以上均为开发验证，上线与业务验收另计。

## 8. 风险与遗留

- 直改写正式数据即不可经审核拦截，依赖审计日志事后追溯——已与用户确认接受。
- 若未来发现某免审字段实际高风险（如社保起缴日期口径），单独将其移回审核列即可，机制不变。
