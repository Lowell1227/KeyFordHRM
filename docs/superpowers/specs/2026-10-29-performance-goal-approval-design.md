# 目标计划五步审批与计划流程版本

业务依据：用户明确指定目标链路，并于本会话确认同人/本人节点及退回规则。以下业务规则已确认；技术拆分由实现者负责。

## 已确认的业务规则

1. 新目标计划主线：员工填写提交 → 绩效上级审核 → 部门负责人审核 → 员工确认 → 分管领导审核 → 目标生效。
2. 连续同人兼任绩效上级、部门负责人时合并办理，保留两节点审计；跳过员工本人承担的审核节点，不能让本人审核自己。员工确认隔开的部门负责人和分管领导即使同人，仍分别办理。
3. 绩效上级退回时，由员工修改重新提交；部门负责人、员工确认或分管领导退回时，由绩效上级调整，再重走部门负责人、员工确认、分管领导后续链路。退回原因必填，下游原确认不再生效。
4. 部门负责人、分管领导只审核和退回；需要改目标内容时退回绩效上级处理。员工确认之后不得直接改目标再沿用旧确认。
5. HR绩效专员全过程可查看全员已保存的目标计划、进度、当前办理人及目标审批记录。其HR身份只读；如果同时被任务冻结为具体审核人，只按该业务身份办理。
6. 分管领导通过才建立正式指标基线并允许目标执行、月度自评等后续业务；员工确认不等于目标最终生效。开放时间到达不得绕过终审。
7. 结果评估流程保持：员工自评 → 绩效上级评价 → 部门负责人复核 → HR校准 → 分管领导审批 → 员工确认 → HR公示 → 到期归档。
8. 以后修改审批规则时，新计划使用新规则，已有计划继续使用其原规则；发起后组织变动也不得改写冻结审核人。

## 实现选择

沿用现有任务、流程记录、通知、指标版本与冻结关系，增加目标审批两个状态和独立目标流程版本。此次不做通用流程编辑器，不引入新的工作流系统。

- 新增 `AssessmentCycle.goalWorkflowVersion`，迁移默认1，保留已有计划的旧链；新创建计划显式绑定2。字段不接受普通编辑或审核改写。
- 保留现有 `workflowVersion`（评分模型版本）和 `planVersion`（配置并发修订号）的原含义。
- 任务通过不可变的所属周期读取目标流程版本；新版本写入发起快照，冻结人员沿用 `managerId / deptHeadId / approverId`。不重复存一份任务流程版本。
- 旧目标版本维持原行为和旧预约哈希。未来结果流程升级采用同样的“旧计划原规则、新计划新规则”版本分流，而不修改当前结果处理分支。
- 新增目标状态 `indicator_dept_reviewing`、`indicator_approving`，新增目标流程节点 `indicator_dept_review`、`indicator_approval`；不复用期末结果状态、节点和时间字段。
- `indicatorConfirmedAt` 继续表示员工确认；新增 `goalApprovedAt` 表示目标分管终审。指标V1激活和月度期次绑定移动到新流程的终审事务。
- 新目标流程单条、批量均按当前阶段及冻结审核人鉴权，HR或管理员身份本身不构成代审权。旧版本的兼容行为单独保留。

## HR目标计划只读边界

绩效专员沿用现有识别：`sysRole=hr_user` 且同时具备 `cycle_plan_edit`、`performance_publish`。HR管理员与系统管理员保留既有读取能力；普通HR不因本次变更获得全员范围。

新增目标计划专用列表与详情读取，返回员工、组织、目标内容、已保存草稿、目标流程节点和记录。不得返回期末评分、自评正文、校准/申诉内容，不修改共享 `DataScope` 或人员档案权限。

前端复用任务列表与目标详情组件，提供“我的计划”“待我审核”“计划进度”三种目标视图。部门负责人、分管领导即使没有直属下属，也能进入明确分配的目标待办。绩效专员进度视图仅有查看动作；PC紧凑展示阶段，手机突出当前节点与办理人。

## 验收要求

- 不同人员完整走完五步；员工确认后仍为待分管审核，终审前无正式指标基线。
- 同人连续节点合并且留痕；本人节点不自审；非连续同人仍需终审。
- 每类退回回到约定节点，修改后旧员工确认失效；重复/并发操作不能跨节点。
- 目标待终审时，即使开放时间已到，仍不得提交自评、月度评价或目标进展。
- 新创建计划用新目标版本；已有草稿、已预约、已启动计划继续原版本和冻结关系，旧预约哈希不变。
- 绩效专员可查全员草稿及进度，不能代审、改目标或读取期末评分；普通HR和无关员工无法扩大读取。
- 已确认的结果评估业务回归通过，新增目标节点不进入结果待办和结果审批。
- API全量测试、构建；Web类型检查、构建及覆盖员工/上级/部门负责人/分管领导/绩效专员的PC与手机浏览器验证。
