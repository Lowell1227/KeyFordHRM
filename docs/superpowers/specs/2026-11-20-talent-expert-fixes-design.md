# 人才库独立评审问题修复设计

依据：用户阅读 `docs/acceptance/2026-11-20-talent-expert-review.md` 后明确“请修复吧”，授权修复F1～F6及不改变既有业务规则的U1/U2表达。B1跟进结束和B2负责范围已询问，答复前不实现依赖行为。本轮不含生产发布授权。

## 已确定修复

- F1：列表携带当前匹配应聘ID；详情与面板优先选中该项，失效明确提示，不能静默换到其他应聘。无应聘筛选时保留最新默认。U1明确人才库状态、本次应聘阶段、员工当前三个对象及两个淘汰动作作用域，不自动联动历史。
- F2：取消首次入职且从未到岗、无有效任职/占号/其他进行中申请时，复用原pending_entry身份为新的已接受应聘建立新的首次入职申请。旧来源申请不改写，新申请沿用原审核/到岗确认规则；不重建员工、重置账号或新增权限。不满足边界继续拒绝。
- F3：读取反馈返回当前面试版本，局部刷新更新基准并保留输入。HR退回反馈使用同一基准；仍保留版本、参与人和阶段校验。
- F4：一次新建应聘生成并保持requestId，服务端事务/唯一约束保证同请求只建一次；内容/候选人不一致拒绝。老请求可省略，旧行保留NULL；不能以人才＋岗位唯一限制合法多次应聘。
- F5：人才表单有未保存修改或待传文件时，Esc/关闭/遮罩均走现有beforeClose提示；无修改和保存成功后正常关闭。不增加自动保存系统。
- F6：选填邮箱做一致格式校验并将前后端错误贴字段；失败保留输入。
- U2：HR界面显示面试关联岗位/批次，旧独立面试明确未关联。沿用既有数据范围，不增加参与人对人才档案或其他应聘的访问。

沿用NestJS/Prisma/PostgreSQL、Vue/Element Plus既有模块和依赖。复用当前隔离分支；不覆盖main未提交删除工作、审查报告或声明产物。版本仍0.9.1，不改生产业务资料、真实通知/日程或付费模型调用。
