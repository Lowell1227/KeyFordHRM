# 绩效指标可见范围、目标跟进与目标地图统一设计

## 1. 文档状态

- 日期：2026-09-01
- 业务方案：已逐项确认
- 开发基线：领先的 `main`
- 发布范围：数据库迁移、API、Web 联合发布
- 关联设计：
  - `2026-08-24-dynamic-business-permissions-design.md`
  - `2026-08-30-goal-tracking-cycle-closure-design.md`
  - `2026-08-15-objective-map-canvas-redesign-design.md`

## 2. 背景与问题

当前系统已经具备绩效待办的本人/团队入口、目标跟进的本人/上级入口、目标地图画布和单选指标可见范围，但四部分的产品职责与数据模型没有完全统一：

1. 绩效待办、目标跟进和目标地图对“上下级”的展示目的不同，页面文案仍混用“直接上级、直属主管、绩效直属上级、团队成员”。
2. 指标可见范围由单个 `IndicatorVisibilityScope` 枚举承载，无法同时向直属上级、直属下属、同部门或自定义人员开放。
3. 现有目标地图以独立 `Objective.parentId` 为主要关系，不能准确表达员工绩效指标与直属上级绩效指标之间的明确对齐。
4. 同部门可见但未对齐的指标如果混入主图，会产生虚假层级或杂乱连线。
5. 页面隐藏和服务端查询存在各自判断的风险，容易出现目标跟进可见、目标地图不可见，或直接 URL 越权读取的结果差异。

本设计建立统一的绩效指标可见性底座，并重新明确三个页面的业务职责。

## 3. 已确认业务决策

### 3.1 页面职责

- **绩效待办：** 查看本人的绩效，以及当前用户在该考核周期任务中担任主管的直属下属绩效。
- **目标跟进：** 查看本人的指标，以及同一考核周期中绩效直属上级允许本人查看的指标；只看直属上级，不沿汇报链继续向上。
- **目标地图：** 使用类似脑图的层级和连线展示当前用户可见的上下级绩效指标；同部门可见指标也可进入地图范围。

### 3.2 权限边界

- 绩效待办的直属下属以 `AssessmentTask.managerId = viewer.id` 为唯一业务边界，不包含间接下属。
- 历史和进行中周期继续使用周期发起时冻结的任务主管关系，不按当前员工档案重算。
- “同部门可见”只影响目标地图、参考指标及其他指标只读入口，不开放同事的绩效任务、复盘总结、评分或审批内容。
- 目标跟进只展示指标、完成度和已允许公开的进展，不展示直属上级的自评分、主管评分或最终绩效结果。
- 任意页面的前端隐藏都不能代替服务端权限校验。

### 3.3 指标对齐

- 员工设置指标时，通过“添加对齐”明确选择同一周期内绩效直属上级的可见指标。
- 目标地图只对真实指标对齐关系画线，不依据姓名、部门、标题或显示顺序自动连线。
- 未设置对齐的指标仍可显示，但不能产生伪连线。
- 上级指标不可见时不返回其名称或占位节点；可见的下级指标提升为当前可见图的根节点。

### 3.4 目标地图布局

采用已确认的方案 A：

- 主画布只展示真实上下级指标对齐脑图。
- 右侧独立区域展示“同部门可见 · 未对齐”。
- 手机端主图保持可拖动和缩放，右侧区域移动到主图下方。

### 3.5 可见范围多选

- 多个可见范围按并集生效，命中任意一项即可查看。
- “全公司可见”是独占选项，选择后自动清除其他范围。
- “自定义部门或员工”可与其他范围并存。
- 指标负责人始终可以查看自己的指标。
- 至少选择一个可见范围，默认选择“绩效直属上级可见”。

## 4. 统一术语

| 业务概念 | 统一名称 | 使用位置 |
| --- | --- | --- |
| 正式绩效汇报关系 | 绩效直属上级 | 员工档案、目标跟进、身份说明、指标可见范围 |
| 正式绩效汇报关系的反向人员 | 直属下属 | 绩效待办、人员列表、指标可见范围 |
| 绩效评分流程动作 | 主管评分 | 待办阶段、按钮、通知、截止时间 |
| 部门管理责任 | 部门负责人 | 员工档案、部门复核、组织管理 |
| 组织树子部门 | 下级部门 | 组织管理、部门范围说明 |
| 花名册原始字段 | 花名册直属主管 | 导入、档案差异，不作为绩效任务授权 |

用户可见文案统一调整：

- 目标跟进：`我 / 绩效直属上级`。
- 绩效待办：`我的绩效待办 / 直属下属的绩效待办`。
- 原“团队成员”人员集合改为“直属下属”。
- 指标可见范围使用“绩效直属上级可见”，不再使用含义模糊的“仅上级可见”。
- “主管评分”继续保留，因为它表示流程动作而不是人员关系字段。

## 5. 可见范围数据模型

### 5.1 独立规则表

新增 `IndicatorVisibilityRule`：

```prisma
model IndicatorVisibilityRule {
  id          String                   @id @default(uuid())
  indicatorId String                   @map("indicator_id")
  scope       IndicatorVisibilityScope
  createdAt   DateTime                 @default(now()) @map("created_at")
  indicator   IndicatorInstance        @relation(fields: [indicatorId], references: [id], onDelete: Cascade)

  @@unique([indicatorId, scope])
  @@index([scope, indicatorId])
  @@map("indicator_visibility_rules")
}
```

继续保留现有：

- `IndicatorVisibilityDepartment`
- `IndicatorVisibilityUser`

当规则集合包含 `custom` 时，上述关联表保存自定义部门和员工。自定义范围可以和其他规则同时存在。

### 5.2 可见范围枚举与显示名称

| 技术值 | 显示名称 | 含义 |
| --- | --- | --- |
| `supervisors` | 绩效直属上级可见 | 本周期任务中冻结的直属上级 |
| `direct_reports` | 直属下属可见 | 同周期任务中由指标负责人担任主管的直接下属 |
| `all_reports` | 全部下属可见 | 同周期冻结主管图中的全部下属 |
| `department` | 本部门可见 | 与指标负责人同一冻结部门 |
| `department_tree` | 本部门及下级部门可见 | 指标负责人冻结部门及当前有效子部门树 |
| `custom` | 自定义部门或员工 | 指定多个部门和多个员工 |
| `company` | 全公司可见 | 全公司在职人员，独占选择 |

### 5.3 统一判断顺序

查看指标时按以下顺序计算：

1. 查看者是指标负责人本人：允许。
2. 命中 `company`：允许。
3. 命中周期任务冻结的绩效直属上级、直属下属或全部下属关系：允许。
4. 命中本人和指标负责人的冻结部门关系：允许。
5. 命中自定义员工或自定义部门：允许。
6. 未命中任何规则：拒绝。

读取进行中或历史绩效周期时，人员关系和人员部门优先使用该周期 `AssessmentTask` 快照；部门树的父子结构使用当前已审核组织结构。不存在周期任务上下文的通用参考指标查询，才回退到当前已审核员工档案关系。

### 5.4 保存校验

- `visibilityScopes` 至少包含一个合法枚举。
- 选择 `company` 时数组长度必须为 1。
- 包含 `custom` 时，至少存在一个有效部门或员工。
- 不包含 `custom` 时，不允许提交自定义部门或员工 ID。
- 范围、部门和员工 ID 在服务端统一去重。
- 选择者只能指定其数据范围内的有效部门和在职员工。
- 校验失败返回明确的 400，不保存部分规则。

## 6. 指标对齐数据模型

新增绩效指标之间的明确对齐关系，不复用 `Objective.parentId` 猜测关系：

```prisma
model IndicatorInstanceAlignment {
  id                String            @id @default(uuid())
  childIndicatorId  String            @map("child_indicator_id")
  parentIndicatorId String            @map("parent_indicator_id")
  createdAt         DateTime          @default(now()) @map("created_at")
  childIndicator    IndicatorInstance @relation("IndicatorAlignmentChild", fields: [childIndicatorId], references: [id], onDelete: Cascade)
  parentIndicator   IndicatorInstance @relation("IndicatorAlignmentParent", fields: [parentIndicatorId], references: [id], onDelete: Cascade)

  @@unique([childIndicatorId, parentIndicatorId])
  @@index([parentIndicatorId])
  @@map("indicator_instance_alignments")
}
```

保存对齐时必须同时满足：

- 子指标和上级指标属于同一考核周期。
- 上级指标负责人是子指标负责人在该周期任务中冻结的绩效直属上级。
- 当前操作人有权设置子指标，并有权查看被选择的上级指标。
- 子指标不能对齐自己，不能形成环，也不能重复对齐。
- 一个子指标允许对齐零个或多个上级指标。

现有独立目标 `Objective`、`ObjectiveAlignment` 和历史数据不删除、不改写。新目标地图以绩效指标关系为数据源；其他仍使用独立目标的功能继续兼容。

指标确认和正式变更时，可见规则数组及上级指标对齐 ID 进入指标基线、版本差异和审计记录。

## 7. API 与兼容契约

### 7.1 指标 DTO

新契约使用：

```ts
interface IndicatorVisibilitySelection {
  visibilityScopes: IndicatorVisibilityScope[];
  visibleDepartmentIds: string[];
  visibleUserIds: string[];
  alignedParentIndicatorIds: string[];
}
```

过渡期：

- API 继续接受旧 `visibilityScope`，并归一化为单元素数组。
- API 响应继续返回旧 `visibilityScope`，取规则集合中的稳定兼容值；新 Web 只读取 `visibilityScopes`。
- 新 API 写入规则表的同时同步旧字段，保证旧 Web 回滚后仍能读取。
- 旧字段只在后续独立收口版本中删除，本次发布不执行破坏性删除。

### 7.2 集中式可见性服务

`IndicatorVisibilityService` 成为唯一指标只读范围判断入口，提供：

- 保存选择的归一化与校验。
- 构建单个查看者的 Prisma 可见条件。
- 判断单个指标是否可见。
- 批量裁剪目标地图节点和边。
- 生成用户可理解的范围标签。

目标跟进、目标地图、参考指标、指标详情及指标版本读取不能再维护各自的范围枚举分支。

### 7.3 目标地图接口

新增或收口为专用指标地图查询：

```http
GET /objectives/indicator-map?cycleId=<uuid>&scope=related|department
```

返回：

```ts
interface IndicatorMapResult {
  cycleId: string;
  nodes: Array<{
    id: string;
    ownerId: string;
    ownerName: string;
    deptId: string | null;
    deptName: string | null;
    title: string;
    description: string | null;
    weight: number;
    progress: number;
    status: string;
  }>;
  edges: Array<{ childIndicatorId: string; parentIndicatorId: string }>;
  unalignedDepartmentNodes: string[];
}
```

服务端先按统一可见规则裁剪节点，再裁剪边。任一端点不可见时不返回该边，也不返回隐藏端点的占位信息。

## 8. 页面设计

### 8.1 指标设置

可见范围控件改为分组多选：

- **汇报关系：** 绩效直属上级可见、直属下属可见、全部下属可见。
- **组织范围：** 本部门可见、本部门及下级部门可见。
- **指定范围：** 自定义部门或员工。
- **全员：** 全公司可见。

收起后显示最多两个已选标签，更多显示 `+N`。选择自定义范围后展开部门和员工多选。选择全公司后清除并禁用其他并列选择。未选择时在控件底部显示红字“请选择至少一个可见范围”。

控件位于指标单元格列表之外时，继续使用独立权限控件样式，不伪装成指标字段单元格。完整模式、简洁模式、主管审核和只读快照使用同一选择数据结构和显示标签。

### 8.2 绩效待办

- 同一考核周期下显示“我的绩效待办”和“直属下属的绩效待办”。
- 切换周期时，本人任务、直属下属任务、阶段数量、筛选和列表同时刷新。
- 直属下属任务严格查询 `AssessmentTask.managerId = viewer.id`。
- 同部门指标可见规则不能扩大任务详情、复盘、评分或审批权限。
- 原“团队成员”列表文案改为“直属下属”。

### 8.3 目标跟进

- 先确定考核周期，再从本人任务快照解析该周期绩效直属上级。
- 人员分组只显示“我 / 绩效直属上级”，不显示间接上级、同部门员工或直属下属。
- 选择上级后仍停留在目标跟进页，只加载上级在同一周期中向本人开放的指标。
- 展示指标内容、完成度、状态和允许公开的进展；不展示评分、等级、复盘总结或审批内容。
- 周期没有绩效直属上级时只显示本人。
- 上级存在但没有开放指标时显示“该上级当前没有向您开放的指标”。

### 8.4 目标地图

- 主画布使用绩效指标节点和 `IndicatorInstanceAlignment` 边。
- 主图按照可见的上级到下级关系布局，可见父级位于上方或左侧，子指标成组展开。
- 右侧区域显示“同部门可见 · 未对齐”，不绘制连线。
- 点击任一节点打开只读指标详情；写操作仍进入对应任务权限页面。
- 隐藏节点不返回、不占位、不泄露标题；可见子节点成为当前可见根。
- 切换周期、范围或搜索时忽略过期请求，不能显示上一周期数据。
- 普通员工可以进入目标地图，但只能看到统一可见性服务返回的指标；不能因为页面入口开放而扩大数据范围。

### 8.5 响应式

- PC：主图占据主要空间，右侧固定宽度展示同部门未对齐指标。
- 手机：周期和范围筛选纵向排列；主图支持横向拖动、缩放和重新定位；未对齐区域移到主图下方。
- 320px 至 390px 下按钮和选择器不重叠，不出现整页横向溢出；只允许地图画布内部按需平移。

## 9. 错误与空状态

- 无权查看人员：`您没有权限查看该员工的目标跟进`。
- 无权查看指标：`该指标不可见或已被移除`。
- 上级无开放指标：`该上级当前没有向您开放的指标`。
- 当前周期无直属上级：只显示本人，不展示错误。
- 当前周期没有地图节点：`当前周期没有对您开放的指标`。
- 没有同部门未对齐指标：隐藏右侧区域，不保留空白栏。
- API 读取失败：保留已选周期和人员，显示原位置重试，不伪装成空数据。
- 直接 URL 越权：API 返回 403；Web 显示明确无权限页面，不显示通用加载失败。

## 10. 数据迁移与回滚

采用 expand-migrate-contract：

1. 新增可见规则表和指标对齐表，不删除旧字段。
2. 将每个指标现有 `visibilityScope` 回填为一条 `IndicatorVisibilityRule`。
3. 对回填数量、重复规则和无规则指标进行迁移校验；无规则指标使用旧字段值，不自动扩大范围。
4. API 双读双写，优先使用规则表，无规则时回退旧字段。
5. Web 切换到多选契约和新地图接口。
6. 真实角色验收稳定后，另立任务停止旧字段写入和删除旧字段。

回滚时旧 API/Web 仍能读取同步维护的旧字段。新表保留，不需要在紧急回滚中执行破坏性逆迁移。

生产发布前必须备份数据库并记录当前 Web/API 镜像、数据库迁移版本和 Git 提交。发布失败时按整套匹配版本回退，不能只回滚 Web。

## 11. 测试与验收

### 11.1 API 与数据层

- 单选旧数据正确回填为一条规则。
- 多个范围按并集生效。
- 全公司与其他范围同时提交被拒绝。
- 自定义范围为空或越权部门/人员被拒绝。
- 绩效直属上级、直属下属、全部下属和部门范围按周期任务快照判断。
- 指标负责人始终可见自己的指标。
- 未授权用户直接读取指标、目标跟进和地图返回 403 或裁剪结果。
- 地图节点先裁剪、边后裁剪，不泄露隐藏端点。
- 指标对齐拒绝跨周期、非直属上级、不可见、自己对齐、重复和成环。
- 旧 `visibilityScope` 契约继续兼容，双写结果一致。

### 11.2 Web 行为

- 可见范围分组、多选标签、`+N`、自定义展开、全公司独占和底部校验提示。
- 完整模式、简洁模式、目标审核只读/编辑状态均显示相同范围。
- 绩效待办切换周期时本人和直属下属数据同时刷新。
- 目标跟进只显示本人和周期绩效直属上级；上级指标按规则过滤。
- 目标地图主图只绘制真实对齐边；同部门未对齐进入右侧栏。
- 无权限、无直属上级、无开放指标、无地图节点和接口错误使用不同状态。
- 快速切换周期不会被旧请求覆盖。

### 11.3 PC 与手机

- 1440px PC 验证完整工作台、目标跟进、多选控件和目标地图 A 布局。
- 390px 与 320px 验证指标设置、周期/人员切换、地图拖动缩放和未对齐区域下移。
- 页面控件不重叠，地图外不出现横向滚动，关键操作无需悬停。

### 11.4 真实角色链路

至少准备：员工 A、其绩效直属上级 B、A 的直属下属 C、A 的同部门同事 D、无关系员工 E。

1. A 的绩效待办只出现 A 和周期任务中由 A 负责的 C。
2. A 的目标跟进只出现 A 和周期绩效直属上级 B。
3. B 选择“直属下属可见”后，A 可以在目标跟进看到 B 的指标。
4. D 的指标选择“本部门可见”后，A 只能在目标地图的同部门区域看到它；不能看到 D 的绩效任务和评分。
5. A 的指标明确对齐 B 的指标后，地图产生一条真实连线。
6. E 通过直接 URL 不能读取 A、B、C、D 的未授权指标。
7. 一个指标同时选择“绩效直属上级可见 + 本部门可见 + 自定义员工”时，三个范围分别命中且不互相覆盖。

## 12. 非目标

- 不把同部门可见扩大为同部门绩效任务、评分或总结可见。
- 不让目标跟进查看间接上级、同部门同事或直属下属。
- 不把绩效待办扩大到间接下属。
- 不依据组织关系自动生成指标对齐边。
- 不显示隐藏指标的占位名称、数量或连接方向。
- 不删除历史 `Objective` 数据或既有审计记录。
- 不在本次联合发布中删除旧 `visibilityScope` 字段。

## 13. 实施与发布约束

- 所有实现直接基于最新 `main`，不创建长期功能分支。
- 开始编码前再次确认 `main` 与 `origin/main` 一致，并识别任何并发未提交改动。
- 数据模型和权限变化先写失败测试，再实施最小改动。
- 不覆盖或夹带其他任务的未提交文件；发生重叠时先核对差异。
- 完成后执行相关 API 测试、Web 类型检查、构建、PC/手机 Playwright 和真实角色权限验收。
- 上线前创建数据库备份、Web/API 回滚镜像或标签，并验证线上 Git 修订。
- 发布数据库迁移、API、Web 后验证内部和外部健康检查、登录、绩效待办、目标跟进、目标地图和无权限访问。
- 确认生产 `ENABLE_TEST_QUICK_LOGIN=false`。
