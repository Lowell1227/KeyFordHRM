# 主管绩效待办默认入口修复设计

## 背景

主管周强从左侧“绩效”进入 `/tasks` 时，页面把缺少查询参数的地址统一解析为 `scope=mine`，因此首屏只展示个人绩效。数据库、直属下属关系、团队任务查询和审核写操作均正常；团队绩效需要再次点击范围切换和“待处理”筛选才能出现。

## 目标

- `manager` 角色从无查询参数的 `/tasks` 进入时，直接看到团队待处理指标审核。
- 默认地址规范化为 `/tasks?scope=team&stage=goal-review&stageState=pending`，刷新和浏览器前进、后退后保持一致。
- 普通员工继续进入个人待办。
- 已显式携带查询参数的个人或团队深链保持原义，不被默认规则覆盖。
- 团队查询和写操作继续严格校验 `assessmentTask.managerId = 当前用户 id`。

## 方案选择

采用路由守卫中的角色感知默认重定向。认证信息加载完成后，仅当目标路由为 `MyTasks`、当前角色为 `manager` 且查询参数为空时，返回带团队待处理参数的替换导航。

未采用以下方案：

- 只加强“团队绩效”按钮提示：仍需主管二次点击，不能解决首屏看不到待办的问题。
- 合并个人和团队任务列表：会混淆任务归属和处理权限，改动面与回归风险过大。

## 数据流与边界

1. 主管点击左侧绩效入口，进入裸 `/tasks`。
2. 全局路由守卫完成会话加载和登录校验。
3. 守卫识别 `manager + MyTasks + 空查询参数`，替换为团队指标审核待处理地址。
4. 现有 `TaskListView` 按 URL 状态调用 `tasksApi.findTeam`。
5. 现有后端按当前用户 `managerId` 返回团队任务；现有详情、通过、驳回和保存能力保持不变。

## 异常与兼容

- 未登录、令牌过期和角色鉴权仍先按现有守卫逻辑处理。
- `/tasks?scope=mine`、团队深链、通知深链和旧 `/manager/scoring` 重定向不受影响。
- `dept_head`、`vp`、`hr`、`system_admin` 不应用此次默认规则，避免把没有直接归属任务的管理角色送入空团队列表。
- 团队接口失败时继续使用现有“团队任务加载失败”和重试交互。

## 验收

- 周强登录后点击“绩效”，地址成为 `/tasks?scope=team&stage=goal-review&stageState=pending`。
- 页面显示“团队绩效”选中、“指标审核”选中、“待处理”选中，并可打开当前待审核员工。
- 当前待审核任务中可看到保存、通过和驳回操作。
- 显式访问 `/tasks?scope=mine` 时仍显示个人任务。
- 前端契约测试、类型检查、构建和周强真实浏览器验收通过。
