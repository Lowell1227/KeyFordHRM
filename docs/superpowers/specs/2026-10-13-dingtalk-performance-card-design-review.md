## 1. 设计目标与已确认范围

员工通过同一个“绩效助手”完成绩效周期里的主要事项：知道当前要做什么，随手记录进展，直接进入本人需要办理的页面，看到明确的处理结果。已经记录的事实能被后续评价引用，减少重复输入。

继续使用现有独立机器人应用和现有 HRM 数据、身份、权限及业务流程。应用可见范围保持用户确认的四人试点；首轮只由姚瑶进行真人联调。一个人同时担任 HR、员工或上级时，卡片按本次事项的实际身份和业务关系确定内容与动作。

本轮设计五类模板，复用现有进展模板，另准备四类。新增卡片首先承接线上已经存在的业务；对话起草正式目标、AI 整理自评草稿属于独立的后续业务能力，不能仅因模板里出现按钮就称为已实现。

## 3. 统一交互方案

采用“聊天表达 + 卡片摘要/短动作 + 钉钉内 HRM 办理页”。

| 方案 | 优点 | 代价 | 本轮选择 |
| --- | --- | --- | --- |
| 卡片摘要与短动作，完整办理进入钉钉内现有页面 | 保留现有校验、附件、版本控制、字段提示及移动端；员工直接进入事项 | 少量复杂操作需要打开端内页面 | 推荐采用；已有进展保存仍可直接在卡片办理 |
| 所有目标/评分/异议表单都搬进卡片 | 很短的操作可减少跳转 | 重建多项目标、评分表和附件交互，需要另一套回调契约及错误恢复 | 不作为本轮模板新增范围 |
| 只有聊天，全部动作由模型执行 | 自然语言入口统一 | 正式提交、评分、权限和重复写入难以向员工明确解释 | 不采用作为正式业务写入路径 |

每张卡显示：事项名称、周期/月份、当前状态、必要摘要、一个主要动作。操作有明确反馈；等待别人办理时显示等待对象，不展示本人不能执行的写按钮。短卡默认至多一个主要动作和一个次要入口，完整细节留在办理页。

新增四类模板的数据变量采用字符串；无值的截止时间/次要动作整组隐藏。文本和按钮显示条件只用于呈现，不能代替后端授权。按钮 URL 由服务端依据上述固定路由生成，不能接受聊天或回调参数中的任意外部地址。

消息标题和聊天结果卡默认不放得分、等级、系数及完整评语；用户打开本人详情后，继续按线上已存在的结果字段可见配置展示。这是本轮卡片呈现建议，不改现有系统公示或权限配置。

## 4. 五类模板逐卡契约

### C1 我的绩效待办（新增）

**用途：** 一个事项一个清楚入口；承接目标、评价、复核、审批、独立改进计划等既有待办。用户没有待办时明确告知，不编造待办或阶段百分比。

**字段：** `title`、`subjectName`、`cycleLabel`（独立事项可为空）、`periodLabel`、`stateLabel`、`summary`、`dueLabel`（无计划时间则隐藏）、`primaryText`、`primaryUrl`、`secondaryText`、`secondaryUrl`。

**触发：** 用户主动查询，或已有业务事件在原通知策略和试点发送开关允许时触发。新模板本身不新增定时催办、每日提醒或自动向四人群发。

**状态与动作：**

| 状态 | 摘要 | 主要动作 |
| --- | --- | --- |
| 轮到本人办理 | 指明事项、月份、截止时间和待补内容 | “制定目标”“填写本月自评”“处理改进计划”等具体动作 |
| 已办理 | 显示完成时间和下一环节 | “查看已提交内容” |
| 等待其他处理人 | 显示后台可公开的当前处理角色 | “查看办理进度” |
| 无待办 | “当前没有需要你办理的绩效事项” | “查看我的绩效” |
| 事项已变化/结束 | 显示最新状态 | “查看最新状态” |

**权限：** 由现有后端当前处理人与本人待办规则产生；不能仅由静态 HR/主管角色或 `task.status` 判断。`approval` 在审批前是审批人的待办，批准后才是员工确认；月度待办需带 `periodId`。

### C2 绩效目标（新增）

**用途：** 支持线上已有的目标制定、审核反馈和员工确认。卡片展示摘要，完整指标、权重、上级对齐、逐项反馈仍在原页面办理。

**字段：** `cycleLabel`、`stateLabel`、`goalCount`、`summary`、`feedbackSummary`（存在本人有权查看的真实反馈时才显示）、`primaryText`、`primaryUrl`、`updatedLabel`。

| 实际状态 | 卡片文案 | 主要动作/页面 |
| --- | --- | --- |
| 本人可制定/修改 | “请完善本期考核目标并提交审核” | “制定目标” → `/tasks/:taskId?stage=goal-setting` |
| 已提交审核 | “目标已提交，等待绩效直属上级审核” | “查看已提交目标” → 同一任务的只读状态 |
| 真实审核退回 | 展示本人可见的退回摘要 | “根据反馈修改” → 原目标制定页 |
| 待员工确认 | “请核对上级审核后的目标” | “查看并确认目标” → `/tasks/:taskId?stage=goal-confirmation` |
| 目标已确认 | “目标已确认，可以持续记录工作进展” | “查看目标” → 原任务详情 |

**写入：** 本轮不通过新卡片直接提交整组目标、调整权重或替员工确认；原页面承担保存、提交、撤回及确认。正式目标基线变更继续使用既有版本与审核规则。

**AI 边界：** 用户聊天表达目标需求可以作为后续草拟目标能力的输入；本轮不能把它自动写成正式目标，也不展示“已替你提交审核”这样的未实现能力。

### C3 目标进展确认（复用现有模板）

**用途：** 对已确认且可更新的本人正式目标，显示待保存进展；员工明确保存后形成正式记录。

**契约沿用：** `state`、`goal`、`month`、`content`、`actualValue`、`targetValue`、`unit`、`healthStatus`、`completion`、`canSave`、`editLabel`、`editUrl`、`notice`。现有模板 ID 保持不变；文本变量 `canSave` 继续与分支传入的 `"true"` / `"false"` 一致。

| 状态 | 呈现 | 动作 |
| --- | --- | --- |
| 唯一匹配、信息齐全 | 目标、明确月份、待保存说明、量化实际/目标及完成度 | “修改”“保存进展” |
| 多目标/多月份/单位缺失 | “请先选择目标和月份/补充信息” | 只有“选择并补充”，不显示直接保存 |
| 定性进展 | 说明与本人确认的状态；不显示虚构 0% | 同上述准入规则 |
| 已保存 | 使用服务端已保存的值，显示“已保存” | “查看进展” → `/action-items?indicatorId=:indicatorId`，移除保存按钮，不再依赖草稿 TTL |
| 保存失败 | 私有提示保留本人输入，服务端未成功前不显示已保存 | 能重试时保留“保存进展”；否则引导当前有效页面 |
| 草稿过期/权限失效/月度锁定 | 明确说明真实原因和下一步 | 不再保留有效保存按钮 |

完成度可以超过 100%；日常实际值不回写考核评分的实际值字段。已提交自评/锁定月份不再写入；已经过去但仍开放的月份可按后端准入补充，不能一律按日历月份判定关闭。

### C4 绩效评价（新增，同模板支持月度和整周期）

**用途：** 让本人直接进入正确期间的自评，让被分配的上级直接进入对应评价；引用现有进展和原草稿，避免重复找月份。

**字段：** `cycleLabel`、`periodLabel`、`reviewRoleLabel`、`stateLabel`、`summary`、`dueLabel`、`primaryText`、`primaryUrl`、`submittedLabel`。必要的填写计数从本次已授权的评价详情计算，未读取详情时不猜填。

| 事项 | 主要动作 | 状态规则 |
| --- | --- | --- |
| 月度员工自评 | “填写本月自评” → `/tasks/:taskId?stage=self-eval&periodId=:periodId` | 待本人、已提交待上级、已完成/只读 |
| 整周期员工自评 | “填写周期自评” → 同一路由，使用 `periodType=cycle` 的实际期间 ID | 不伪造月份或月度进度 |
| 上级月度/整周期评价 | “填写本期评价” → 同任务、同期间的现有上级评价页 | 按后端 `canEdit` 和实际分配关系展示 |
| 上级周期结果评定 | “提交周期评定” → `/tasks/:taskId/final-grade` | 月度全部完成不等于该环节已完成 |
| 评价退回 | 展示真实退回原因摘要，进入原草稿 | 原页面重新读取 `draftVersion`，保留已有修改与历史 |

**写入：** 本轮新卡片不直接提交评分表；进入现有页面完成逐项评分、说明、等级及附件核对。员工附件继续遵循线上最多 10 个、单个 20 MB、提交后只读的规则。AI 整理自评草稿不在本轮模板新增范围，不自动打分、选等级或提交。

### C5 绩效结果（新增）

**用途：** 按实际审批和确认顺序，告诉员工何时需要核对结果，确认后等待什么；通过现有页面办理确认和异议。

**字段：** `cycleLabel`、`stateLabel`、`summary`、`primaryText`、`primaryUrl`、`updatedLabel`。本轮消息中不发送分数/等级/系数/评语，详情中沿用既有权限投影。

| 状态 | 卡片摘要 | 动作 |
| --- | --- | --- |
| 审批前 | 不向员工展示未获准的结果 | 通用待办/进度页，不生成“待确认结果”卡 |
| 审批通过、待员工确认 | “本周期结果已完成审批，请核对并确认；确认后进入 HR 公示” | “查看并确认结果” → `/tasks/:taskId?stage=result` |
| 员工已确认、尚未公示 | “结果已确认，等待 HR 公示” | “查看结果” |
| 员工提交不同意原因 | “结果已退回绩效直属上级重新评定” | “查看重评进度” |
| 重评再次审批通过 | “重新评定的结果已完成审批，请再次核对” | “查看并确认结果” |
| 结果已公示 | “本周期结果已公示” | “查看结果”；不能重新显示“不同意”写按钮 |

卡片不提供一键“确认结果/不同意”的新回调。点击进入原详情后使用现有“确认结果”“不同意”及二次确认；不同意原因 1～2000 字。重评状态必须来自真实异议流转记录及最新办理状态，不能将所有 `manager_scoring` 都称为重评。

线上仍保留历史“已公示但未确认”记录的兼容确认分支；这类记录从“查看结果”进入原详情按实际权限处理，不把它当成新周期的正常确认顺序。

## 5. 发送、更新与权限规则

1. 只使用经过本人的既有服务权限过滤后的数据构造卡片投影；结果数据不绕过 `publishVisibleFields`。
2. 卡片实例绑定接收人、事项类型、任务/期间、来源事件、模板版本。业务对象 ID、卡片 ID 和链接均不是授权。
3. 现有进展 `save` 回调保持原契约。其余四类首版使用受控端内链接，正式写动作仍由现有页面/API完成；不为卡片平行复制目标/评分/异议业务。
4. 打开卡片或办理时重新读取最新状态。旧卡不展示仍有效的过期动作；涉及草稿版本的原页面仍执行版本和并发检查。传入 `periodId` 时确认属于该任务，不能静默改选其他月份后提交。
5. 仅在企业机器人本人单聊使用，保持禁止转发设置；后端仍校验接收人/操作者，不能把禁止转发当作权限。
6. 同一事项状态事件对同一接收人去重。优先更新原卡为“已办理/状态已变化”，避免每个状态都产生一条新消息。发送失败不伪报业务失败或成功。
7. 通用通知与试点机器人收发分别保留既有配置边界；不得在新旧应用同时重复推送同一事项，也不得因有新模板自动打开通知开关。
8. 无待办、无周期、无目标、未审核通过、无身份绑定、月份锁定分别给出真实提示；不能统一显示“保存失败”。
9. 普通员工、上级、HR 的卡片内容取决于本次事项和实际权限。姚瑶具有 HR 身份不意味着本人卡片可以引用其他员工绩效。

## 6. 实施拆分与评审结论

| 部分 | 当前状态 | 后续最小工作 |
| --- | --- | --- |
| 进展模板 | 已在钉钉平台创建；分支一期代码/自动化验证已有，真实联调未完成 | 保留模板，先修已保存记录长期查看链接，再核对变量/保存回调与真人点击 |

## 8. 验收用例

- 员工从卡片进入准确的任务和月份；多周期、多月份不能因默认选择而写错对象。
- 目标审核退回后旧卡切换为需修改；已提交/已确认的卡片不执行旧写动作。
- 进展未点击保存零正式记录，重复保存至多一条；失败保留输入，成功显示服务端结果；量化超额/定性空完成度正确。
- 月度与整周期评价标题和入口正确；附件及评分字段沿用已有页面；提交后只读；退回保留原草稿并更新版本。
- 月度评价全部完成但周期等级未提交时，上级仍有待办；不能错误显示周期已完成。
- 结果审批前员工看不到结果；审批后按字段配置核对；确认后待公示；不同意带原因走重评，不进 HR 申诉台账；公示后不出现新异议按钮。
- 普通员工没有面谈台账编辑入口；改进计划始终用独立事项的实际待办与权限。
- 姚瑶作为本人只能写本人进展；卡片转发、切换账号、伪造期间及名单外访问全部被拒绝。
- PC 和 320/390px 下长目标、长反馈及无截止时间正常；一张短卡一个主动作，按钮不挤压或截断。
- API/页面成功但卡片更新失败时业务状态仍正确；重试不重复提交；取消时没有正式写入。
- 已保存超过 24 小时仍能从卡片进入正式目标进展详情；待保存草稿过期仍按原规则拒绝保存。
- 验证未打开全员消息、没有重复新旧应用推送、没有把模拟业务文本写入真实目标。
