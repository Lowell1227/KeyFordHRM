# 员工再入职与招聘入职接收设计

## 文档状态

- 日期：2026-09-18
- 状态：业务设计、书面设计和实施计划已确认
- 实施状态：尚未进入业务代码实现、业务代码提交或生产发布
- 适用范围：已离职或已归档员工再入职、待入职状态、账号恢复、招聘模块入职接收接口
- 主数据边界：HRM 员工档案与任职记录是人员和组织的正式来源；钉钉仅用于身份绑定、登录、通知和工作台入口

## 1. 与既有设计的关系

本设计扩展以下既有设计：

- `2026-08-19-employee-master-data-archive-design.md`
- `2026-09-01-personnel-master-maintenance-design.md`

若既有设计与本次已确认结论冲突，以本文为准。主要覆盖点为：

1. HR 管理员允许创建并审核本人提交的人员模块变更，不再限制必须由另一名管理员审核。
2. 再入职复用原员工主档和账号，但可分配新工号；旧工号必须保留为历史记录。
3. 审核通过不等于立即在职；未来入职日的员工进入独立“待入职”状态，到生效日才获得登录资格。
4. 合同、日期完整性、主管缺失等一般业务问题只作字段旁提醒，不阻断保存、提交或审核；仅身份冲突、重复员工、工号冲突等无法安全落库的问题阻断。
5. 用户可见业务术语统一使用“再入职”。现有 `EmploymentType.rehire` 表示用工类型“返聘”，不得因为员工发生再次入职就自动设置该值。

## 2. 背景与当前事实

当前系统已经具备以下基础：

- `User` 是员工长期稳定的账号和业务引用锚点。
- `EmploymentRecord` 保存带生效日期的任职历史。
- `EmployeeDataChangeRequest` 承载员工档案和任职变更审核。
- `User.archivedAt` 用于员工档案归档，归档后当前档案只读。
- 离职审核会结束任职、设置离职状态，并停用已启用的钉钉身份关联。
- 所有真实登录方式都会检查当前是否存在有效且非离职的任职记录；没有当前有效任职时拒绝登录。
- `EmployeeEffectiveDateService` 和定时任务能够按日期刷新当前任职投影。
- 招聘模块目前仅为规划入口，没有候选人、面试、Offer 等正式业务数据模型。

当前缺口是：离职或归档员工没有完整的再入职入口、待入职状态、账号按日期恢复机制，以及供未来招聘模块安全交接已接受 Offer 的稳定接口。

## 3. 目标与非目标

### 3.1 目标

- 同一自然人再次入职时复用原 `User.id`、员工主档和历史业务关系，不产生重复员工。
- 支持为再入职员工分配新工号，并完整保留所有历史工号。
- 支持草稿、HR 审核、待入职、按日期生效、取消和历史补录。
- 再入职生效时恢复标准用户能力，但不自动恢复历史 HR、管理员等高权限。
- 原钉钉身份确认仍属于本人时，在生效日恢复可用；冲突时由 HR 处理。
- 为未来招聘模块提供幂等、可审核、不会直接创建正式员工的入职接收契约。

### 3.2 本期非目标

- 不建设招聘职位、候选人、面试、Offer 或人才库页面。
- 不允许招聘系统直接创建正式员工、开放登录或写入组织主数据。
- 不根据姓名、手机号或钉钉通讯录自动合并员工。
- 不自动恢复员工离职前的系统管理权限。
- 不自动复用旧合同为新合同。
- 不把钉钉组织架构作为再入职部门、岗位或直属主管的来源。

## 4. 核心业务不变量

1. 一个自然员工始终只有一个长期 `User.id` 和一份员工主档。
2. 再入职新增任职历史，不覆盖或删除原离职记录、合同、绩效和审批历史。
3. 同一员工同一时点最多存在一条有效任职；同一员工最多存在一条未完成的入职或再入职申请。
4. 历史正式工号不得分配给其他员工；取消前仅预留但尚未生效的新工号可以释放。
5. 审核通过与正式生效是两个动作。未来生效申请在生效日前不得登录，也不得进入在职人员业务范围。
6. 系统权限、业务身份和用工类型相互独立：
   - 系统权限控制管理能力。
   - 直属主管、部门负责人等业务身份从新任职关系重新计算。
   - 用工类型描述全职、兼职、返聘、外援等用工形态，不表示是否曾经离职。
7. 任何登录方式都必须通过当前有效任职校验，不能仅凭账号、密码或钉钉绑定绕过。

## 5. 人员与工号设计

### 5.1 主档复用

再入职必须选择现有已离职或已归档员工，申请始终关联原 `User.id`。审核和生效过程不得创建第二个 `User`、第二份员工档案或新的钉钉身份主体。

员工匹配遵循以下优先级：

1. 明确传入的 `existingEmployeeId`。
2. 已确认且唯一的外部身份映射。
3. HR 根据疑似匹配结果人工确认。

姓名、手机号、邮箱等只用于提示疑似历史员工，不得作为自动合并依据。

### 5.2 工号

- `User.employeeNo` 表示当前或下一段已确认任职使用的工号。
- 每条任职记录保存当次工号快照，历史查询不依赖 `User.employeeNo` 当前值。
- 系统维护工号占用/历史登记，保证历史正式工号不能分配给其他员工。
- 再入职可以使用原工号，也可以分配新工号。
- 新工号在申请提交时预留，审核退回时继续随草稿保留；取消申请时释放。
- 生效后，新工号成为当前工号，旧工号保留在任职历史和工号历史中。

## 6. 状态模型

### 6.1 用户可见状态

员工档案列表统一使用：

```text
全部｜在职｜试用期｜待入职｜已离职｜草稿｜已归档
```

“待入职”是独立人员生命周期状态，不与草稿或已离职混用。实现时增加对应 `UserStatus` 枚举值，并确保现有只查询在职/试用期的业务范围不会把待入职人员纳入。

### 6.2 申请状态

```text
草稿
  -> 待审核
      -> 已退回 -> 草稿
      -> 审核通过
          -> 待入职
              -> 已取消
              -> 已生效
```

- HR 管理员可以审核本人创建的申请。
- 审核通过且生效日在未来：员工取消归档、状态变为待入职，但不能登录。
- 审核通过且生效日为今天或更早，并且任职当前有效：立即生效。
- 生效日前修改工号、部门、岗位、直属主管、入职日或用工类型等关键字段时，必须形成新版本并重新审核，不能静默修改已审核记录。
- 生效日前可以取消；生效后不能取消，只能通过新的离职流程结束任职。

### 6.3 取消恢复

申请必须保存审核前快照。取消待入职时：

- 撤销待生效任职。
- 恢复原来的已离职或已归档状态。
- 恢复原归档时间和原当前工号投影。
- 释放尚未生效的新工号预留。
- 保留申请、审核、取消原因和操作者审计记录。

## 7. 再入职流程

### 7.1 发起

- 已离职和已归档员工的操作列显示“办理再入职”。
- 点击后打开右侧抽屉，不自动解除归档或恢复账号。
- 抽屉首先展示姓名、历史工号、最近任职部门、最近岗位、原直属主管和离职日期，帮助 HR 核对人员。

### 7.2 填写内容

本次再入职至少包含：

- 新工号或确认继续使用原工号。
- 公司、部门、岗位和直属主管。
- 计划入职/生效日期。
- 员工状态：入职后在职或试用期。
- 用工类型与试用期信息。
- 合同草稿或附件引用（可选）。
- 钉钉绑定状态提示。
- 来源系统和来源编号。

### 7.3 审核

再入职复用人事变更审核，变更类型显示“再入职”。审核表沿用统一结构：

```text
序号｜变更类型｜审核对象｜变更内容｜提交人｜提交时间｜操作
```

“变更内容”集中展示新工号、部门、岗位、直属主管、计划入职日、合同和钉钉状态。详细前后值、提醒和附件在抽屉中按需展开。

审核人只有“退回”和“通过”两类业务动作。审核是二次确认，不执行复杂自动判断，也不要求换人审核。

### 7.4 审核通过

审核通过时在一个事务中：

1. 锁定申请和目标员工，防止重复审核或重复再入职。
2. 解除员工档案归档并记录原状态快照。
3. 创建未来生效的任职记录，保留原离职记录不变。
4. 预留或更新新工号，保留旧工号历史。
5. 将系统权限重置为“标准用户”。
6. 清除不应自动继承的 HR、系统管理员等管理权限；业务身份等待新关系重新计算。
7. 未来生效时把员工状态设为待入职；当天或追溯且当前有效时直接执行生效。
8. 写入完整审计，但不在未来生效日前开放登录。

## 8. 生效、账号和钉钉身份

### 8.1 生效处理

到达生效日后，员工任职生效服务更新 `User` 当前兼容投影：

- 当前工号。
- 公司、部门、岗位。
- 直属主管。
- 入职、转正和离职日期。
- 用工类型。
- 在职或试用期状态。

定时任务负责批量生效；登录前和关键人员查询前执行轻量补偿检查，避免定时任务短暂延迟导致已到日期的员工无法登录或状态滞后。补偿必须幂等。

### 8.2 系统权限

- 再入职员工统一恢复为“标准用户”。
- 历史 HR、HR 管理员、系统管理员、绩效专员等高权限不自动恢复。
- 直属主管、部门负责人、绩效直属上级、最终业务审批人等业务身份从新组织和业务关系重新计算。
- 需要管理权限时，由系统管理员走现有权限维护入口另行授予。

### 8.3 钉钉身份

- 原未结束钉钉绑定仍属于该员工且不存在冲突时，在生效日恢复为启用。
- 未绑定或绑定缺失时，员工正常生效，但暂时不能使用钉钉登录，由 HR 后续绑定。
- 钉钉身份已绑定给其他员工时，只提示冲突并禁止该身份登录，不阻断员工任职生效。
- 钉钉组织、部门和主管信息不得回写本次任职。
- 本地密码登录和钉钉登录都必须通过当前有效任职校验。

## 9. 合同处理

- 原合同保留为历史，不自动复制、续签或重新启用。
- 本次再入职可以创建新合同草稿或关联已上传附件。
- 未录入合同只在字段旁显示提醒，不阻断保存、提交、审核或任职生效。
- 合同继续使用独立合同记录和审核，不塞入任职记录。
- 合同重叠、签署日期缺失、续签未关闭旧合同等均为可见提醒；只有引用不存在、文件损坏等技术上无法保存的问题阻断。

## 10. 校验原则

### 10.1 提醒但不阻断

以下问题使用字段旁橙色文字或小型状态提醒，不使用顶部难懂错误，也不阻断操作：

- 未上传新合同。
- 试用期日期不完整。
- 入职日期早于当前日期。
- 部门负责人或直属主管尚未设置。
- 钉钉账号尚未关联。
- 已结束的历史任职区间疑似重叠但仍可形成补录；若会同时产生两条当前有效任职，则按下一节阻断。

### 10.2 必须阻断

只有无法保证人员唯一性或引用完整性的情况阻断：

- 目标员工当前已经存在有效在职任职。
- 该员工已经存在一条未完成的入职或再入职申请。
- 新工号已被其他员工当前使用或作为其历史正式工号保留。
- 同一员工同一时点出现两条将同时成为当前任职的记录。
- 明确指定的员工、部门或岗位不存在。
- 钉钉身份已绑定给其他员工时禁止自动启用该绑定，但不阻断任职生效。
- 同一来源编号重复提交但内容不一致。

阻断信息必须指出冲突对象和下一步处理方式。

## 11. 历史补录

- 允许 HR 录入过去发生的再入职任职。
- 补录记录覆盖当前日期且仍有效时，审核通过后立即刷新当前投影和登录资格。
- 补录记录已经结束时，只增加任职和工号历史，不开放账号、不改变当前人员状态。
- 历史重叠先提示 HR；查询历史时仍沿用现有“生效日起始日较晚者作为临时结果”的兼容规则，并保留审计提醒。
- 历史补录不得改写已启动绩效周期冻结的组织和绩效直属上级关系。

## 12. 招聘入职接收接口

### 12.1 领域边界

未来招聘模块负责：

- 招聘需求和职位。
- 候选人、面试和沟通。
- Offer 发放和接受状态。

人员模块负责：

- 自然人和历史员工匹配。
- 新员工或再入职判断。
- 工号、公司、部门、岗位和直属主管。
- HR 审核、任职记录、合同、账号和生效。

招聘模块在 Offer 被接受后只能创建入职草稿，不能创建正式员工、直接写任职、开放登录或写入 HRM 组织树。

### 12.2 接口契约

预留领域接口：

```text
POST /api/v1/employee-archives/onboarding-intakes
```

请求核心字段：

```text
sourceSystem       来源系统，manual 或 recruitment
sourceReference    来源唯一编号，例如 offerId
intakeType         new_hire 或 reentry
existingEmployeeId 再入职时由 HR 明确选择的历史员工 ID
identitySnapshot   姓名、联系方式及已知外部身份摘要
employeeNo         拟使用工号
company/dept/position/directManager
effectiveDate      计划入职和生效日期
employmentType/probation
contractReferences 合同草稿或附件引用
```

响应核心字段：

```text
intakeId
matchStatus        new / matched_reentry / needs_review / conflict
matchedEmployeeId
recordStatus
nextAction
```

### 12.3 幂等与匹配

- `(sourceSystem, sourceReference)` 是幂等键；相同内容重复提交返回原草稿。
- 相同幂等键但内容不一致时返回明确冲突，不覆盖原草稿。
- 再入职请求原则上必须提供 `existingEmployeeId`；外部系统无法确认时返回 `needs_review`，由 HR 匹配。
- 姓名、手机号和邮箱只能生成候选提示，不能自动合并。
- 员工正式生效后，人员模块向来源系统返回或提供查询 `employeeId`、入职状态和生效时间；不回传不必要的敏感档案。

本期只实现可供手工新增和再入职复用的入职接收能力及来源元数据，不建设招聘业务表和招聘页面。

## 13. 页面交互

### 13.1 员工档案列表

- 列表保持单一员工列表，不重复展示组织树。
- 查询面板位于状态标签上方，状态标签紧邻列表。
- 已离职、已归档员工显示“办理再入职”。
- 待入职员工显示“查看入职”“修改并重新审核”“取消入职”。
- 正式生效后恢复普通员工操作，不再显示再入职入口。

### 13.2 再入职抽屉

抽屉采用三个紧凑区块：

1. 历史身份：姓名、历史工号、最近部门、最近岗位、离职日期。
2. 本次入职：新工号、组织岗位、直属主管、入职日期、用工类型、试用期。
3. 关联信息：合同草稿、钉钉状态、来源系统。

底部显示审批流程：

```text
已创建 -> HR 审核 -> 待入职 -> 已生效
```

退回、取消或冲突信息显示在相应节点和字段附近，说明性长文字收进问号提示。

## 14. 数据模型调整

实施阶段采用最小向前兼容扩展：

1. `UserStatus` 增加待入职状态。
2. `EmploymentRecord` 增加工号快照及与申请的来源关联。
3. 增加 `EmployeeNumberAssignment` 工号占用/历史登记：至少包含员工、工号、状态、首次生效日、结束日、来源申请和释放时间。状态覆盖预留、当前、历史和已释放；预留、当前和历史状态下工号跨员工唯一，只有未生效且已释放的预留号可以再次使用。
4. `EmployeeDataChangeRequest` 增加可索引的 `sourceSystem`、`sourceReference`、`intakeType` 和申请版本/取消字段；申请详细内容仍保存于前后值 JSON。
5. 对 `(sourceSystem, sourceReference)` 建立唯一约束；同一来源需要重新办理时，在原入职接收记录下创建新申请版本，不生成第二个来源记录。
6. 不新增第二套员工、合同或招聘候选人表。

具体字段命名和数据库约束在实施计划中结合现有 Prisma 迁移细化，但不得削弱本文的人员唯一性、工号历史、幂等和生效边界。

## 15. 并发、审计与失败处理

- 提交、审核、生效、取消均按申请 ID 幂等。
- 审核时锁定员工和申请，避免并发产生两条待入职记录。
- 生效过程在单事务中更新任职、工号、当前投影、权限、钉钉状态和审计；失败整体回滚并保留可重试状态。
- 定时生效失败必须记录明确错误并可重试；登录补偿只能执行同一幂等生效逻辑。
- 记录创建人、审核人、生效人/任务、取消人、前后值、来源系统和来源编号。
- 日志和接口响应不得暴露完整手机号、身份证号、合同附件地址或钉钉身份明文。

## 16. 测试与验收

### 16.1 API 与数据测试

- 原员工再入职始终复用原 `User.id`，员工列表仍为一人一行。
- 新工号生效、旧工号保留且不能分配给其他员工。
- 同一员工重复提交、重复审核、重复生效和重复取消均幂等。
- 待入职期间没有当前有效任职，所有真实登录方式均被拒绝。
- 生效日后即使定时任务延迟，登录补偿也能安全完成投影刷新。
- 取消后恢复原离职/归档状态，并释放未生效工号。
- 历史补录不错误改变当前任职或已启动绩效快照。
- 招聘来源重复提交不产生重复草稿或重复员工。

### 16.2 真实角色浏览器验收

- HR 管理员能对已离职和已归档员工发起再入职并审核本人申请。
- 待入职员工在独立标签中可查，能查看流程、修改后重新审核或取消。
- 普通员工在生效日前不能登录，生效日后使用标准用户权限登录。
- 历史 HR/管理员权限没有自动恢复。
- 原钉钉绑定属于本人时在生效日恢复；冲突时页面给出明确处理提示。
- 员工详情能看到历史工号、每段任职和新旧合同，不出现重复员工。
- PC 和手机端验证抽屉滚动、长文本、字段提醒和固定操作区。

### 16.3 成功标准

上线后必须同时满足：

1. 再入职不产生重复员工、重复账号或重复钉钉身份。
2. 审核通过、生效日期和登录资格严格分离。
3. 工号变更可追溯，历史正式工号不会被其他员工占用。
4. 再入职只恢复标准用户权限，管理权限必须另行授予。
5. HR 可完成发起、自审、待入职维护、取消和历史补录。
6. 一般业务校验只提醒，数据完整性冲突才阻断，错误信息可理解并有下一步。
7. 招聘模块未来可以通过稳定接口移交 Offer 接受结果，但不能越过 HR 审核和正式生效。
8. 钉钉组织始终不会覆盖 HRM 人员、岗位、部门或主管关系。

## 17. 实施边界

书面设计通过后，实施计划按以下顺序拆分：

1. 状态、工号历史和入职来源数据模型。
2. 再入职草稿、审核、取消和生效领域服务。
3. 登录准入、标准权限重置和钉钉身份恢复。
4. 入职接收 API 与幂等匹配。
5. 员工列表、再入职抽屉、审核页和流程状态。
6. API、Web、迁移、角色验收和生产发布。
