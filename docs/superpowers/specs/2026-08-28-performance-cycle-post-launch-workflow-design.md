# 绩效周期发起后工作流设计

> 日期：2026-08-28
>
> 状态：业务方案已逐项确认，等待文档整体审阅
>
> 范围：绩效周期正式发起后，直至结果确认及历史更正
>
> 前置设计：[周期计划发起前工作流设计](./2026-08-28-cycle-plan-prelaunch-workflow-design.md)
>
> 关联设计：[组织调岗与绩效交接设计](./2026-08-28-organization-transfer-performance-handoff-design.md)

## 1. 设计目标

本设计把周期发起后的员工执行、直属上级评分、逐级审核、结果审定、员工确认和历史更正串成一条连续工作流。

目标是：

1. 员工和各级管理者始终从现有“绩效待办”进入，不增加新的学习路径。
2. 月度评分、周期汇总和周期审核各自职责清楚，避免把一整个季度拆成三套相互独立的流程。
3. 直属上级、部门负责人、HR、分管总和最终负责人只处理自己应负责的环节。
4. 人员转正、离职、调岗、长期缺勤等变化不靠手工改分，而是通过可追溯的人员范围和任务交接规则处理。
5. 所有正式结果都有版本、来源、操作记录和更正历史，不用覆盖旧数据。

## 2. 设计边界

### 2.1 本文包含

- 周期类型与评分频率；
- 月度任务生成、开放、逾期和提醒；
- 员工自评、直属上级逐指标评分和自动汇总；
- 指标版本及跨月生效；
- 周期汇总、收尾和例外人员处理；
- 部门负责人审核、HR 校准、分管总审核和最终审定；
- 结果发布、员工确认和历史结果更正；
- 旧“最终业务审批人”的兼容处理；
- 发起前、组织调岗与发起后流程的衔接。

### 2.2 本文不包含

- 重新设计已经认可的“绩效待办”页面布局；
- 公司范围的绩效排名公示；
- 员工结果申诉入口；
- 组织架构调岗操作本身；
- 当前阶段的开发排期和技术实施拆分。

## 3. 统一业务术语

| 术语 | 统一含义 |
| --- | --- |
| 周期参与任务 | 一名员工在一个绩效周期中的总任务 |
| 月度考核记录 | 周期参与任务下某个月的执行和评分记录 |
| 月度正式评分 | 直属上级对当月每个指标提交评分后，系统自动计算出的月度总分 |
| 周期结果 | 一个周期内所有有效月份汇总后的结果，或非月度评分周期的一次整体结果 |
| 部门负责人审核 | 部门负责人对本部门员工的周期结果进行审核 |
| HR 校准 | HR 对结果分布、异常和一致性进行校准审核 |
| 分管总审核 | 李宏、倪靖、郭志浩按各自分管范围审核 HR 校准后的结果 |
| 最终审定 | 李宏以公司最终负责人身份对公司结果作最终决定 |
| 结果更正 | 已形成结果后，经申请和复核重新评分并生成新版本；不称为申诉 |
| 直属上级 | 绩效上下级关系的唯一来源；来自本系统组织架构中的直属上级关系 |

旧页面、旧数据和历史任务可以继续显示历史术语，但新周期、新任务和新操作统一使用上表名称。

## 4. 保留现有绩效待办交互

现有“绩效待办”页面的整体布局、筛选方式、员工/团队分栏和任务列表样式保留。

### 4.1 我的绩效待办

- 目标制定；
- 目标确认；
- 自评；
- 结果确认。

“目标确认”继续保留，不因本次流程整理而取消。

### 4.2 我的团队绩效待办

- 指标审核；
- 主管评分；
- 结果审核。

“结果审核”沿用同一页面和列表样式，通过任务上的角色标签区分：

- 部门审核；
- HR 校准；
- 分管审核；
- 最终审定。

用户只需要理解“现在轮到我做什么”，不需要先进入一个新的流程管理工作台。

## 5. 周期类型与评分频率

### 5.1 月度周期

- 固定按月评分；
- 不显示“按月度评分”开关；
- 一个周期只生成一个月度考核记录。

### 5.2 季度、半年、年度周期

创建计划时提供“按月度评分”选项，默认选中。

选中后：

- 发起时一次生成 3、6 或 12 个月度考核记录；
- 未来月份先生成但不开放；
- 每个月都有员工自评、直属上级逐指标评分和月度总分；
- 周期结束时对有效月份做周期汇总，然后只走一次完整审核链。

未选中时：

- 周期结束前只进行一次整体自评；
- 直属上级对周期指标逐项给出正式评分；
- 系统计算一个周期总分；
- 之后走一次完整审核链。

### 5.3 自定义周期

- 只按整个周期评分；
- 不提供月度评分开关；
- 只形成一个周期整体结果。

### 5.4 配置变更边界

评分频率属于计划核心内容。计划审核通过后如果更改评分频率，原计划审核结论失效，必须重新检查并重新提交审核，不能在进行中的周期里直接切换。

## 6. 月度时间计划

### 6.1 默认规则

对于上一自然月的考核：

1. 次月第 1 个法定工作日 09:00 开放员工自评；
2. 次月第 3 个法定工作日 18:00 为员工自评计划完成时间；
3. 再后第 3 个法定工作日 18:00 为直属上级评分计划完成时间；
4. 员工提前提交后，直属上级无需等待员工截止时间，可立即评分。

### 6.2 HR 调整

系统先按默认规则生成全部月份，HR 可在默认时间基础上调整：

- 统一调整全部月份规则；
- 单独调整特殊月份；
- 单月恢复默认；
- 全部恢复默认。

统一调整时，如果已有特殊月份，系统明确让 HR 选择“保留特殊月份”或“覆盖全部月份”。

### 6.3 校验强度

- 节点先后顺序错误：阻止保存；
- 跨月、间隔过长、非工作日或与其他节点重叠：提示风险，但允许 HR 确认保存；
- 计划审核通过后调整时间计划：需要重新提交计划审核。

## 7. 数据结构与版本原则

### 7.1 业务结构

```text
绩效周期
└─ 周期参与任务（员工 × 周期）
   ├─ 月度考核记录（0..12）
   │  ├─ 当月指标快照
   │  ├─ 员工自评
   │  ├─ 直属上级逐指标评分
   │  ├─ 月度总分
   │  └─ 修订版本
   ├─ 周期汇总结果
   ├─ 审核链记录
   └─ 员工最终确认
```

季度、半年和年度周期不是拆成多个独立周期；月度考核记录始终归属于同一个周期参与任务。

### 7.2 版本原则

- 已提交的正式评分不直接覆盖；
- 已开放月份保存当时使用的指标快照；
- 更正生成新修订，旧修订作废归档但可查；
- 汇总和报表只使用最新有效修订；
- 所有变更记录申请人、审批人、原因、时间和新旧差异。

## 8. 指标版本及跨月生效

### 8.1 按月度评分的周期

- 周期发起时创建指标版本 V1，默认适用于全部月份；
- 中途调整指标时创建新版本，例如 V2；
- 发起人自由选择 V2 从当前月或未来某个月开始生效；
- 生效月之前继续使用 V1；
- 生效月及以后尚未完成的月份使用 V2；
- 月份开放时，把当时有效的指标版本冻结为该月快照。

已经形成直属上级正式评分的月份不被新版本覆盖。若确需改变往月评分，必须发起结果更正申请；审批通过后，旧评分作废归档，该月接受新指标和新评分。

### 8.2 非月度评分的周期

- 中途可以调整指标，记录原因和生效日期；
- 周期最终评分使用最新审批通过的指标版本；
- 历史版本完整保留；
- 不按新旧指标的使用天数做加权拆分；
- 已形成正式周期评分后再调整，进入结果更正流程。

## 9. 月度执行与直属上级评分

### 9.1 月度状态

月度考核记录使用以下主状态：

1. 未开放；
2. 员工自评；
3. 直属上级评分；
4. 已完成；
5. 结果更正中。

“已逾期”是附加标签，不另建主状态。

这些状态用于表达当前主要处理环节，不代表员工自评和直属上级评分必须严格串行。员工未自评时，直属上级评分任务仍可开放；页面分别显示两项任务的实际完成情况。

### 9.2 员工自评

- 员工按当月同一组有效指标填写自评；
- 到期后入口不关闭，仍可继续填写；
- HR 可提醒；
- 员工未自评不阻止直属上级评分；
- 在直属上级正式提交前，员工仍可补交自评；
- 直属上级正式提交后，当月锁定。

季度、半年和年度周期只要启用了“按月度评分”，普通员工每个月都需要自评，本要求不因周期较长而丢失。

### 9.3 直属上级评分

- 每个指标必须有正式分数；
- 系统自动计算月度总分，不要求主管重复输入总分；
- 直属上级正式提交后锁定当月；
- 后续修改只能通过结果更正；
- 绩效上下级只取本系统组织架构中的直属上级，不取花名册的“直属主管”字段，也不取钉钉组织关系。

### 9.4 分数可见性

直属上级正式提交后，员工可以立即看到该月正式评分，同时页面明确显示：

- “月度评分已完成”；
- “周期结果尚未审核/审定”。

员工此时无需按月确认，也没有申诉入口。若月度评分后来发生结果更正，默认显示最新有效版本，并可查看历史版本。

## 10. 人员变化与有效月份

### 10.1 试用期员工

- 处于试用期的员工不进入本绩效计划；
- 员工转正后，系统生成“参与范围变更待确认”；
- HR 确认是否加入当前周期，并选择从当前月或未来某月生效；
- 不自动追补试用期月份。

### 10.2 离职员工

- HR 确认最后一个有效考核月；
- 默认建议离职当月，可改为前一个月；
- 后续月份标记“因离职终止”；
- 终止月份不生成零分、不记逾期，也不进入平均；
- 有有效月份时按有效月份汇总；
- 没有任何有效月份时显示“未形成绩效结果”。

### 10.3 最高负责人

李宏作为公司最终负责人，没有上级评价人：

- 个人绩效标记“最高负责人豁免”；
- 不生成员工自评、主管评分或个人绩效结果；
- 不进入个人绩效平均；
- 其公司级管理和最终审定权限不受影响。

### 10.4 长期缺勤与月份免评

长期病假、产假、停薪留职等状态在员工档案维护：

```text
人员 → 员工档案 → 任职状态记录
```

绩效模块不另设“月份免评”编辑入口，只消费员工档案产生的状态：

- 保存任职状态时，系统展示受影响的绩效周期和月份，并给出免评建议；
- 整月缺勤默认建议免评；
- 部分月份缺勤默认继续参评，HR 管理员可填写原因后改为免评；
- 影响进行中周期时，由 HR 管理员确认；
- 免评月份不生成任务、不记逾期、不记零分，也不进入平均；
- 已有正式评分的月份不能直接改为免评，必须进入结果更正。

### 10.5 调岗与直属上级变化

调岗发生在本系统组织架构，不修改员工档案中的公司信息和合同信息。绩效交接遵循关联设计：

- 调岗可立即生效，也可选择未来某个月生效；
- 若当月原直属上级尚未正式提交评分，生效后由新直属上级接手；
- 若原直属上级已正式提交，当月结果保留，后续月份交给新直属上级；
- 原直属上级保留自己已处理月份的只读记录，不能再处理未来月份；
- 新直属上级可查看接管后的任务以及同一周期内必要的历史上下文；
- 全部 HR 可查看调岗记录，便于补位和追溯。

## 11. 周期汇总与收尾

### 11.1 按月度评分

- 周期总分 = 全部有效月份正式总分的等权平均；
- 不设置月份权重；
- 每个月只取最新有效评分修订；
- 免评、离职终止和未纳入月份不进入分母；
- 任一应评分月份缺少直属上级正式分数时，周期总分显示“待生成”，不得把缺失月份按零分计算。

### 11.2 非月度评分

直属上级对周期指标逐项正式评分后，系统自动形成一次整体总分。

### 11.3 收尾处理中

周期时间结束但仍有应完成的主管评分时，周期进入“收尾处理中”，不能直接标记“已结束”。HR 管理员可以：

- 提醒；
- 延长处理时间；
- 按已确认的交接规则重新指派；
- 对确实无法考核的月份填写原因并标记“无绩效结果”。

所有应完成月份已完成或已按规则处理后，系统才生成周期结果并进入审核链。

## 12. 周期级结果审核链

### 12.1 审核频率

采用“按周期审核”：

- 月度周期：当月汇总后审核一次；
- 季度、半年、年度按月评分：各月完成员工与主管环节，周期结束汇总后审核一次；
- 季度、半年、年度不按月评分：整体评分完成后审核一次；
- 自定义周期：整体评分完成后审核一次。

不为季度的每个月重复执行整套部门、HR、分管总和最终审定流程。

### 12.2 完整链路

```text
员工自评
  → 直属上级评分
  → 部门负责人审核
  → HR 校准
  → 分管总审核
  → 李宏最终审定
  → 员工结果确认
```

### 12.3 部门负责人审核

- 按周期审核本部门员工；
- 查看员工指标、月度总分、周期总分和主管评价；
- 可以通过，也可以将某名员工退回直属上级；
- 不能直接修改评分；
- 退回只影响被退回员工；
- 部门负责人不能审核自己的绩效，其本人结果从直属上级评分后直接进入 HR 校准。

### 12.4 HR 校准

现有“结果审批”统一调整为“结果校准”，不再保留一个内容重复的 HR 结果审批环节。

HR 校准负责：

- 查看整体分布、异常值和跨部门一致性；
- 退回某名员工给相应直属上级重新处理；
- 不能直接编辑业务评分；
- 校准完成后生成不可变的“HR 校准结果快照”，再提交分管总。

### 12.5 分管总审核

分管总为李宏、倪靖、郭志浩：

- 只查看 HR 校准后的结果快照，不查看尚未校准的过程结果；
- 倪靖、郭志浩只审核各自分管范围；
- 可以通过，也可以将本分管范围退回 HR 重新校准；
- 不能直接修改分数；
- 退回只影响对应分管范围，不重开其他已通过范围；
- 倪靖、郭志浩的分管范围全部通过后，才能进入公司最终审定。

李宏兼具分管总和公司最终负责人身份。李宏所分管范围不再要求他先做一次“分管审核”再做一次“最终审定”，而是在最终审定时一并处理，避免重复点击。

### 12.6 李宏最终审定

- 查看全公司经 HR 校准、且相关分管总已经审核通过的结果；
- 可以全部审定并发布；
- 可以把某一分管范围退回 HR 重新校准；
- 退回不影响其他已通过范围；
- 只有最终审定完成后，周期结果才成为可供员工最终确认的正式结果。

## 13. “最终业务审批人”的处理

### 13.1 现有含义

现有“最终业务审批人”是按部门/业务范围产生的审批责任人，并不是公司层面的最后决策人。系统当前还会在周期发起时把该责任人固化到员工任务中。

### 13.2 新周期中的统一命名

新周期拆分为两个不同概念：

| 新概念 | 作用范围 | 人员来源 | 权限 |
| --- | --- | --- | --- |
| 分管总审核人 | 指定分管范围 | 维护李宏、倪靖、郭志浩与分管范围的映射 | 审核或退回本范围 HR 校准结果 |
| 公司最终审定人 | 全公司 | 固定为李宏 | 最终审定、发布或退回某范围 |

现有“最终业务审批人”在新周期中的业务位置改为“分管总审核人”，不再承担公司最终审定含义。

### 13.3 历史兼容

- 已发起的历史周期继续使用原“最终业务审批人”字段、名称、任务和权限；
- 不批量迁移历史任务；
- 新周期使用新的分管总和公司最终审定人配置；
- 现有部门审批人映射不能未经核对直接视为分管范围，启用新流程前需由 HR 确认各组织范围分别归属李宏、倪靖或郭志浩；
- `canViewAll` 只代表查看范围，不能据此获得审核、退回或最终审定写权限；
- 系统管理员身份也不自动获得业务审核权限。

## 14. 结果发布与员工确认

### 14.1 发布

- 李宏最终审定通过时完成正式结果发布；
- 不另设一个重复的“结果公示”工作流；
- 不提供全公司公开排名或员工互看结果。

原主菜单“结果公示”不再作为新流程入口；如有历史数据，只提供历史只读查看。

### 14.2 员工结果确认

- 员工只在整个周期最终结果发布后确认一次；
- 页面只有“确认”按钮；
- 不提供申诉理由输入框或申诉入口；
- 到期后入口不关闭，可继续确认；
- HR 可以提醒；
- 不自动代员工确认；
- 员工未及时确认不阻止周期结束，系统记录实际确认时间。

员工结果确认的作用是“确认已知悉正式结果”，不是重新发起结果争议。

### 14.3 申诉历史

新流程不再使用“申诉管理”主菜单。既有申诉数据保留为只读历史档案；后续需要改动结果时统一进入“结果更正”。

## 15. 已结束周期的结果更正

### 15.1 发起与审批

- 员工或直属上级均可对本人/本人负责的往期月份发起结果更正申请；
- 申请说明需要重评的月份、原因和拟使用的指标版本；
- HR 管理员审批申请；
- 审批通过后，原月份评分作废归档，并开放新的评分修订；
- 审批驳回则保持原结果有效。

### 15.2 更正范围

- 只重评受影响员工和月份；
- 不重开整个周期；
- 不影响其他员工；
- 新月度评分完成后，系统重新计算该员工周期总分；
- 原月度结果、原周期结果和原员工确认记录作为历史版本保留。

### 15.3 HR 结果更正复核

重新评分后由 HR 进行一次定向“结果更正复核”：

- 对比新旧指标、月度评分、周期总分和分布影响；
- 只能通过或退回，不能直接编辑分数；
- 通过后新版本成为最新有效结果；
- 员工重新确认；
- 周期继续保持“已结束”，列表增加“结果更正中”标签，不回退为“进行中”。

报表默认使用最新有效结果，同时允许查看历史版本。

## 16. 权限与数据可见范围

权限由“角色 + 数据范围 + 当前任务责任人”共同决定，查看权限与操作权限分开。

| 角色 | 可查看 | 可操作 |
| --- | --- | --- |
| 员工 | 本人指标、自评、主管已正式提交的月度评分、最终周期结果 | 本人自评、最终结果确认、本人结果更正申请 |
| 当前直属上级 | 当前下属及同周期必要历史上下文 | 自己负责月份的评分、退回后的重评、结果更正申请 |
| 原直属上级 | 自己曾负责并提交的月份 | 只读，不可处理未来月份 |
| 部门负责人 | 本部门待审核周期结果 | 通过或退回本部门员工，不可改分 |
| 周期 HR 负责人/HR 管理员 | 周期、人员变化、执行进度及校准所需结果明细 | 范围确认、提醒、收尾处理、HR 校准、结果更正审批/复核 |
| 其他 HR | 全部周期、流程进度、人员变化和调岗历史 | 仅处理自己被明确分配的 HR 任务；不因 HR 身份自动获得改分或审批权 |
| 倪靖、郭志浩 | 各自范围的 HR 校准结果快照 | 分管审核或退回本范围 |
| 李宏 | 全公司 HR 校准及最终结果 | 公司最终审定、发布或退回某范围 |
| 系统管理员 | 系统配置及授权所需信息 | 不因系统角色自动成为业务审核人 |

详细分数不得因为 `canViewAll`、系统管理员或普通 HR 身份被无条件扩大。需要参与校准或周期运营的 HR，应通过周期责任或明确授权获得相应明细范围。

## 17. 通知、提醒与日志

### 17.1 通知原则

- 待办产生时通知当前责任人；
- 临近计划完成时间可提醒；
- 逾期不关闭任务，持续保留待办；
- HR 可按员工、部门、月份或当前环节提醒；
- 退回时通知被退回责任人，并展示原因和下一步；
- 责任人因调岗变化时，通知新旧直属上级和周期 HR 负责人。

### 17.2 审批日志

所有审核和更正记录像日志一样跟在对应表单或结果详情下方，至少包括：

- 环节；
- 操作人及当时角色；
- 操作时间；
- 通过、退回、作废、重新提交等动作；
- 原因或说明；
- 影响范围；
- 对应结果版本。

## 18. 管理列表与状态衔接

发起前设计中的三大列表分组继续使用：

- 筹备中；
- 进行中；
- 已结束。

周期正式发起后进入“进行中”。卡片和详情同时显示两个维度：

1. 周期主状态，例如“进行中”“收尾处理中”“已结束”；
2. 当前业务环节，例如“员工自评”“主管评分”“HR 校准”“分管审核”“最终审定”“员工确认”。

补充标签包括：

- 已逾期；
- 存在免评月份；
- 人员范围待确认；
- 结果更正中；
- 最高负责人豁免。

每个卡片只保留一个最主要操作，其他操作收入口中；详情页展示计划摘要、当前任务、受阻原因、下一步和完整日志。

## 19. 现有模型的实施影响

本节只记录未来实施时必须处理的结构差异，不代表本阶段进入开发。

1. 当前 `AssessmentTask` 主要按“员工 × 周期”建模，缺少独立月度记录层，需要增加月度实体而不是把月份塞进一个 JSON 字段。
2. 当前指标实例只容纳一次自评/主管评分，需要把评分绑定到月度记录和修订版本。
3. 当前流程记录主要绑定单个任务，需要能够记录周期级部门审核、HR 校准、分管范围审核和公司最终审定。
4. 当前计划时间字段不能完整表达每个月的具体开放/完成时间及特殊月份，需要独立月度时间计划。
5. 当前任务状态不足以表达“收尾处理中、月份免评、结果更正中”等业务状态，需要区分主状态与标签。
6. 当前“最终业务审批人”只有业务范围审批含义，需要新增独立的公司最终审定人配置和任务责任，不得复用只读全局查看权限。
7. 发起时必须固化员工、直属上级、部门负责人、分管范围、指标版本和时间计划快照，后续变化通过明确的交接或版本机制处理。

## 20. 核心验收场景

### 场景 1：季度按月评分正常完成

- 发起时生成 3 个月度记录；
- 员工每月自评；
- 直属上级每月逐指标评分，系统自动算月总分；
- 三个月完成后等权汇总；
- 只执行一次部门审核、HR 校准、分管审核和最终审定；
- 员工最终确认一次。

### 场景 2：季度不按月评分

- 不生成三个独立评分月；
- 周期结束时完成一次整体自评和逐指标主管评分；
- 形成一个总分后走完整审核链。

### 场景 3：第二个月调整指标

- V1 保留第一个月；
- HR 选择 V2 从第二个月生效；
- 第二、第三个月使用 V2；
- 第一个月正式评分不被覆盖。

### 场景 4：员工逾期未自评

- 自评入口保持开放并显示逾期；
- HR 可提醒；
- 直属上级仍可评分；
- 主管正式提交前员工可以补交，提交后当月锁定。

### 场景 5：周期中调岗并立即生效

- 原主管尚未正式评分时，新直属上级接手当月；
- 原主管已经正式评分时，当月保留，后续月份由新直属上级评分；
- 双方权限和历史记录正确切换。

### 场景 6：周期中转正

- 试用期月份不参评；
- 转正后产生范围变更待确认；
- HR 选择当前月或未来月加入，不追补试用期月份。

### 场景 7：离职或整月免评

- 无效月份不生成零分、不记逾期、不进平均；
- 有有效月份则按有效月份形成结果；
- 无有效月份显示“未形成绩效结果”。

### 场景 8：部门负责人审核自己

- 系统不生成其本人部门审核任务；
- 其结果由直属上级评分后直接进入 HR 校准。

### 场景 9：分管总与最终负责人

- 倪靖、郭志浩只看到各自分管范围的 HR 校准快照；
- 李宏看到公司范围的校准结果；
- 李宏分管范围不重复生成分管审核任务；
- 其他分管范围通过后，李宏完成最终审定和发布。

### 场景 10：往月结果更正

- 员工或直属上级发起申请；
- HR 管理员审批后开放目标月份新修订；
- 旧指标和评分作废归档；
- 系统重新计算该员工周期结果；
- HR 定向复核，员工重新确认；
- 其他员工及周期主状态不受影响。

### 场景 11：历史周期兼容

- 历史任务继续显示并使用原“最终业务审批人”；
- 新周期显示“分管总审核人”和“公司最终审定人”；
- 历史任务、权限和日志不被批量改写。

## 21. 与其他设计的衔接

1. 周期创建、检查、提交审核、HR 管理员审核和立即/预约发起，按《周期计划发起前工作流设计》执行。
2. 正式发起成功后，本文流程接管；发起检查失败仍属于发起前流程，不进入本文状态。
3. 组织调岗、生效时间、重新调岗和历史记录，按《组织调岗与绩效交接设计》执行；本文只定义其对绩效任务责任人的影响。
4. 现有动态业务权限中的历史“最终业务审批人”保留历史语义；新周期按本文拆分为分管总审核人和公司最终审定人。

## 22. 进入实施计划前的门槛

只有在本设计整体审阅通过后，才进入实施计划。实施计划至少需要覆盖：

- 数据迁移和历史兼容；
- 月度记录、指标版本和结果修订模型；
- 分管范围与最终审定人配置；
- 多角色权限和任务路由；
- 现有绩效待办页面的增量接入；
- 状态、日志、提醒和报表口径；
- 按月度/非月度、调岗、转正、离职、免评、退回和结果更正的端到端验收。

在此之前不修改业务代码，也不安排发布。
