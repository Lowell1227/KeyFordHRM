# 周期开放后目标跟进与评分闭环设计

## 1. 背景

当前系统已经能够创建、审核并开放 `workflowVersion = 2` 的绩效周期，也会在开放时为范围内员工生成周期任务、评分期次和指标版本外壳。但员工端仍存在三类断点：

1. 绩效待办按周期 ID 工作，却只显示周期名称；两个同名周期无法辨认，豁免任务还会被展示成所有阶段“已完成”。
2. 目标跟进只接受特定季度名称，月度周期和名称不符合正则的正式季度会被前端过滤为“暂无考核周期”。
3. 评分期次只打通了员工复盘提交。期间级主管草稿、退回、正式评分、锁定和周期汇总尚未闭环；整周期评分也被页面误称为“每月目标复盘”。

本设计把周期开放后的员工目标执行统一到“周期任务为父级、评分期次为子级”的模型中。周期创建与开放仍负责锁定参与快照；员工工作台、目标跟进、复盘评分和周期汇总全部读取该快照，不重新计算范围。

## 2. 目标

1. 周期正式开放后，范围内员工一定能在绩效待办和目标跟进中找到对应周期。
2. 同名周期可明确区分；正常参与、已豁免和仅团队可见不会混淆。
3. 员工从目标制定、主管审核、员工确认进入持续目标跟进，不因周期类型或名称格式丢失入口。
4. `scoringFrequency = monthly` 使用多个自然月期次；`scoringFrequency = cycle` 使用一个整周期期次，两者共用同一套复盘评分状态机。
5. 员工复盘、直属上级评分、期间锁定和周期汇总形成事务一致、可审计、可重试的闭环。
6. 周期汇总完成后继续进入现有部门复核、HR 校准和最终审定流程，不重做后续审批职责。
7. PC 端和 390px 手机端均可完成选择、跟进、复盘和评分。

## 3. 非目标

1. 不重新计算或修改已开放周期的参与人员、部门、主管和豁免快照。
2. 不把一个周期拆成多条 `AssessmentTask`。
3. 不迁移或覆盖旧流程 `workflowVersion = 1` 的历史评分字段。
4. 不改变部门复核、HR 校准、最终审定、公示和申诉的既有权限边界。
5. 不因为本次打通而自动发布生产；发布必须单独确认并执行回滚保护。

## 4. 核心模型

### 4.1 周期任务

`AssessmentTask` 继续表示“一名员工 × 一个绩效周期”的总任务，是员工是否属于某周期以及当时组织责任的唯一事实来源。

- 正常参与任务：`participantDisposition = active`，可进入目标制定和后续评分。
- 周期豁免任务：`participantDisposition = cycle_exempt`，状态为 `exempted`，保留周期可见性和豁免原因，不生成评分期次。
- 最高负责人豁免：`participantDisposition = top_leader_exempt`，与周期豁免同样不生成评分期次。

员工端不得通过当前组织树重新推导参与资格，也不得把“能够登录”当成“进入周期”。

### 4.2 评分期次

`AssessmentPeriod` 表示一个正式评分期：

- 月度模式：按周期计划生成 1、3、6 或 12 个 `periodType = month` 的期次。
- 整周期模式：生成一个 `periodType = cycle`、`periodKey = cycle` 的期次。

两种模式共用状态：

1. `unopened`：尚未开放；
2. `self_eval`：员工复盘与自评；
3. `manager_scoring`：直属上级评分；
4. `completed`：主管已正式提交并锁定；
5. `no_result`：本期无绩效结果，不计入周期均分。

“逾期”“员工未提交”“已退回”“结果更正中”是附加状态，不新增平行主状态。

### 4.3 目标版本与进展

目标确认后激活正式 `IndicatorVersion`，并绑定到尚未锁定的评分期次。持续进展继续写入 `IndicatorProgressUpdate`；员工正式提交期间复盘时，在同一事务中同步生成一条正式进展记录。草稿保存不写进展历史。

为使正式复盘进展可追溯且可幂等去重，`IndicatorProgressUpdate` 增加可空的 `periodId` 和 `periodReviewRevisionId` 外键：

- 日常手工进展继续使用两个外键均为空；
- 正式期间复盘使用当前 `AssessmentPeriod.id` 和本次员工正式修订 ID；
- 对“指标实例 × 员工正式修订”建立唯一约束，阻止同一幂等提交重复写进展；
- 主管退回后员工再次正式提交会生成新修订和新进展，保留完整重提历史；
- 迁移只增加可空列、外键和索引，不回填、不改写历史进展。

目标跟进与正式评分分离：进展描述目标执行事实，期间自评和主管评分形成正式绩效结果，二者不能互相覆盖。

## 5. 周期上下文接口

### 5.1 员工目标跟进周期

新增：

```http
GET /cycles/tracking-contexts?ownerId=<uuid>
```

返回 `PerformanceCycleContext[]`：

```ts
interface PerformanceCycleContext {
  id: string;
  name: string;
  type: CycleType;
  startDate: string;
  endDate: string;
  openedAt: string;
  scoringFrequency: 'monthly' | 'cycle';
  task: {
    id: string;
    status: TaskStatus;
    isExempt: boolean;
    exemptReason: string | null;
    participantDisposition: ParticipantDisposition;
  };
  periods: Array<{
    id: string;
    periodKey: string;
    periodType: 'month' | 'cycle';
    sequence: number;
    status: AssessmentPeriodStatus;
    selfEvalOpenAt: string;
    selfEvalDueAt: string;
    managerDueAt: string;
    employeeSubmittedAt: string | null;
    managerSubmittedAt: string | null;
    selfScoreTotal: number | null;
    managerScoreTotal: number | null;
  }>;
}
```

查询规则：

- 周期必须已经开放，并且存在 `employeeId = ownerId` 的任务；
- 包含正常参与和已豁免任务；
- 不返回草稿、预约中、发起阻断或尚未开放的周期；
- 不按周期名称、周期类型或兼容字段过滤；
- 默认允许查询本人；保留现有“本人查看直接上级目标”的权限，不新增任意员工查询能力；
- 服务端复用目标跟进现有 owner 授权判断，浏览器传入的 ownerId 不能扩大权限。

### 5.2 绩效待办周期

保留 `GET /cycles/mine` 的兼容用途，但返回周期时增加当前查看人的个人任务摘要，并继续保留团队任务周期可见性。个人任务摘要只查询 `employeeId = viewer.id`，不能用任意一条经理或审批任务冒充本人的参与状态。

### 5.3 排序与唯一标签

统一排序优先级：

1. 当前日期范围内且本人有待处理动作的正常参与周期；
2. 当前日期范围内的其他正常参与周期；
3. 当前日期范围内的已豁免周期；
4. 最近结束周期；
5. 尚未开始周期。

同组按 `startDate`、`endDate`、`openedAt` 倒序，最后按周期 ID 保证稳定顺序。

统一显示标签：

```text
周期名称｜MM/DD-MM/DD｜每月复盘 / 整周期评分｜正常参与 / 已豁免 / 团队周期｜开放 MM/DD HH:mm
```

窄屏选择器显示周期名称和状态，日期、模式、开放时间放在第二行，不能通过截断删除唯一识别信息。

## 6. 员工目标跟进流程

### 6.1 周期选择

绩效待办和目标跟进共用同一标签格式和稳定排序。目标跟进在人员切换时重新加载该人员可见周期，不能沿用上一个人的周期数组。

### 6.2 状态化空页面

目标跟进不再把所有无指标情况显示为“暂无考核周期”或“暂无考核指标”：

- 无周期任务：`当前没有已开放的考核周期`；
- 已豁免：`本周期已豁免，无需制定、跟进或评分`，同时显示原因；
- `indicator_drafting`：`目标待制定`，提供进入目标制定的主按钮；
- `indicator_reviewing`：`目标已提交，等待直属上级审核`；
- `indicator_confirming`：`目标待本人确认`，提供进入目标确认的主按钮；
- `goal_confirmed` 及之后：展示正式指标、最新进展和评分期次；
- 任务存在但正式指标为空：`正式目标版本尚未生成`，提供返回任务详情的入口。

### 6.3 持续进展

目标确认后允许员工更新：

- 完成度 0–100%；
- 进展状态：正常、风险、阻塞、完成；
- 进展说明；
- 实际值；
- 附件。

每次正式更新生成一条时间顺序稳定的进展历史。月度复盘正式提交生成的进展带上 `periodId` 和 `periodKey` 语义，目标跟进可以按评分期次筛选历史，但不重复创建同一提交的记录。

## 7. 员工复盘与自评

### 7.1 开放规则

- 到 `selfEvalOpenAt` 后，期次由调度器从 `unopened` 进入 `self_eval`；
- 员工提前正式提交后立即进入 `manager_scoring`；
- 员工到 `selfEvalDueAt` 仍未提交，调度器也把期次推进到 `manager_scoring`，同时保留员工补交能力，直到主管正式提交；
- 主管正式提交后员工不能再覆盖该期结果。

### 7.2 通用文案

页面按 `periodType` 生成文案：

- `month`：`YYYY年M月复盘与评分`；
- `cycle`：`整周期复盘与评分`。

服务端错误、通知标题和审计摘要同样按期次类型生成，不能继续硬编码“月度复盘”。

### 7.3 提交事务

员工正式提交必须在同一个事务中：

1. 校验期次、任务归属、指标版本和乐观锁版本；
2. 保存每项完成度、状态、实际值、说明、附件和自评分；
3. 计算员工自评加权总分；
4. 写入正式修订快照；
5. 为每项指标写入一条正式进展记录；
6. 更新员工提交时间和期次状态；
7. 写审计日志和系统内待办通知。

任一步失败则全部回滚。重复幂等键返回同一正式结果，不重复写进展或修订。

## 8. 直属上级评分

### 8.1 接口

新增：

```http
PUT  /assessment-periods/:id/manager-draft
POST /assessment-periods/:id/manager-return
POST /assessment-periods/:id/manager-submit
```

三个接口都要求 `expectedVersion`。草稿携带逐指标 `managerScore` 和选填 `managerComment`；退回携带选填原因和幂等键；正式提交携带逐指标评分、选填说明和幂等键。主管草稿和提交使用现有 `draftVersion` 乐观锁；退回与正式提交按幂等键返回原结果，并分别写审计修订或 `AssessmentPeriodReviewRevision(stage = manager)`。

### 8.2 权限与可编辑性

- 只有期次快照中的 `managerId` 可以评分和退回；
- HR、系统管理员和 `canViewAll` 只有读取能力，不能代替直属上级提交；
- 非直属上级通过直接 URL 访问也必须返回 403；
- 员工提交后主管可立即评分；员工未提交时到 `selfEvalDueAt` 后主管可评分；
- 主管正式提交后期次锁定，普通接口不能修改。

### 8.3 校验与提醒

- 每项主管评分必填，范围为 0–100；
- 主管说明始终选填；
- 与员工自评分相差 10 分及以上只提醒；
- 主管分低于 60 分只提醒；
- 提醒不阻止保存或正式提交；
- “同意自评”只作用于当前指标，不提供整页自动填满。

### 8.4 退回

主管退回后：

- 期次回到 `self_eval`；
- 清空当前 `employeeSubmittedAt`，但不删除员工最近一次正式内容和历史修订；
- 员工可以继续修改并重新提交；
- 退回前正式员工提交快照保留在修订记录中；
- 原因选填，但操作人、时间和版本必须审计；
- 已被更高版本更新或已锁定的期次拒绝旧退回请求。

### 8.5 正式提交

主管正式提交必须在同一事务中：

1. 校验全部主管评分和版本；
2. 按冻结指标权重计算期次主管总分；
3. 保存主管评分和选填说明；
4. 写正式主管修订快照；
5. 更新 `managerSubmittedAt`、`managerScoreTotal` 和 `status = completed`；
6. 刷新父任务周期汇总；
7. 写审计日志与系统内通知。

正式提交后员工可以查看该期正式反馈；最终周期等级和发布结果仍遵循现有公示字段与结果遮罩规则。

## 9. 周期汇总与后续流转

### 9.1 汇总规则

- 月度模式：所有 `completed` 且存在 `managerScoreTotal` 的有效期次等权平均；
- `no_result` 期次从分子和分母同时排除，不记 0 分；
- 尚有 `unopened`、`self_eval` 或 `manager_scoring` 期次时不形成最终周期分；父任务仍保持现有 `manager_scoring` 状态，前端根据未完成期次派生显示“收尾处理中”，不新增数据库状态枚举；
- 整周期模式只有一个有效期次，该期正式主管总分就是周期汇总分；
- 没有任何有效正式评分期次时不生成 0 分结果，由 HR 在后续人员变化能力中处理“无结果”原因。

### 9.2 父任务更新

所有必需期次进入 `completed` 或 `no_result` 且至少一个有效期次完成后：

1. 计算周期汇总分；
2. 使用现有评分等级规则更新 `GradeResult.calculatedScore` 和原始等级；
3. 复用现有主管评分后的后续节点解析：需要部门复核则进入 `dept_review`，否则进入 `hr_calibration`；
4. 写周期汇总审计记录；
5. 重复刷新必须幂等，不能重复推进任务或覆盖更高阶段状态。

## 10. PC 与手机交互

### 10.1 目标跟进

PC：左侧人员，顶部周期选择，主体指标表格，右侧或抽屉展示指标详情与进展历史。评分期次显示为紧凑标签栏。

手机：人员和周期选择纵向排列；指标使用单卡片；期次使用横向可滚动标签或原生选择器；所有操作区不得产生横向溢出。

### 10.2 员工复盘

PC 使用指标同屏表格或紧凑纵向卡片，参考信息与填写区并排；手机按指标逐项卡片，参考信息折叠在当前卡片下方。底部操作栏始终显示保存状态和正式提交。

### 10.3 主管评分

PC 同屏显示员工材料、自评分、主管评分和选填说明；手机逐项评分。支持“提交并处理下一人”，但不能绕过当前期次校验。

## 11. 错误处理与一致性

- 周期或任务已变化：返回 409，前端保留未提交内容并提示刷新；
- 草稿版本冲突：返回当前版本号和更新时间，不静默覆盖；
- 目标版本未确认：期次不可正式提交，显示明确下一步；
- 调度器重复执行：状态条件更新保证只开放一次；
- 通知关闭：不发钉钉消息，但系统内状态和待办仍更新；
- 进展写入或评分保存任一失败：事务回滚，不显示“保存成功”；
- API 读取失败：保留周期和人员选择，提供原位置重试，不回退成“暂无周期”。

## 12. 兼容策略

1. 已开放 `workflowVersion = 2` 周期直接使用现有任务、期次和指标版本，不重新发起。
2. 真实评分模式以 `scoringFrequency` 和实际 `AssessmentPeriod.periodType` 为准；`monthlyFollowUpRequired` 仅保留兼容，不决定新页面和任务。
3. 已经存在的同名周期不改名，通过日期、模式、状态和开放时间区分。
4. 旧 `workflowVersion = 1` 继续使用现有任务级自评和主管评分，不强行生成期次。
5. 新接口上线前必须确认现有进行中期次的状态可以被新主管评分接口安全接管。

## 13. 测试与验收

### 13.1 API 单元与服务测试

- 周期上下文只返回 owner 实际任务周期，包含豁免，不依赖名称；
- 任意人员 ownerId 越权返回 403；
- 同名周期稳定排序和上下文状态正确；
- 员工提交同时写复盘、进展、修订和审计，失败全部回滚；
- 员工未提交到期后主管仍可评分；
- 主管草稿、退回、正式提交、幂等和并发冲突；
- 月度有效期次等权平均、`no_result` 排除、缺失不记零；
- 整周期单期汇总；
- 父任务只推进一次并进入既有后续节点；
- `workflowVersion = 1` 兼容不回归。

### 13.2 Web 契约与响应式测试

- 两个同名周期分别显示正常参与与已豁免，切换后页面状态不同；
- 目标跟进接受月度、季度、半年度、年度和自定义正式周期；
- 已豁免、目标待制定、待主管审核、待本人确认和正式跟进空状态；
- 月度期次切换和整周期单期文案；
- 员工 PC/390px 复盘；
- 主管 PC/390px 评分、提醒、退回和提交；
- 加载失败不伪装为空状态；
- 页面无横向溢出，底部操作栏不遮挡最后一项。

### 13.3 真实角色流程

使用受控员工、直属上级和 HR 账号，通过业务页面完成：

```text
创建周期 → 审核 → 开放 → 员工制定目标 → 直属上级审核
→ 员工确认 → 持续进展 → 员工期间复盘 → 直属上级期间评分
→ 周期汇总 → 进入既有部门复核或 HR 校准
```

至少验收：

- 一个每月复盘并评分周期；
- 一个整周期评分周期；
- 两个同名但参与状态不同的周期；
- 一个已豁免员工；
- 1440px PC 和 390px 手机；
- 非直属上级直接 URL 越权；
- 员工未提交但主管到期评分；
- 重复提交和多设备版本冲突。

## 14. 交付与发布

开发在隔离工作区按测试驱动完成。每个行为先建立失败测试，再实施最小代码并回归相关套件。完成后把提交线性合入最新 `main`，确认没有遗漏的功能分支，也不夹带主工作区现有未提交内容。

生产发布必须：

1. 再次确认最新线上 Web/API 基线和当前 `main`；
