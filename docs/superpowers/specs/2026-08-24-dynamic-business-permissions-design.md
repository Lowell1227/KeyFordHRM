# 动态业务身份与系统角色兼容演进设计

## 文档状态

- 日期：2026-08-24
- 状态：业务方案已确认，进入实施
- 发布范围：绩效直属上级、部门负责人、最终业务审批人和周期 HR 负责人
- 兼容原则：保留现有账号角色、JWT、路由与历史任务；停止把错误角色当作业务操作授权

## 1. 决策摘要

系统权限拆成三层：

1. **系统角色**决定账号能够进入哪类系统功能，现有 `sysRole` 在过渡期保持不变。
2. **动态业务身份**由当前组织关系和任务关系实时计算，包括绩效直属上级、部门负责人、最终业务审批人、周期 HR 负责人。
3. **任务归属与状态**决定某一条业务记录能否被当前人操作；仅能查看全局数据不代表可以代替业务责任人审批。

本次以兼容方式增加动态能力，不重写历史任务，不修改花名册、组织或人员主数据，也不需要数据库迁移。历史绩效任务中保存的 `managerId`、`deptHeadId`、`approverId` 继续作为该任务的责任快照。

## 2. 名词与职责

| 概念 | 来源 | 业务作用 | 是否直接授予系统管理权限 |
| --- | --- | --- | --- |
| 系统角色 | `User.sysRole` | 基础菜单、后台管理和账号级权限 | 是 |
| 花名册直属主管 | 员工档案 | 展示组织任职事实 | 否，不作为绩效参数 |
| 绩效直属上级 | `User.directManagerId` 与历史任务 `managerId` | 主管评分、团队绩效处理 | 仅授予相关人员/任务能力 |
| 部门负责人 | `Department.leaderId` 与历史任务 `deptHeadId` | 部门复核 | 仅授予相关部门/任务能力 |
| 最终业务审批人 | 部门显式审批人、规则推导与历史任务 `approverId` | 最终结果审批 | 仅授予本人负责的审批任务能力 |
| 周期 HR 负责人 | `Cycle.hrOwnerId` | 周期 HR 运营、校准和异常处理 | 仅授予相关周期能力 |
| `canViewAll` | 账号权限 | 扩大只读数据范围 | 否，禁止作为写入或审批旁路 |

同一个账号可以同时拥有多个动态业务身份。身份并不互斥，也不要求把账号改成某个单一主管角色。

## 3. 授权模型

### 3.1 查看权限

页面入口和只读查询可由系统角色、动态业务能力或 `canViewAll` 决定。`canViewAll` 只能扩大查看范围。

### 3.2 操作权限

业务写操作必须同时满足：

```text
当前账号已登录
  AND 当前账号是该记录保存的业务责任人
  AND 当前任务处于允许操作的状态
```

系统管理员和拥有 `canViewAll` 的账号不会因为能看见记录而自动获得代办权。需要纠错时使用明确的管理操作和审计入口，不伪装成业务审批人。

### 3.3 动态能力计算

后端在登录和 `/auth/me` 响应中增加兼容字段 `businessCapabilities`：

- `canManageTeam`：存在当前直属下属，或存在本人负责的主管评分历史任务。
- `canReviewDepartment`：是当前部门负责人，或存在本人负责的部门复核历史任务。
- `canViewPerformanceApproval`：是当前/历史最终业务审批人，或仅具有全局只读范围。
- `canOperatePerformanceApproval`：存在当前审批范围或本人负责的历史审批任务。
- `canHandleHrCycle`：是当前周期 HR 负责人。
- `identities`：按身份类型返回可理解的名称和数量，用于当前账号界面展示。

前端收到该字段后，以动态能力为准；旧服务或旧登录态暂时没有该字段时，才回退到现有角色规则，保证发布切换不中断。

## 4. 本次实施范围

### 4.1 后端

- 新增集中式业务能力计算服务，并接入登录与 `/auth/me`。
- 周期可见范围同时识别任务中的员工、绩效直属上级、部门负责人和最终审批人，不再要求这些身份预先对应某个固定角色。
- 最终审批接口取消固定 `vp/chairman/system_admin` 入口限制，允许真实动态审批人进入。
- 最终审批写操作严格校验 `AssessmentTask.approverId`；`canViewAll` 和系统管理员不再绕过。
- 最终审批只读列表保留 `canViewAll` 的全局查看能力。
- 不更新任何历史任务的责任人字段。

### 4.2 前端

- 绩效审批入口按 `canViewPerformanceApproval` 控制。
- 团队绩效入口按 `canManageTeam` 控制。
- 当服务端已返回动态能力时，不再用旧主管/高管角色扩大业务入口；字段缺失时保留旧规则作为短期兼容。
- 在账号区域展示当前人的一个或多个业务身份，让验收人看得见系统为何开放相应功能。

### 4.3 暂不改变

- `sysRole` 数据模型、JWT 载荷和现有角色值。
- 试用期、转正、面谈等模块已有的记录责任人与显式角色规则；后续按同一模式逐模块迁移。
- 员工档案、花名册直属主管、部门树和钉钉身份关系。
- 历史绩效任务、历史审批结果和周期快照。

## 5. 兼容与回滚

- API 字段为增量字段，旧前端可忽略。
- 新前端在字段缺失时回退旧角色规则，支持 API/Web 分步替换。
- 本次无数据库迁移，回滚只需恢复上一版 API 与 Web 镜像。
- 运行中历史任务仍按保存的责任人执行，不因当前组织变化被重算。

## 6. 验收标准

1. 普通员工如果是某人的绩效直属上级，可以看到团队绩效入口。
2. 普通员工如果被指定为最终业务审批人，可以看到审批入口并处理本人任务。
3. 旧 `vp` 账号在服务端明确返回无审批能力时不再因角色看到审批入口。
4. 旧登录态尚无动态字段时仍保持原入口，发布过程不中断。
5. `canViewAll` 账号可以查看全局审批数据，但不能通过或驳回他人任务。
6. 同时具备全局查看和部分审批职责的账号，只能勾选和操作 `approverId` 为自己的行。
7. 当前账号界面能显示其全部动态业务身份。
8. 历史任务责任人、结果和数据库结构均不改变。
