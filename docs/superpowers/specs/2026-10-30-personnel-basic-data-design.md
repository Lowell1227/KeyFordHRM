# 人员基础资料与表单交互

用户已确认优先建设工作地点、职系，并要求优雅、优先做好交互。沿用已确认的 HR 共同维护范围和档案审核，不新增角色或员工可见范围。

## 本轮交付

- 人员导航只保留一个“基础资料”入口，页面内用紧凑标签切换合同主体、工作地点、职系、岗位。原合同主体和岗位 URL 兼容跳转；复用现有管理组件及岗位审核。
- 工作地点、职系提供名称搜索、启用/停用、改名和新增。用既有业务列表外壳，PC 表格、手机卡片，无重复页标题或装饰大卡片。
- 档案编辑、新建员工改用共享选择器；岗位编辑里的“岗位族”统一为“职系”。选择器保留原值，新增可选项通过小弹窗就近完成，成功后直接选用，不丢原表单。
- 选择器展开或从管理页返回时刷新选项；管理链接置于下拉底部，文案简短，打开新标签页。加载、空目录、名称重复、失败重试、取消、键盘和长名称都要可用。

## 数据边界

新增人员基础资料表，种类仅 work_location / job_family，名称最多100字、去首尾空格、同种类唯一。具有稳定目录 ID，但现有任职和岗位字段继续保存名称快照；目录改名和停用均不回写历史记录，不新增员工外键，不静默关联同名资料。旧名称保持原样可保存，新选项来自启用目录。该目录是标准选项来源，不引入新的任职生效或审批规则，现有字符串 API 的兼容边界保持。

目录初始为空，不自动从个人档案回填或合并历史名称；本轮不修改生产数据。合同主体沿用原有 ID/快照模型，岗位变更仍提交原审核流程。职级、标准字典、转签原/新公司关联等留待后续，不扩大本轮。

## 权限

沿用 employee_archive_edit 维护资料；hr/system_admin 原有能力保持。employee_archive_review 可查看选用；organization_edit 单独用户可读取职系并在原岗位权限下选用，不能据此写工作地点或目录。岗位写入继续 organization_edit，与目录写入分别判断；普通员工即使伪带 capability 也不能进入管理页/API。不授予或改写真实账号权限。

## 接口

- GET /personnel-reference-data/:kind?includeInactive=true|false，数组，默认启用。
- POST /personnel-reference-data/:kind，{name}。
- PATCH /personnel-reference-data/:kind/:id，{name?,isActive?}。
- 不提供物理删除；布尔值严格转换；目录更新和审计同事务。

## 验收

1440×900、1024×768、390×844、必要时320宽：目录切换、搜索/状态过滤、空/错状态、保留筛选、就近新增后选中、返回刷新、原值/停用选项保留、字段底部错误、重复/长名、手机滚动和抽屉底部操作。验证管理员、编辑HR、审核HR、组织编辑HR和员工的接口/入口/按钮差异。新建与档案草稿、岗位审核应保持现有行为。

保留四个既有无关脏文件；本轮已有按钮文案的两项未提交修改属于同一任务，可继续完善。生产部署另待用户明确发布指令。
