# 绩效模块周期优先选择设计

## 背景

绩效待办当前允许考核周期为空。周期为空时，个人待办和团队待办会向接口发送不带 `cycleId` 的请求，从而把多个历史周期的任务合并到同一个列表。页面虽然已经对周期按开始日期倒序，但初始化又主动清空个人周期，团队 URL 没有 `cycleId` 时也不会回填，因此排序本身无法避免跨周期混数。

同类问题不仅存在于绩效待办。目标地图、目标跟进、绩效报表、HR 校准、绩效审批、结果公示和管理工作台绩效汇总也都以考核周期作为数据的第一业务维度，但目前使用了不同的默认逻辑：有的取接口第一条，有的只寻找进行中周期，有的在找不到周期时退回跨周期查询。

## 目标

1. 所有以考核周期为第一维度的绩效模块，在存在可用周期时始终选中一个真实周期。
2. 默认周期统一按照“进行中优先，其次最近结束，最后最早将开始”的规则选择。
3. 有周期选择器的页面把有效 `cycleId` 写入 URL，刷新、返回和分享链接后仍保持同一周期。
4. 所有周期型数据请求必须携带 `cycleId`，不得因为周期为空而退化为跨周期查询。
5. 保留业务状态限定。例如 HR 校准只在可校准周期中选择，审批只在待审批周期中选择，公示只在可公示周期中选择。
6. 不改变后端接口、权限、业务流转或历史数据。

## 非目标

- 不把申诉处理、绩效面谈和改进计划改为强制单周期。这些页面是跨周期工单或历史记录列表，允许跨周期查看。
- 不修改考核周期管理、模板管理和指标库。它们不是按单个周期处理业务数据的工作台。
- 不增加新的全局状态库，不把周期偏好写入浏览器持久化存储。
- 不改变各模块现有的可见周期范围和角色权限。

## 统一周期选择规则

新增一个无副作用的共享周期选择模块，输入页面已经有权访问且符合当前业务状态的周期集合、可选的 URL 周期和当前日期，输出排序后的周期以及最终选中周期。

### 有效 URL 周期

如果 URL 中的 `cycleId` 存在于当前页面的可用周期集合中，始终保留该周期，不强制跳回默认周期。这样可以支持历史周期复核、刷新和分享深链。

如果 URL 中的 `cycleId` 不存在、已失效或不再符合该页面状态，则选择默认周期，并使用 `router.replace` 规范化 URL，避免浏览器历史中增加无意义的一步。

### 默认周期优先级

日期比较使用用户本地日期的 `YYYY-MM-DD`，开始和结束日期均按包含边界处理。

1. 进行中周期：`startDate <= today <= endDate`。如果有多个，选择开始日期最晚的一个；仍相同时选择结束日期最晚的一个。
2. 最近结束周期：在 `endDate < today` 的周期中，选择结束日期最晚的一个。
3. 最早将开始周期：在 `startDate > today` 的周期中，选择开始日期最早的一个。
4. 日期缺失或无效的周期不参与前三项；只有全部周期日期均不可用时，才按接口原顺序选择第一条作为确定性兜底。

调用页面负责先限定候选集合，因此共享算法不自行改变周期状态或角色权限。

## URL 与查询约束

有周期选择器的页面统一使用 `cycleId` 查询参数：

- 页面初始化：加载周期，校验或选择周期，先规范化 URL，再请求业务数据。
- 用户切换周期：更新 URL，并清理与旧周期绑定的任务、人员选择、分页和弹窗详情。
- 页面刷新或浏览器返回：优先恢复 URL 中仍有效的周期。
- 重置筛选：只清理部门、员工、状态、关键词和分页等次级条件，保留当前 `cycleId`。
- 无可用周期：周期选择器显示“暂无考核周期”并禁用，业务数据保持空状态，不发送无 `cycleId` 的请求。
- 周期接口失败：显示现有错误反馈或重试入口，业务数据保持空状态，不发送跨周期请求。

## 模块调整

### 1. 绩效待办

- 个人待办和团队待办共用同一有效周期。
- 删除周期下拉中的“全部考核周期”和“仅看待办任务”伪周期选项。
- 初始化不再清空 `selectedCycleId`；个人和团队列表、团队阶段汇总都必须携带所选 `cycleId`。
- 从个人切换团队、从团队切换个人、打开员工工作台以及返回列表时保留周期。
- 团队筛选的“重置”保留周期，只清理次级筛选。
- URL 中无周期或周期无效时，回填统一默认周期，并清理旧周期的 `employeeId`、`taskId` 和 `page`。

### 2. 目标地图

- 移除“全部周期”语义，目标树请求必须携带周期。
- 使用共享算法替换当前“只找未关闭进行中周期，否则为空”的逻辑。
- 将周期选择写入 URL；新建目标时默认继承当前地图周期。

### 3. 目标跟进

- 保留现有季度周期清洗、人员选择和深链能力。
- 在清洗后的可用周期中使用共享默认算法，替换独立的状态优先算法。
- 有效的 `employeeId`、`cycleId` 和目标深链仍优先于默认选择。

### 4. 绩效报表

- 不再依赖接口第一条作为默认周期。
- 周期写入 URL，汇总、进度、等级名单和导出全部读取同一周期。
- 部门筛选和报表页签切换不得清空周期。

### 5. HR 校准

- 候选集合仍限定为 `hr_calibration` 状态。
- 在候选集合内使用共享默认算法，并将周期写入 URL。
- 周期变化时清理勾选、批量等级、编辑草稿和分页，避免把旧周期修改带入新周期。

### 6. 绩效审批

- 候选集合仍限定为 `approval` 状态。
- 在候选集合内使用共享默认算法，并将周期写入 URL。
- 周期变化时清理选中任务和驳回对话框上下文。

### 7. 结果公示

- 候选集合仍使用当前可公示周期范围。
- 在候选集合内使用共享默认算法，并将周期写入 URL。
- 任务列表、批量选择和公示动作必须绑定同一个周期；切换周期时清理选择。

### 8. 管理工作台绩效汇总

- 保留“只展示可形成结果汇总的周期”这一业务限定。
- 使用共享算法确定最近有效结果周期，替换依赖接口顺序的选择。
- 当前页面没有周期选择器，因此本次不新增 UI 控件；只保证汇总、图表和列表始终绑定一个确定周期。

## 数据流

1. 页面请求其有权访问的周期集合，并在需要时按业务状态先过滤候选集合。
2. 共享选择模块校验 URL 周期或计算默认周期。
3. 页面规范化 URL，并清理与旧周期绑定的次级状态。
4. 页面仅在存在有效周期后请求业务数据，所有请求显式传入 `cycleId`。
5. 用户切换周期时重复第 3、4 步；较早请求返回时不得覆盖新周期数据。

## 错误与并发处理

- 周期加载失败与“确实没有可用周期”使用不同提示。
- 周期尚未解析完成时不发业务请求，避免先出现跨周期结果再跳变。
- 页面已有请求序列或生命周期守卫的继续复用；缺少守卫且存在并发覆盖风险的页面增加轻量请求序列。
- URL 周期失效时静默规范化到默认周期，不弹出错误；如果没有可用周期则显示空状态。
- 任何批量操作都继续使用服务端版本校验和现有权限检查，本次不改变写操作契约。

## 测试设计

### 共享规则单元测试

- 有效 URL 周期优先保留。
- 多个进行中周期选择开始日期最近者。
- 无进行中周期时选择最近结束者。
- 只有未来周期时选择最早开始者。
- 日期边界、无效日期、空集合和确定性兜底。
- 使用本地日期而不是 UTC 日期，避免时区跨日。

### 页面契约测试

- 绩效待办无 `cycleId` 时自动写入默认周期，个人、团队列表和团队阶段汇总请求均带该周期。
- 有效历史周期深链被保留；无效周期被替换，并清理旧任务和分页参数。
- 周期下拉只包含真实周期；重置筛选不清空周期。
- 目标地图、目标跟进、绩效报表、HR 校准、绩效审批和结果公示的首个业务请求均带默认周期。
- 切换周期后旧请求不能覆盖新周期结果，旧选择和编辑上下文被清理。
- 无周期或周期接口失败时不出现无 `cycleId` 的业务请求。
- 管理工作台汇总使用统一算法选择的最近有效结果周期。

### 真实角色验收

- 员工：进入绩效待办和目标跟进，看到一个真实默认周期，刷新后不变。
- 主管周强：进入团队绩效待办，默认周期写入 URL，列表和阶段数量只属于该周期；打开员工后返回仍保持周期。
- HR：检查目标地图、绩效报表、HR 校准和结果公示的默认周期及切换行为。
- 审批角色：检查绩效审批只显示所选待审批周期的数据。
- 桌面与 390px 窄屏均确认周期选择器不为空且没有新增横向溢出。

## 验收标准

1. 八个周期型入口在存在可用周期时都有确定的选中周期。
2. 默认选择严格符合“进行中、最近结束、最早将开始”的优先级。
3. 有效深链周期被保留，无效深链被规范化。
4. 有周期选择器的页面 URL 均包含 `cycleId`。
5. 周期下拉不再出现“全部周期”等会触发跨周期查询的选项。
6. 业务请求不会在周期为空时退化为跨周期查询。
7. 重置次级筛选、切换范围、打开详情和返回列表不会丢失周期。
8. 申诉、面谈和改进计划仍可跨周期查看，现有行为不变。
9. 聚焦契约测试、类型检查和生产构建通过，并完成员工、周强、HR 和审批角色的真实页面复核。
