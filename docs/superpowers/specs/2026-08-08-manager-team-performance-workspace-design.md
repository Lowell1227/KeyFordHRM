# 主管团队绩效工作台设计

## 文档状态

- 日期：2026-08-08
- 状态：已完成业务讨论，等待书面复核
- 采用方案：统一绩效待办工作台（方案 1）
- 目标路由：`/tasks`

本文扩展 `2026-08-08-performance-workspace-design.md` 中的绩效待办设计。凡涉及“`/tasks` 只调用 `tasksApi.findMine`”“不新增 API”“不修改 Prisma 模型”以及团队待办仅作有限展示的约束，均以本文为准；目标跟进和目标地图的既有设计不变。

## 背景与目标

现有 `/tasks` 只显示当前员工自己的绩效任务，主管需要进入独立的 `/manager/scoring` 页面才能查看部分团队工作，而且目标审核与上级评估仍是两种割裂的操作体验。参考实际绩效系统后，本轮需要把主管高频工作纳入统一绩效待办：

1. 主管能按周期、部门和员工查看自己负责的团队任务。
2. 主管能高效审核员工目标，支持逐人操作和批量通过、批量驳回。
3. 指标列表默认简洁，可按单条就地展开，不用在多个页面或大抽屉间往返。
4. 主管能在员工自评旁完成逐指标评分、评语和综合评价。
5. 指标可设置可见范围，并支持自定义选择部门和员工。
6. 目标提交、审核、评估、撤回均有可追溯的流程记录。

## 方案选择

### 方案 1：统一到 `/tasks`（采用）

`/tasks` 同时承载“我的待办”和“团队待办”。员工使用原有个人流程；主管在同一工作台进入目标审核和上级评估。既有 `/manager/scoring` 重定向到 `/tasks?scope=team&stage=manager-eval`。

优点：入口统一、员工与主管交互模型一致、能复用当前任务详情和状态机，也便于后续增加阶段。主要代价是需要补齐团队查询、批量审核、草稿和撤回接口。

### 方案 2：保留独立主管评分页

继续扩展 `/manager/scoring`。改动较小，但目标审核与个人待办仍然割裂，并持续维护两套工作区，不采用。

### 方案 3：新增独立团队目标模块

重新建立团队目标与评估模块。边界清晰但会重复现有绩效任务、指标和流程能力，迁移成本与验收风险过高，不采用。

## 信息架构与路由

统一工作台使用以下查询参数表达页面状态：

- `/tasks?scope=mine`：我的绩效待办。
- `/tasks?scope=team&stage=goal-review`：团队目标审核。
- `/tasks?scope=team&stage=manager-eval`：团队上级评估。
- `/tasks?scope=team&stage=goal-review&cycleId=...&deptId=...&employeeId=...`：可恢复的筛选与选中员工状态。

默认规则：

- 普通员工固定进入 `scope=mine`，不显示团队入口。
- 有直属员工的主管可切换“我的待办 / 团队待办”。
- 从 `/manager/scoring` 进入时重定向到团队上级评估，并保留可映射的周期、员工参数。
- 筛选、阶段和选中员工写入 URL；刷新和浏览器前进、后退后仍可恢复。

工作区采用三段结构：

1. 二级导航：目标跟进、目标地图、绩效待办。
2. 上下文栏：我的绩效待办、我团队的绩效待办及阶段状态。
3. 主工作区：团队列表或员工详情。

团队员工详情在桌面端进一步分为：

- 左侧员工栏：部门/员工选择、头像、姓名和阶段状态。
- 中间指标区：简洁可展开指标、评分和综合评价。
- 右侧参考区：参考目标与目标变更记录，可收起。

## 用户与权限

### 员工

- 只能访问自己的绩效任务。
- 可见自己的全部任务指标，不受指标参考可见范围限制。
- 按现有状态机完成目标制定、目标确认、自评和结果确认。

### 直属主管

- 团队工作台只返回 `assessmentTask.managerId = 当前用户 id` 的任务。
- 可查看和处理自己负责的员工目标审核与上级评估。
- 可使用部门和员工筛选，但候选范围也必须限制在其负责的任务集合内。
- 始终可见其负责任务的全部指标。

### 部门负责人、HR 与管理员

- 继续使用现有数据权限和后续节点页面。
- 本轮不把 HR 校准、部门复核或发布流程搬入主管团队工作台。
- 主管专用写操作不能仅凭宽泛数据权限执行，必须校验任务的 `managerId`。

## 团队待办列表

团队列表按周期和阶段展示成员任务，提供：

- 阶段切换：目标审核、上级评估。
- 筛选：周期、部门、员工、状态。
- 搜索：姓名、工号。
- 数量：全部、待完成、未开始、已完成。
- 行信息：员工、部门、岗位、任务状态、更新时间、当前操作。
- 目标审核批量命令：批量通过、批量驳回。

列表不展示当前用户模型中不存在的“职级”字段。后续若业务补充职级数据，再单独加入。

点击员工进入同一路由下的员工详情，不离开绩效工作台。切换员工时保留周期、部门、阶段和状态筛选。

### 阶段状态口径

“未开始、待完成、已完成”描述的是所选阶段的进度，不等同于整张绩效任务的最终状态：

- 目标审核：`indicator_reviewing` 为待完成；目标审核之前的状态为未开始；`indicator_confirming` 及其后续状态为已完成。
- 上级评估：`manager_scoring` 为待完成；上级评估之前的状态为未开始；`dept_review`、`hr_calibration` 及其后续状态为已完成。
- `exempted` 单独显示“已豁免”，默认计入全部，不计入待完成。

状态先由后端按统一顺序映射为阶段进度，前端只负责展示和筛选，不重复推导。

## 指标列表交互

### 默认简洁模式

每条指标在收起状态只展示：

- 序号与指标名称。
- 权重。
- 可见范围。
- 当前流程或评价状态。
- 展开/收起图标。

列表底部固定显示权重合计。合计不是 100% 时使用明确错误状态，并禁止目标提交或审核通过。

### 单条展开

点击指标行或展开图标后，在原位置展开：

- 指标描述。
- 目标值、单位和完成口径。
- 评分标准与数据来源。
- 对齐的参考目标。
- 当前阶段对应的自评、主管评价或驳回信息。

各指标独立控制展开状态，同时提供“全部展开 / 全部收起”。默认全部收起；出现以下情况时自动展开第一条相关指标并滚动定位：

- 校验错误。
- 主管驳回原因。
- 未保存修改。
- 提交失败对应的指标。

展开只改变该行内容高度，不切换整套页面，也不打开覆盖主内容的大抽屉。

## 目标审核

主管可在员工详情逐人通过或驳回，也可在团队列表批量处理。

### 逐人审核

- 通过前校验任务归属、任务状态、至少一条指标以及权重合计 100%。
- 通过后从 `indicator_reviewing` 进入 `indicator_confirming`。
- 驳回必须填写原因，任务返回 `indicator_drafting`。
- 驳回原因显示在员工目标编辑时最相关的位置，并写入流程记录。

### 批量通过

- 请求携带任务 id 列表。
- 服务端逐条校验当前用户是否为任务主管、任务是否处于 `indicator_reviewing`、指标是否有效。
- 每个任务使用独立事务；合法任务正常通过，非法任务单独失败。
- 响应返回成功项和失败项及原因，前端保留失败项选择状态并刷新成功项。

### 批量驳回

- 请求携带任务 id 列表和一条必填公共驳回原因。
- 每个任务独立退回并生成自己的流程记录。
- 部分失败不回滚已成功任务。

## 指标可见范围

每条指标支持：

- 全公司可见。
- 部门内可见（不含下级部门）。
- 部门内可见（含下级部门）。
- 直接下级可见。
- 所有下级可见。
- 仅上级可见。
- 自定义范围。

自定义范围通过弹层同时选择多个部门和多个员工，并显示已选数量。保存时至少选择一个部门或员工。

可见范围用于目标地图、参考目标和其他发现型查询，不改变任务本身的授权：任务员工本人、指定主管以及当前流程的合法处理人始终能读取完成当前节点所需的指标。

历史指标迁移时默认设为“仅上级可见”，避免升级后扩大可见范围。

## 目标对齐与参考信息

指标可通过“添加对齐”关联已有目标：

- 一条指标可关联多个目标。
- 关联关系保存目标 id，不把目标正文复制成可变字段。
- 绩效任务中的指标内容仍是周期快照，参考目标后续变化不会覆盖已提交指标。
- 右侧“参考目标”按权限只显示当前用户有权查看的关联目标。
- 右侧“目标变更记录”展示指标保存、提交、审核、驳回和重新提交等事件。

## 上级评估

上级评估一次只处理一名员工，不提供批量评分提交。

### 指标评价

收起状态展示：指标名称、权重、员工自评摘要、主管评价状态。

展开状态左右对照展示：

- 指标描述、目标值和实际完成值。
- 员工自评分与自评评语。
- 主管评分与主管评语。

主管评分沿用现有评分边界和计算规则，不在前端重新计算最终结果。校验失败时展开并定位相应指标。

### 综合评价

指标列表下方展示：

- 员工总评，只读。
- 主管综合评价。
- 优势、待改进项、发展计划及现有附件能力。

主管可“保存草稿”或“提交评估”。草稿不改变任务状态；提交后按现有规则进入部门复核或 HR 校准。

### 撤回评估

正式提交后，仅在下一节点尚未处理时允许主管撤回：

- 当前用户仍为任务主管。
- 当前状态必须是本次上级评估直接进入的 `dept_review` 或 `hr_calibration`。
- `manager_scored_at` 之后不存在部门复核、HR 校准或更后节点的有效操作记录。

撤回使用单事务完成：

- 状态恢复为 `manager_scoring`。
- 清除本次正式提交时间。
- 保留各指标评分、评语和综合评价作为草稿。
- 写入明确的撤回流程记录。

下一节点已经处理时隐藏或禁用撤回命令，并返回明确原因。撤回不能依赖前端判断，服务端必须再次校验。

## 数据模型调整

### 指标可见范围

新增 `IndicatorVisibilityScope` 枚举，值对应本文定义的七种范围。`IndicatorInstance` 新增 `visibilityScope` 字段，默认值和历史迁移值为“仅上级可见”。

自定义范围使用关系表：

- `IndicatorVisibilityDepartment`：`indicatorInstanceId`、`departmentId`，联合唯一。
- `IndicatorVisibilityUser`：`indicatorInstanceId`、`userId`，联合唯一。

服务层集中解析可见范围，业务查询不能在不同控制器中重复拼接权限条件。

### 目标对齐

新增 `IndicatorObjectiveAlignment`：

- `indicatorInstanceId`。
- `objectiveId`。
- 联合唯一索引。

删除目标时按照现有目标删除政策处理关联；不得级联删除绩效指标实例。

### 流程动作

`FlowAction` 增加 `withdraw`，明确记录上级评估撤回。批量审核仍为每个任务写入现有 `submit` 或 `reject` 动作，并在 `extraData` 中标记批次 id，便于审计关联。

现有 `IndicatorInstance` 的 `managerScore`、`managerComment` 和 `ManagerEvalSummary` 足以承载评价草稿，不另建平行评分模型。

## API 设计

### 团队列表

`GET /tasks/team`

查询参数：

- `cycleId`
- `stage=goal-review|manager-eval`
- `status`
- `deptId`
- `employeeId`
- `keyword`
- `page`
- `pageSize`

接口只返回当前用户作为 `managerId` 的任务，同时返回分页数据和阶段计数。员工候选项和部门候选项必须由同一授权任务集合派生。

### 目标审核

- `POST /tasks/team/indicator-review/batch-approve`
- `POST /tasks/team/indicator-review/batch-reject`

批量通过请求包含 `taskIds`；批量驳回额外包含必填 `reason`。响应统一为：

```ts
{
  succeeded: Array<{ taskId: string; status: string }>;
  failed: Array<{ taskId: string; reason: string }>;
}
```

逐人审核继续沿用现有任务指标提交与驳回能力，但前后端命名和按钮文案统一为主管“通过 / 驳回”。

### 可见范围与目标对齐

扩展指标保存 DTO，使每条指标可提交：

- `visibilityScope`
- `visibleDepartmentIds`
- `visibleUserIds`
- `alignedObjectiveIds`

服务端校验所有部门、用户和目标 id 均在当前操作者可选范围内，不能只校验 id 是否存在。

### 上级评估

- `PUT /tasks/:id/manager-evaluation-draft`：保存指标评分、评语和综合评价，不迁移状态，不写正式提交时间。
- `POST /tasks/:id/manager-score`：保留为正式提交入口，并复用草稿 DTO 的业务字段。
- `POST /tasks/:id/manager-score/withdraw`：满足撤回条件时恢复 `manager_scoring`。

正式提交和撤回均在服务端事务内写任务状态、时间字段、评价摘要和流程记录。

## 前端组件边界

建议新增或提取以下组件，避免把所有状态堆入 `TaskListView.vue`：

- `TeamTaskList.vue`：团队成员列表、筛选、计数和批量选择。
- `TeamMemberRail.vue`：员工切换和状态显示。
- `PerformanceIndicatorList.vue`：简洁指标行、单条展开和权重合计。
- `IndicatorVisibilityEditor.vue`：范围选择及部门/员工自定义弹层。
- `GoalReviewWorkspace.vue`：逐人目标审核与流程操作。
- `ManagerEvaluationWorkspace.vue`：自评/上评对照、草稿、提交和撤回。
- `PerformanceReferencePanel.vue`：参考目标和目标变更记录。

现有 `PerformanceWorkspace.vue` 继续只负责页面结构和导航，不请求团队业务数据。`TaskDetailView.vue` 中可复用的指标展示与状态映射应提取后共享，不复制第二套实现。

## 加载、错误与并发

- 列表、员工栏和详情分别维护加载状态，切换员工时保持工作区稳定尺寸。
- 草稿存在未保存修改时，切换员工或路由前提示确认。
- 保存草稿失败时保留本地输入，并展开首个服务端校验失败指标。
- 批量操作展示逐条结果；失败项可重试，成功项不可重复提交。
- 写接口使用当前任务更新时间或版本进行并发校验，检测到任务已被其他节点处理时返回冲突并刷新详情。
- 所有 403、404 和状态冲突使用统一错误提示，不泄露无权查看的员工或目标信息。

## 响应式与视觉规则

- 桌面端保持员工栏、指标主区、参考区三栏结构。
- 窄屏下员工栏和参考区改为抽屉，指标主区占满宽度。
- 指标行使用稳定网格列宽；展开内容只增加纵向高度，不能挤压评分控件。
- 长指标名、描述和评语允许换行，命令按钮保持固定最小尺寸。
- 图标命令使用项目现有 Element Plus 图标并提供工具提示。
- 卡片圆角不超过 `8px`，不使用嵌套卡片、大面积渐变或营销式标题。
- 颜色同时表达文本状态，不以颜色作为唯一信息。

## 测试策略

### 后端单元与接口测试

- 团队列表只返回当前用户作为直属主管的任务。
- 部门、员工筛选不能扩大数据范围。
- 可见范围覆盖七种枚举和自定义部门/员工组合。
- 历史指标迁移默认“仅上级可见”。
- 批量通过和驳回验证部分成功、部分失败及独立流程记录。
- 评估草稿不迁移状态，正式提交按现有分支进入部门复核或 HR 校准。
- 下一节点未处理可撤回；已处理、非直属主管和错误状态均不可撤回。
- 并发版本冲突不会覆盖后来提交的数据。

### 前端组件与页面测试

- 员工不出现团队入口，主管可切换我的待办和团队待办。
- URL 可恢复周期、阶段、部门、员工和状态筛选。
- 指标默认收起、单条展开、全部展开和异常自动定位正确。
- 自定义可见范围可同时选择部门和员工。
- 批量结果保留失败选择并移除成功项。
- 上级评估草稿刷新后恢复，正式提交后只读，撤回后恢复可编辑。

### 浏览器业务验收

至少使用员工和直属主管两个真实权限角色完成：

1. 员工提交目标。
2. 主管按部门和员工筛选，在简洁列表展开指标并驳回。
3. 员工根据驳回原因修改并重新提交。
4. 主管批量通过多个合法任务，并观察一个非法任务独立失败。
5. 员工完成自评。
6. 主管保存逐指标评价草稿，刷新确认数据仍在，再正式提交。
7. 下一节点未处理时撤回；下一节点处理后确认不能撤回。
8. 验证目标变更记录、流程记录和指标可见范围。

视觉验收使用至少 `1440x900` 桌面视口和 `390x844` 窄屏视口，检查文字遮挡、控件溢出、长评语换行、抽屉操作和布局跳动，并在刷新后再次验证状态。

## 完成标准

- 主管可在 `/tasks` 完成团队目标审核与上级评估，不依赖旧评分抽屉。
- 部门和员工筛选、指标展开、批量审核、可见范围、草稿、提交及撤回形成真实业务闭环。
- 每项写操作均经过服务端权限和状态校验，并留下独立审计记录。
- 自动化测试、桌面与窄屏浏览器验收全部通过。
- `/manager/scoring` 平滑重定向，旧书签不失效。

## 非目标

- 不在本轮改造部门复核、HR 校准、结果发布和申诉页面。
- 不引入新的微服务或消息中间件；继续在现有模块化单体内实现。
- 不实现钉钉免登、组织同步或消息推送。
- 不新增当前业务模型没有来源的职级数据。
- 不复制参考系统品牌、外层客户端导航或第三方插画。
