# 绩效查询筛选与考核范围预览设计

## 背景

部门复核、绩效面谈和改进计划缺少完整的周期、部门、员工查询条件；绩效校准、结果审批、结果公示和申诉处理虽已有部分条件，但排列、默认周期和姓名/工号口径不一致。创建周期时，考核范围入口重复，且部门勾选只显示人数，无法确认实际纳入哪些员工。

## 已确认范围

- 统一页面：部门复核、绩效校准、结果审批、结果公示、申诉处理、绩效面谈、改进计划。
- 统一基础条件顺序：绩效周期计划、部门、员工姓名/工号；页面专属状态或排序条件放在其后。
- 默认选择当前用户可见范围内 `createdAt` 最新的周期，可切换其他周期。
- 团队任务已有等价条件，不重复增加；绩效报表保留分析型筛选。
- 创建周期考核范围改为单行摘要和唯一入口，并能预览最终纳入人员。
- PC 与 390px 手机端均需验证。

## 查询交互

前端新增共享的绩效记录筛选组件。组件只负责稳定的控件顺序、标签、响应式布局和查询/重置动作；各页面继续拥有自己的状态筛选、数据加载和权限语义。

周期选项沿用每个页面现有的可见范围接口；统一按 `createdAt` 降序排列，缺少创建时间时保持服务端顺序。首次加载选择最新周期，重置也回到最新周期。部门列表只读取有效 HRM 部门。员工关键字在服务端同时匹配姓名和工号，所有条件叠加原数据权限，不扩大任何人的可见范围。

绩效校准的周期分布和进度仍按整个周期计算，部门及员工条件只过滤校准名单；审批概览同样保持周期全局口径。其他分页列表由服务端返回过滤后的总数和结果。

## 考核范围选择

表单内只保留一行：范围摘要在左，唯一的“查看与调整”按钮在右。摘要展示选择的部门数量和最终人数，不再同时出现“选择考核对象”和“查看与选择”。

抽屉中保留部门树和按人员补充能力，并新增“已纳入人员”区域。后端提供只读预览接口，输入与周期草稿相同的部门、显式人员和排除项，使用与周期启动一致的有效员工条件，返回最终人员分页列表及人数。列表展示姓名、工号、部门和岗位；选择变化后刷新。预览不会创建或修改周期、任务、员工或组织数据。

PC 使用部门选择与人员预览双栏布局。手机端使用上下区域，人员预览保持卡片化，不压缩桌面表格。

## API 与权限

- 部门复核、面谈、改进计划、校准、审批、公示和申诉查询补齐 `cycleId`、`deptId`、`keyword` 中各自缺失的字段。
- 人员预览接口沿用 `cycle_plan_edit` 权限边界和候选人员最小字段投影。
- 不新增数据库字段或迁移，不修改评分、流程、通知或角色配置。

## 验证与发布

- API 测试覆盖条件组合、姓名/工号匹配、分页总数、原权限约束和人员预览排除规则。
- Web E2E 覆盖七页控件顺序、最新周期默认、请求参数、查询重置、底部分页及 PC/390px 布局。
- 周期创建 E2E 覆盖单行入口、部门选择后实际人员预览、显式人员和排除项。
- 运行 API 相关测试与构建、Web 类型检查/生产构建及针对性 Playwright。
- 用户已授权在领先 `main` 直接开发并上线。发布包含 API 与 Web，不涉及数据库迁移；发布前保留两个服务的回滚镜像，发布后核验外部健康、镜像提交及真实页面。
