# 真实业务校准的合成绩效演示数据设计

## 文档状态

- 日期：2026-08-11
- 状态：设计已由用户逐段确认
- 目标环境：当前尚未上线的生产模式数据库
- 数据观察日：2026-08-11
- 方案：原始业务资料校准、身份完全虚构、固定随机种子的确定性合成数据

## 背景

当前 `api/prisma/seed-demo-history.ts` 仅包含 8 个账号、4 名普通员工和 3 个周期，所有普通员工基本归属于同一主管，部门、岗位、绩效表现和流程状态过于集中。这类数据可以验证页面是否有内容，但无法支撑真实组织下的权限、管理跨度、绩效分布、跨周期趋势和异常业务流程验收。

本设计以现有 Prisma 模型、绩效制度、花名册统计分布、考核表和业务负责人指标表为约束，生成可重复构建的合成数据。原始人员记录只用于统计校准，不逐行导入；姓名、工号、联系方式和其他身份信息全部重新生成。

## 目标

1. 生成 128 名当前人员及 4 名历史离职人员，覆盖真实的组织层级、岗位结构、管理跨度和用工类型。
2. 生成从旧制历史档案到 2026 Q1、Q2、Q3 和年度管理层目标的连续时间线。
3. 让目标值、实际值、评分、等级、评语、申诉、面谈和改进计划彼此一致。
4. 让 HR、分管领导、部门负责人、直属主管、普通员工、低绩效员工和试用期员工均有可完整验收的代表账号。
5. 支持生产模式下显式执行、重复执行和精确清理，同时不影响非合成数据。
6. 通过生成器、数据库和跨角色浏览器验收三个层次证明数据有效。

## 非目标

- 不复制原始花名册中的真实姓名、手机号、身份证号、邮箱、地址、银行卡或紧急联系人信息。
- 不把系统扩展为完整人事档案、考勤、薪资、社保或合同管理系统。
- 不为演示数据新增公司枚举、角色、状态或绩效流程节点。
- 不修改基础 `prisma db seed` 的职责，也不让普通数据库初始化自动写入演示人员。
- 不制造外键缺失、权重错误、时间倒序或无法解释的评分等技术脏数据；异常仅表现为合法业务状态。

## 总体架构

新增独立入口 `api/prisma/seed-realistic-demo.ts`，由 `api/package.json` 中的 `db:seed:realistic` 命令显式调用。脚本分为配置、生成、校验、持久化和汇总五个边界清晰的单元：

1. `realistic-demo/config`：固定观察日、随机种子、确定性 ID 命名空间、人员配额、部门权重、周期及验收账号定义。
2. `realistic-demo/generator`：纯函数生成组织、人员、指标、周期、任务和业务事件，不访问数据库。
3. `realistic-demo/validator`：在落库前验证计数、关系、日期、权重、评分和状态机约束。
4. `realistic-demo/persist`：在一个 Prisma 事务中精确替换合成数据并批量写入。
5. `realistic-demo/report`：落库后查询数据库并输出验收摘要，证明实际数据与生成清单一致。

业务数据先在内存中使用确定性 UUID 建立完整引用，再执行事务。这样可使用 `createMany` 批量写入，并避免依赖数据库返回的随机 ID 串联后续对象。

## 指标模板

生成器按岗位族选择模板，而不是为所有人复制同一套指标。

### 项目与产品

- 项目交付及时率、里程碑达成率、项目毛利、库存清理、客户验收和跨团队协作。
- 目标和实际值使用百分比、金额、项目数或文字里程碑。

### 供应链与仓储

- 采购降本、供应商准交率、质量问题率、库存准确率、重大项目保障和供应商治理。
- 发生严重延期、质量事故或品牌影响时关联扣分或降档。

### 销售、门店与 B2B

- 销售额、回款率、坏账控制、新渠道占比、客户开发、库存清理和门店运营。
- 阶梯目标可使用合格、良好、优秀三档，分别对应基准、超目标 20% 和超目标 50% 等业务口径。

### 电商、直播与新媒体

- GMV、投产比、转化率、直播场次、内容产出、粉丝增长和活动交付。

### 创意、视觉与产品设计

- 作品准确率、设计交付、审核留痕、视觉升级、外部认可、AI 工具应用和知识沉淀。

### 客服及业务支持

- 响应时效、一次解决率、客户满意度、投诉升级、数据差错和业务协同。

### 财务、人事与行政

- 结算及时率、报表准确率、预算控制、招聘交付、关键岗位到岗、绩效覆盖、制度交付和员工服务。

### 普通员工和管理者结构

- 普通员工默认使用工作目标 80% 和工作态度 20%，每人 3–6 项指标。
- 管理者增加人才培养、流程优化、跨部门协作和风险责任指标。
- 奖励、扣分和一票否决作为独立指标类型，不混入普通 KPI 权重。
- 每项指标包含名称、描述、目标值或目标文本、单位、数据来源、统计口径和评分标准。

## 评分生成与等级校准

每名员工持有一个固定的潜在绩效水平，并在各周期叠加小幅、可复现的岗位事件和随机扰动。同一员工跨周期表现应有延续性，但不得完全不变。

评分按以下顺序生成：

1. 基于岗位模板和潜在绩效水平生成实际值。
2. 按评分标准计算指标基础分。
3. 叠加合法奖励、扣分或一票否决事件。
4. 生成与结果一致的员工自评；约 90% 的任务中自评分比主管评分高 2–6 分，其余任务允许一致或低于主管评分。
5. 计算加权总分和初始等级。
6. 按一级部门规模执行 HR 校准，在全公司范围达到已规定的固定等级计数。
7. 生成校准说明、审批结果、系数和归档摘要。

小部门不单独强制凑齐 20%、40%、30%、10%；比例在公司总量上控制，部门级只限制明显失真。A 级人数不得超过配置上限。D 级任务必须创建绩效改进计划。

评语由低分、高分和业务事件组合生成，必须提及具体指标或结果，禁止只重复“表现优秀”“继续努力”等无信息模板。

## 关键故事线

关键故事由固定人员 ID 绑定，重复执行后角色和历史不变化：

1. 优秀项目经理连续两个周期为 A，Q3 目标提高并承担部门目标拆解。
2. 稳定骨干长期为 B，Q2 某项交付不足，Q3 已形成改善行动。
3. 低绩效员工由 Q1 的 C 降为 Q2 的 D，改进措施直接来自低分指标。
4. 两名员工连续两个周期为 D，进入末尾淘汰评估，但脚本不伪造已经解除劳动关系。
5. 一名员工因数据口径错误申诉后从 C 调整为 B，保留部门处理和 HR 复核记录。
6. 一名员工申诉后维持原等级，处理意见解释证据和评分标准。
7. 一名晚入职员工因在岗不足三分之一豁免。
8. 一名员工在 Q2 中途转岗，Q2 保留原岗位评价，Q3 使用新岗位目标。
9. 四名历史离职员工仍可查询历史绩效档案，但不出现在当前人员列表。

## 数据安全与幂等

### 执行门禁

生产模式允许执行，但必须同时满足：

- `ENABLE_REALISTIC_DEMO_SEED=true`
- `REALISTIC_DEMO_ACCOUNT_PASSWORD` 为非空且满足现有密码要求
- 数据库连接成功且 Prisma schema 与脚本所需字段一致

任一条件不满足时只输出明确错误并退出，不执行删除或写入。

### 确定性身份

- 所有合成对象使用固定命名空间生成 UUID。
- 人员工号、周期名称、模板代码和指标代码由固定规则生成。
- 能写入 JSON 的业务表使用 `source=realistic-demo-v1` 标记；无法写入标记的表由确定性 ID 清单识别。
- 用户可见的姓名和工号保持自然，但不与原始花名册逐行对应。

### 重建策略

脚本在事务开始后先解析完整的确定性 ID 清单，并查询实际命中记录。若命中记录不属于已知合成周期、合成人员或合成模板，立即中止。确认范围后，按外键逆序删除旧的合成子记录，再按依赖顺序重建。

清理和重建在同一个事务中完成。任何创建或校验失败都会回滚，数据库保留上一次完整的合成数据。脚本不得执行无条件 `deleteMany({})`、清空 schema 或数据库重置。

提供 `db:seed:realistic:clean` 清理命令，但它使用同一确定性 ID 清单且要求 `ENABLE_REALISTIC_DEMO_CLEAN=true`；本设计只要求实现清理能力，不在首次落库验收时执行。

## 数据流与写入顺序

事务内按以下依赖顺序写入：

1. 部门补充和部门关系。
2. 当前人员、历史离职人员和管理关系。
3. 部门负责人和审批人回填。
4. 指标库、模板、维度和模板指标。
5. 目标及行动项。
6. 周期、模板快照和任务。
7. 指标实例、自评和主管评价。
8. 等级结果、流程记录和绩效档案。
9. 面谈、申诉、改进计划、试用期考核、转正申请和签名。
10. 通知与审计相关记录。

密码哈希在事务外预先计算；业务记录只在门禁和预校验通过后进入事务。

## 错误处理

生成器和校验器使用带业务路径的错误信息，例如 `Q2/员工工号/指标代码/weight`，方便定位单条错误。以下情况在写入前失败：

- 当前人员不是 128 人或用工类型配额不匹配。
- 汇报关系成环、主管不存在或部门负责人无法解析。
- 普通维度或指标权重合计不为 1。
- 实际值、分数、总分和等级不符合评分规则。
- 已完成流程的时间戳缺失、倒序或晚于观察日。
- 豁免员工仍存在等级、面谈或改进计划。
- D 级结果没有改进计划。
- 申诉修改后任务、等级和归档不一致。
- 已离职员工出现在观察日之后的新周期任务中。
- 非验收账号写入了统一密码。

落库后的统计与生成清单不一致时，事务视为失败并回滚。

## 验证策略

### 生成器单元测试

- 固定种子生成快照稳定。
- 人数、部门、岗位族、用工类型和角色计数正确。
- 主管关系无环且团队规模落在设计区间。
- 周期任务数、豁免数和等级计数符合本设计。
- 指标权重、评分计算、时间顺序和故事线约束正确。
- 不出现原始花名册姓名、真实手机号格式或非测试邮箱域名。

### 数据库集成验证

在干净 PostgreSQL 上执行迁移和基础 seed 后：

1. 首次运行真实演示 seed 成功。
2. 查询各核心表计数和固定故事线。
3. 连续运行第二次，记录总数和确定性 ID 不变化。
4. 插入一条非合成控制记录后再次运行，控制记录仍存在且内容不变。
5. 使用清理能力的 dry-run 输出精确目标，不实际删除。

### API 和浏览器验收

使用 8 个代表账号验证：

- 首页统计、组织人数和权限范围。
- 个人任务、团队任务、指标确认、自评和主管评分。
- 部门复核、HR 校准、审批、发布和员工确认。
- 历史趋势、等级分布和部门对比。
- 面谈、申诉、改进计划、试用期和转正。
- 已离职历史档案、豁免员工和转岗员工。
- 通知跳转及已读状态。

页面验收必须刷新后复核状态，并检查浏览器控制台。最终报告列出每个角色、页面、API、业务步骤、通过结果和阻塞项，不能只以构建或单元测试成功作为完成标准。

## 实施边界

- 遵循现有 Prisma schema、模块化单体架构和 API 合同。
- 优先复用 `seed-demo-history.ts` 中已验证的快照、任务、评分和流程创建模式，但拆分为可测试的生成器、校验器和持久化单元。
- 不修改与模拟数据无关的业务页面或服务。
- 若实现过程中发现 schema 无法表达已批准的故事线，先报告具体字段或状态缺口并修订设计，不以演示为由扩大模型。

## 完成标准

以下条件全部满足后，真实演示数据任务才算完成：

1. 代码和测试实现完成，生成器与数据库验证通过。
2. 重跑幂等，非合成控制记录未被修改。
3. 当前未上线的生产模式数据库成功写入一次。
4. 8 个代表账号可以登录并看到各自正确的数据范围。
5. 关键故事线可以从 UI 和 API 连续追踪。
6. 浏览器刷新后状态正确，控制台无相关错误。
7. 交付最终数据统计、验收结果和剩余阻塞项。
