# 员工档案与入离职简化设计

## 1. 状态与目标

- 日期：2026-09-26。
- 状态：用户已于 2026-09-26 确认开发、提交、推送和上线；实施与验证结果另行记录，不以设计确认代替上线验收。
- 本次明确确认的日期口径：北京时间入职日零点生效；最后工作日当天仍可使用系统，次日零点离职停用；提前审核不提前停用，事后补审在审核通过时停用，并保留实际离职日期。
- 目标：录入省事、中断不丢、审核简单、人员不重复、当前信息与历史记录一目了然。
- 核心原则：一人一份档案，每次入职一段经历，每次正式变更有记录。

本设计在现有员工档案、任职、合同、人事变更审核和登录模块内收敛流程，不建设第二套员工主数据或审批系统。以下为本次开发依据。

- `2026-09-18-employee-reentry-onboarding-design.md`
- `2026-09-18-employee-create-wizard-design.md`

保留一人一档、手动归档、管理员可自审、新工号、身份查重、历史补录和钉钉仅用于身份登录等既有边界。本文确认后，四步向导替代七步向导；明确日期边界、退回续填、取消归档和历史展示。

## 2. 信息结构

| 信息 | 含义 | 保存规则 |
| --- | --- | --- |
| 员工主档 | 同一个自然人的稳定身份、个人资料与账号关联 | 再入职复用，不建立重复人员 |
| 任职经历 | 每次入职至离职的完整经历 | 每次入职生成新工号，历史工号永久保留 |
| 任职变更 | 本段经历中的调岗、转正、主管调整等 | 保留前后值、生效日及审核来源，不换工号 |
| 合同材料 | 独立的合同及附件记录 | 新增、修订、作废均留痕；不自动复制旧合同为新合同 |
| 变更申请 | 未正式生效的新增或修改内容 | 草稿可续填、退回可修改、审核与生效可追溯 |

档案主列表中同一员工一人一行。草稿和未正式建立主档的新增申请不计入正式员工人数。历史工号可以查询到同一人，但不能登录或重新分配；预留的新工号与当前有效工号明确区分。

本次入职与经历内调岗必须能被明确区分；沿用现有实体和来源关联，不能靠岗位名称或时间重叠推测人员是否重复。

## 3. 三类状态分开管理

| 状态类别 | 用户可见内容 | 不得混淆 |
| --- | --- | --- |
| 任职状态 | 待入职、试用期、在职、已离职 | 提交离职申请不立即变为已离职 |
| 办理进度 | 草稿、待审核、已退回、已通过待生效、已生效、已撤回／取消 | 审核通过不必然已经生效 |
| 归档标记 | 未归档、已归档 | 归档不是离职；取消归档不是再入职 |

列表组合示例：

- 在职 · 离职待审核。
- 在职 · 档案修改已退回。
- 已离职 · 再入职待审核。
- 待入职 · 10 月 8 日生效。

“待入职”只用于基础档案已经批准、尚未到入职日期的人员；未审核新增申请留在申请办理范围，不提前作为在职员工参与业务。

## 4. 操作流程

### 4.1 新增员工

新增员工 → 四步填写 → 提交审核 → HR 管理员二次确认 → 按日期生效。

1. 基本信息：姓名、联系方式、身份查重。
2. 本次任职：公司、部门、岗位、入职日期、用工类型、试用期、花名册直属主管与绩效直属上级。
3. 补充资料：个人教育、住址、紧急联系人、保障与银行卡、合同附件，按分组展开。
4. 检查并提交：已填信息、缺失提醒与身份匹配结果。

姓名是保存草稿的最低条件；其他信息未填完整不阻止保存草稿。正式提交沿用现有必要字段与身份唯一性要求，不额外增加材料完整性门槛。补充资料可跳过，后续在原档案补充。

工号在提交时生成并预留，不要求人工填写。姓名不触发查重；手机号命中需人工确认是否同一人；身份证精确命中按已有人员状态进入查看档案或再入职，不能新建第二个人。

身份命中尚未建立主档的待审或退回申请时，进入原申请查看或续办。已取消、已归档申请保留历史，但不能永久阻断合法重新办理；仍需复用已有身份主体并检查是否另有有效任职或正在办理的申请。

### 4.2 草稿保存与恢复

- 自动保存成功显示小型“已保存”，失败显示明确原因，不以“已保存”掩盖失败。
- “保存并退出”与关闭抽屉都需要确认已保存成功；失败保留输入，并允许重试或明确选择放弃未保存内容。
- 恢复原步骤、普通字段、合同附件，以及已保存但不回显明文的敏感字段。
- 已填写的值优先于自动带入值；岗位、日期等联动不覆盖人工修改。
- 自动保存更新同一份草稿，不为每次键入制造一条业务历史。
- 退回后显示退回原因和“修改后重新提交”；复用原申请及预留工号，保留各次提交、退回和审核版本。

### 4.3 修改档案

查看档案 → 编辑对应分组 → 保存草稿或提交审核。

只提交实际改变的字段。空字符串、空值与日期表示应按业务含义标准化，未修改不生成审核。修改草稿中的身份证或银行卡只在明确替换时更新；续填时输入框为空不能丢弃已保存的新值。

未经审核的修改不能覆盖正式内容。一般字段提醒贴近输入框；无权限、身份冲突、引用不存在或并发覆盖等确实不能安全执行的问题，应说明原因与下一步。

### 4.4 办理离职

在职／试用期员工 → 办理离职 → 填最后工作日与原因 → 提交审核 → HR 管理员确认 → 到日期停用。

- 申请期间保留原任职状态，显示离职办理进度。
- 未来离职已通过：显示具体停用日期，不提前关闭本地或钉钉登录。
- 离职生效：结束本次任职，保留合同与历史业务记录，停止新登录，并使原登录会话失效。
- 不自动归档、不删除员工，也不自动更改已启动绩效周期的历史关系。
- 业务交接、财务结算、设备归还不作为本期新增审批环节。

### 4.5 再入职

已离职／已归档员工 → 办理再入职 → 确认本次任职 → 审核 → 按日期生效。

- 原员工主档、账号关联和历史记录保持同一主体。
- 已归档员工发起再入职不立即取消归档；基础档案审核通过后转入待入职展示，或在日期已到时生效。原归档标记作为本申请造成的展示变化留痕，以便取消时准确恢复。
- 个人资料自动带入；原部门岗位可作为参考，明确确认本次任职，不自动采用钉钉组织信息。
- 生成新工号，新合同单独维护；旧工号、旧合同与原离职记录保持历史属性。
- 待入职阶段不能登录；生效后使用新工号，恢复标准用户资格。
- 历史 HR、系统管理员等高权限不自动恢复，由有权管理员通过原权限入口维护。
- 钉钉身份仍属于本人且无冲突时按现有绑定政策恢复；不能因再入职自动绑定其他人的身份。
- 已批准待生效申请如需修改，撤销该版本的待生效内容并重新审核，不能留下会按旧日期自动生效的任职记录。
- 取消尚未生效的再入职，只撤销本申请造成的待生效影响；恢复原离职展示、历史工号显示及仍适用的归档标记，不恢复旧工号登录资格。不能整份回放旧快照而覆盖期间另行批准的信息变更。
- 取消后保留新工号的预留与取消痕迹，自动序列不回退、不回填；重新办理沿用原人员主体，不重建员工。

### 4.6 归档与取消归档

- 归档只由操作员显式执行，支持批量离职员工和草稿。
- 草稿归档与员工归档分别处理，不把草稿当作正式员工。
- 有未完成的已提交申请时，沿用现有规则不执行归档，并显示“请先处理正在办理的变更”及原申请入口；单纯未提交草稿可显式归档。批量结果逐项说明，不把成功与失败混为一条提示。
- 已归档内容仍可查询历史；取消归档恢复展示及原编辑资格，不改变任职状态或登录权限。
- 草稿取消归档后仍是草稿，可从原位置继续填写。
- 归档、取消归档沿用已有维护权限并记录操作者和时间，不新增多级审批。

## 5. 日期与审核生效

所有业务日期统一解释为 `Asia/Shanghai` 日历日，不能因浏览器或服务器时区不同产生八小时偏移。

| 场景 | 正式生效规则 |
| --- | --- |
| 未来入职已批准 | 入职日 00:00 生效，之前不能登录 |
| 当天或过去入职，任职当前仍有效 | 审核通过后生效，保留业务入职日与实际审核时间 |
| 未来离职已批准 | 最后工作日完整保留登录资格，次日 00:00 停用 |
| 最后工作日为今天，今天审核 | 当天仍有效，次日 00:00 停用 |
| 最后工作日已过去，事后补审 | 审核通过时立即停用，保留真实最后工作日 |
| 已结束任职的历史补录 | 只增加历史，不开放账号、不替换当前任职 |

例如最后工作日为 10 月 8 日，页面明确展示“10 月 9 日 00:00 停用”。最后工作日、停用时刻、申请时间与审核时间是不同概念，不共用一个含糊的“日期”。

定时任务和请求时的生效检查使用同一规则、同一批准版本。任务延迟不能让离职员工继续操作，也不能让未来入职提前登录。历史补录不改写已启动绩效任务快照。

## 6. 审核交互与权限

- 沿用现有人事变更审核入口与 HR 管理员二次确认，允许管理员审核本人提交的申请。
- 不增加部门负责人、直属上级逐级审核，也不改变既有普通 HR 权限范围。
- 列表默认只有“退回”“通过”，支持批量；一个通过动作处理本次待审内容，内部仍保留基础档案和绩效关系的独立审核状态。
- 同一申请本次“通过”涉及的待审范围在一个事务内完成；任一范围失败，本次操作均不生效，并说明具体原因。此前已经生效的范围不回退。批量不同员工分别处理，允许逐项成功或失败并明确展示结果。
- 详情只突出变更前后值、生效日期、必要影响和附件。解释性文字放在小问号中，支持换行。
- 对既有部分审核记录：基础档案批准后可按日期建立有效任职；未审的首次／再入职绩效关系保持空白，普通在职变更继续使用上一份已批准关系。不得从待审值计算权限或生成绩效关系快照。
- 已退回记录可恢复填写；未生效申请的撤回／取消保留历史，并撤销其待生效影响。首次入职取消后不留在待入职列表、不开放账号，可从原申请重新办理；已经建立的身份关联继续复用。
- 已部分生效的申请，只能撤回或退回尚未批准、尚未生效的部分；已生效部分保持正式记录，改变它必须另做更正审核。页面分别显示各部分结果，不能把整单简写为“已取消”而隐藏已生效内容。
- 已生效业务变化不得抹除，可发起带原因的更正审核；真正再次入职仍使用再入职流程，不能借取消归档或普通修改恢复登录。
- 前端入口、接口与服务内检查必须一致。未获授权的动作不展示为可点击；不能以解决页面报错为由扩大权限。

## 7. 页面结构与历史展示

员工档案保留单一列表，不重复组织树。

顺序：标题与操作按钮 → 查询面板 → 状态标签 → 表格 → 分页。

- 操作按钮：新增员工、归档、批量操作、刷新；归档标签内按权限提供取消归档。
- 状态标签：全部、在职、试用期、待入职、已离职、办理中、草稿、已归档。“办理中”是待审和退回申请的快捷视图，不新增一层审核流程。
- 查询：姓名／当前或历史工号、部门，其他低频条件折叠；状态由标签控制，避免重复选择。
- 列表重点：姓名与工号、部门、岗位、任职状态、办理进度、操作。
- “全部”显示未归档正式人员，不把新增草稿、申请版本变成重复员工行；草稿和归档在各自标签查看。
- “办理中”按现有人员维护数据范围展示可查看的待审、退回记录，明确新增对象和办理进度；尚无正式主档的申请也有原地查看、续填入口，不要求经办人具有审核权限。同一人员的多个申请汇总到一行后展开，不增加正式员工人数，也不扩大人员数据可见范围。
- 草稿有未完成提示，办理中的正式员工仍只显示一行；点击办理进度打开对应申请。

详情抽屉分为四个区域，当前信息优先展示：

| 区域 | 默认呈现 | 展开查看 |
| --- | --- | --- |
| 当前档案 | 个人信息、当前任职、主管与账号状态 | 分组编辑及字段说明 |
| 任职历史 | 按每次入职分组、当次工号、起止日期与部门岗位 | 本段经历内的调岗、转正、离职与相关申请 |
| 合同材料 | 当前合同与历史合同分开 | 修订、作废、附件及审核记录 |
| 变更记录 | 事项、业务日期、办理人、结果 | 前后值、实际提交审核时间、原因及附件 |

历史记录按时间倒序，可按类型筛选。每条业务事项对应一条主记录，提交、退回、重提、审核和生效作为展开节点，避免同一事项占据多行造成误解。敏感字段只显示“已修改”等脱敏结果，不能在历史接口中返回密码哈希、证件或银行卡密文及指纹。

PC 与移动端均保持抽屉内容独立滚动，操作区可见；长文本与表格不挤压主要操作。历史只对已有权限范围内的人员可见。

## 8. 实现边界与兼容

- 沿用现有员工、任职、工号登记、合同、变更申请、审计和身份绑定模块。统一生效规则，不增加平行人员或审批引擎。
- 建立或补齐明确的任职经历关联与申请版本关联，确保调岗和再入职不会混用工号。
- 旧接口兼容不能绕过审核状态、日期或当前有效任职；敏感响应使用字段白名单。
- 原生效申请更正、重新审核必须更新或撤销旧待生效版本，保持幂等与并发安全。
- 未来招聘只移交入职草稿与来源编号，不直接创建正式员工或开放登录。本期不建设招聘页面。
- 不自动批量修正真实员工、历史离职日期、合同、现有审批或旧工号。若需要生产数据治理，另列对象、影响和恢复方式，经用户授权后处理。
- 既有历史缺少明确关联时，保留原记录和来源，不凭猜测归并任职经历。

## 9. 本期必须修复的现有缺口

1. 新增可选日期和未填字段的空值处理，保证姓名草稿和正常提交可用。
2. 手机号候选确认不被提交时的重新检索清空；身份字段各自正确处理。
3. 退回新增可续填重提，不永久占用身份证而无法继续。
4. 普通档案修改草稿恢复时保留敏感字段的新值。
5. 未审核或已退回的绩效关系不能由自动生效程序写入正式数据。
6. 未来离职不能提前关闭钉钉登录；到期停用必须覆盖已有会话。
7. 档案、草稿、变更及离职详情不能返回密码哈希和内部敏感存储字段。
8. 再入职待生效申请修订后，旧日期、旧岗位等不能继续生效。
9. 前端动作与后端已有能力授权一致。

## 10. 验收标准

- 只填姓名可保存；切换步骤、关闭再打开不丢普通字段、敏感替换值和附件；保存失败有可执行提示。
- 未修改保存不产生审核；退回后在原内容上修改重提，不生成重复员工。
- 新员工和再入职分别验证手机候选、身份证命中、历史工号查询和新工号登录。
- 审核通过不等于提前生效；用受控时间覆盖北京时间入职日零点、最后工作日当日、次日零点和迟到补审。
- 离职前会话在离职生效后不能继续操作；新登录、钉钉登录及已有会话口径一致。
- 基础档案与绩效关系分别覆盖待审、退回、已通过组合，不采用未审关系。
- 取消待生效申请不遗留生效任务；修订重审采用新版本；历史补录不错误改变当前状态。
