# 目标持续跟进与月度自评设计

> 日期：2026-09-03
>
> 状态：业务设计已确认，进入实施计划
>
> 首个验收计划：`2026 Q3 季度考核（902LW测试）`
>
> 适用范围：工作台、目标跟进、月度自评、主管月度评分、提醒、重开与季度汇总

## 1. 与既有设计的关系

本设计采用已经确认的“模型 1”：目标持续跟进与月度正式评分分开记录，在月末形成月度自评结果。

本文件是月度目标跟进和评分的最新业务口径。它替代《月度复盘与评分一体化设计》中与下列事项冲突的内容：

- 员工只能在月末填写一次进展；
- 员工逾期后主管可以不等员工提交直接评分；
- 月度自评必须填写多组复盘说明；
- 缺少月份可以从季度均分中排除；
- 目标当前状态按记录提交时间直接取最新。

既有设计中不冲突的内容继续保留，包括按期次冻结指标版本、正式提交修订历史、并发控制、幂等提交、响应式页面和周期级审核链。

## 2. 背景与已确认问题

当前系统已具备目标进展、月度自评、主管评分和月度结果修订等基础实体，但线上验收暴露出以下问题：

1. 目标当前状态按记录创建时间取最新。晚补的 7 月月度自评记录会显示在已存在的 8 月结果之前，看起来像旧月份覆盖新月份。
2. 自评截止后，定时任务会把未提交的月份自动推进到主管评分，造成主管待办提前出现。
3. 第一份月度自评提交后，任务级状态进入主管评分，日常“更新进展”随之被锁死，无法贯穿整个考核周期。
4. 月度自评页面仍要求所有指标填写进度、状态和自评分，并展开多组可选说明，员工填写门槛较高。
5. 零权重指标也被要求填写自评分和主管评分。
6. 目标详情把所有主动进展和月度结果同等铺开，历史记录喧宾夺主。
7. 现有提醒是周期级通用催办，不能准确表达某个月份的员工逾期和主管等待。
8. 主管评分提交后没有 HR 重新开放该月份的能力。
9. 当前季度汇总会排除 `no_result` 后平均，与“三个月结果齐全后才生成季度总分”的口径不一致。

以上问题必须作为一个闭环处理，不能只修工作台文案或目标卡片排序。

## 3. 设计目标

1. 员工在考核周期内可随时、低门槛地更新每个目标的执行状态。
2. 每个月形成一份独立、冻结、可追溯的月度自评结果。
3. 月度自评只强制填写每个有效权重指标的自评分；目标跟进内容可以为空。
4. 主管只能在员工提交月度自评后评分。
5. 当前状态永远优先展示最新业务月份，不被更晚提交的旧月份记录覆盖。
6. 保留每次主动提交的目标进展，但默认聚焦当前状态，历史记录渐进展开。
7. 工作台准确告诉员工正在处理哪个月份，以及已经提交了几个月。
8. 主管评分、月度总分和季度总分来源清晰且可追溯。
9. 逾期只产生提醒，不自动提交、不自动推进、不自动关闭月份。
10. 公示前允许受控重开；公示后不重开月份。

## 4. 非目标

本次不做以下事项：

- 不允许员工为日常目标进展选择历史月份或倒填业务日期；
- 不提供字段级合并、复杂补录配置或批量代填；
- 不改变部门复核、HR 校准、结果审批和公示职责；
- 不设计公示后的月度分数、月度总分或季度总分更正；
- 不把现有“申诉处理”扩展成月度评分重算流程；
- 不删除历史进展、历史月度自评结果或正式提交修订；
- 不新增“月度归档”“mark”“月度归档结果”等业务概念；
- 不把钉钉组织关系作为绩效上下级来源。

如果后续使用中发现禁止倒填导致员工补救门槛过高，再单独评估历史月份补录，不提前建设。

## 5. 统一业务术语

产品页面、通知、接口说明和验收文档统一使用以下术语：

| 术语 | 含义 |
| --- | --- |
| 目标跟进 | 员工在考核周期内持续更新目标执行情况的过程 |
| 目标进展记录 | 员工每次主动提交的状态、进度和描述 |
| 月度自评 | 员工每个月需要完成的一项正式任务 |
| 月度自评结果 | 员工正式提交并冻结的当月状态、进度、描述和逐指标自评分 |
| 主管月度评分 | 主管在员工提交月度自评后进行的逐指标评分 |
| 月度总分 | 系统按指标有效权重汇总的主管月度评分 |
| 季度总分 | 三个月月度总分的简单平均值 |

页面中不得用“月度跟进”同时指代日常更新和月末正式提交，也不得再显示“月度归档”或 `mark`。

推荐页面文案统一为：

- 月度自评待办；
- 填写月度自评；
- 提交月度自评；
- 月度自评已提交；
- 月度自评结果；
- 历史月度自评结果；
- 待主管月度评分；
- 主管月度评分已完成。

## 6. 业务模型

### 6.1 目标进展记录

目标进展记录是过程记录，员工在考核周期内可随时提交。每次提交只包含：

- 状态；
- 进度，0–100%；
- 描述。

三项均在主动提交时填写。输入、草稿和自动保存不生成目标进展记录。新交互不再要求上传附件；既有历史附件继续只读展示，不删除数据。

每次主动提交都保留为独立记录。员工不能修改或删除已经提交的历史记录，只能再提交一条新进展。

普通进展归属员工实际提交时所在的自然月，时区固定为 `Asia/Shanghai`。本期不允许选择其他月份，也不允许倒填。

### 6.2 月度自评结果

月度自评结果是正式月份记录，以 `AssessmentPeriod` 为归属边界。每个指标可包含：

- 状态，可为空；
- 进度，可为空；
- 描述，可为空；
- 员工自评分。

有效权重大于 0 的指标必须填写 0–100 分的员工自评分。有效权重为 0 的指标仍可展示和填写目标跟进内容，但不显示、不要求员工自评分，也不参与总分。

员工可以只更新部分目标后提交整个月份。未更新的目标显示“本月未更新”，不阻止提交；所有有效权重指标的自评分仍必须齐全。

### 6.3 主管月度评分

主管月度评分归属于同一 `AssessmentPeriod`：

- 有效权重大于 0 的每个指标必须填写主管评分；
- 主管评语选填；
- 零权重指标不显示、不要求主管评分；
- 主管可以查看员工提交的状态、进度、描述和自评分；
- 员工自评总分仅作参考，不作为正式结果。

### 6.4 数据实体职责

继续沿用现有实体边界：

- `IndicatorProgressUpdate`：保存每次主动目标进展，以及由正式月度自评提交产生的月度结果进展；
- `AssessmentPeriod`：保存月份主状态、提交时间、月度总分和锁定状态；
- `AssessmentPeriodIndicatorReview`：保存当前月份各指标的工作数据；
- `AssessmentPeriodReviewRevision`：保存员工和主管每次正式提交的不可变快照；
- `AuditLog` 与 `FlowRecord`：保存退回、重开和后续状态撤回的操作依据。

不删除既有扩展字段，但新页面不再突出“问题原因、下一步计划、所需支持、补充说明”等字段。历史数据继续可读；新月度自评只围绕状态、进度、描述和评分。

## 7. 当前状态与历史排序

### 7.1 业务月份

每条可展示的进展记录都必须向前端返回明确的 `businessPeriodKey` 和记录来源：

- 主动目标进展：按 `createdAt` 转换为上海时区自然月；
- 月度自评结果：使用关联 `AssessmentPeriod.periodKey`；
- 来源值只区分“主动进展”和“月度自评结果”，不在页面创造新业务实体。

### 7.2 当前值选择

目标当前状态按以下规则确定：

1. 先按 `businessPeriodKey` 倒序，最新业务月份优先；
2. 同一业务月份内按正式提交或主动提交时间倒序；
3. 时间相同时按稳定记录 ID 倒序；
4. 旧月份晚补或重提不能覆盖更新月份；
5. 没有任何记录时显示“尚未更新”。

例如：8 月记录在 9 月 3 日 10:42 提交，7 月记录在 10:52 补交，当前仍展示 8 月，因为 8 月是更新的业务月份。

### 7.3 历史展示

目标卡片和详情页默认只突出：

- 当前状态；
- 当前进度；
- 最新业务月份的描述；
- 记录对应月份。

历史记录使用弱化入口“历史进展 N 条”，默认折叠。展开后：

- 按业务月份倒序分组；
- 每月先展示月度自评结果；
- 主动目标进展作为次级时间线展示；
- 每次主动提交均可查看；
- 指标定义变更历史继续单独展示，不与执行进展混排。

## 8. 月度自评填写

### 8.1 自动带入

打开某月月度自评时，每个目标按以下顺序准备状态、进度和描述：

1. 已有该月草稿时，显示草稿；
2. 没有草稿时，带入该业务月份内最新一条主动目标进展；
3. 该月没有主动进展时保持为空，并显示“本月未更新”；
4. 不自动沿用上一个月份；
5. 自评分永远不从历史月份沿用。

员工可以修改带入内容。修改只影响即将提交的月度自评结果，不覆盖原主动目标进展。

### 8.2 提交规则

- 以员工和月份为单位一次提交整份月度自评；
- 只强制校验所有有效权重指标的自评分；
- 状态、进度和描述均可为空；
- 允许只有部分目标存在跟进内容；
- 零权重指标不纳入“评分完成数”；
- 提交使用幂等键和草稿版本，旧页面或旧设备不能覆盖新版本。

正式提交在同一事务中：

1. 保存当前月份指标结果；
2. 计算员工自评参考总分，保留两位小数；
3. 创建员工正式提交修订；
4. 为存在跟进内容的指标形成可展示的月度自评结果进展；
5. 将月份推进到“待主管月度评分”；
6. 写入流程和审计记录；
7. 为主管生成待办与通知。

没有状态、进度和描述的指标不制造空白进展记录，但它的自评分仍保存在月度自评结果中。

### 8.3 提交后

员工提交后，该月份内容冻结，员工不能直接编辑。主管尚未提交前，可以退回员工补充；退回原因沿用现状为选填，但如果填写必须进入修订、流程和审计记录。

退回后只重开该月份，不影响其他月份。员工修改并重新提交后，主管重新评分。

## 9. 主管月度评分与总分

### 9.1 开放条件

主管月度评分只在员工正式提交该月月度自评后开放。员工未提交时：

- 不产生可评分待办；
- 主管可查看员工日常目标进展；
- 主管不能保存或提交该月正式评分；
- 超过员工截止时间只标记逾期并发送提醒，不自动推进月份。

### 9.2 月度总分

系统按月份冻结的指标有效权重计算：

`月度总分 = Σ（主管指标评分 × 指标有效权重）`

规则如下：

- 只计算有效权重大于 0 的指标；
- 所有参与计算的主管评分必须齐全；
- 主管评语始终选填；
- 月度总分保留两位小数；
- 主管正式提交后锁定该月份并创建不可变修订。

### 9.3 季度总分

季度总分使用三个自然月月度总分的简单平均：

`季度总分 =（第 1 月月度总分 + 第 2 月月度总分 + 第 3 月月度总分）÷ 3`

只有三个必需月份都满足以下条件时才生成季度总分：

- 员工已提交月度自评；
- 主管已提交月度评分；
- 月份状态为已完成；
- 月度总分非空。

任一月份缺失时：

- 不把缺失月份记为 0；
- 不只平均已完成月份；
- `no_result` 也不能被排除后提前生成季度总分；
- 周期级部门复核、HR 校准和审批不能开始。

季度总分保留两位小数。

## 10. 状态与任务表达

### 10.1 月份主状态

沿用现有月份主状态，不新增平行主状态：

| 主状态 | 含义 |
| --- | --- |
| `unopened` | 月度自评尚未开放 |
| `self_eval` | 待员工月度自评，包含逾期、主管退回和 HR 重开情形 |
| `manager_scoring` | 员工已提交，待主管月度评分 |
| `completed` | 主管已提交并锁定 |
| `no_result` | 兼容历史数据，不用于跳过季度必需月份 |

下列状态由主状态、截止时间和最新流程记录派生显示，不增加相互竞争的数据库主状态：

- 月内跟进中；
- 待员工月度自评；
- 月度自评已逾期；
- 已退回待修改；
- 待主管月度评分；
- 月度已完成；
- HR 已重新开放。

### 10.2 工作台

员工工作台优先显示最早一个尚未提交的已开放月份，先补齐前序缺口。示例：

> 2026年9月月度自评
>
> 第3/3期 · 已提交 2/3

工作台不得仅根据 `AssessmentTask.status` 把仍有月度自评待办的员工显示为“结果确认”或“结果处理中”。月度流程必须以 `AssessmentPeriod` 为真实来源。

当没有员工待办但仍有主管评分未完成时，员工侧显示“等待主管月度评分”；存在未来未开放月份时显示“持续跟进目标，等待下月月度自评”，不得提前进入结果确认。

只有所有必需月份完成并进入公示后，员工才看到正式“结果确认”。

### 10.3 目标跟进概览

目标跟进页不再使用含义不清的“期次进度 0/3 已完成”。顶部至少区分：

- 当前月份与动作，例如“9月待月度自评”；
- 员工月度自评提交进度，例如“已提交 2/3”；
- 本月目标更新覆盖，例如“本月已更新 2/3 个目标”；
- 如需展示主管进度，明确写“主管月度评分 1/3 已完成”。

目标进展和正式评分进度不能合并为一个数字。

## 11. 随时更新目标进展

员工是否可以更新进展，不再由任务当前是否处于主管评分决定。满足以下条件即可更新：

- 当前用户是目标所属员工；
- 考核计划已正式开放且尚未公示；
- 目标已形成正式确认版本；
- 员工未被豁免；
- 计划未关闭。

某个月月度自评已提交或主管已评分，不影响员工为之后业务月份继续更新目标。公示后目标进展转为只读。

## 12. 提醒节奏

提醒以“员工 + 月份”为对象，不再只依赖任务级状态。

员工月度自评未提交时：

1. 截止前 3 天提醒员工；
2. 截止当天提醒员工；
3. 逾期第 1 天提醒员工和绩效直属上级；
4. 之后每逾期 3 天提醒员工和绩效直属上级；
5. 员工提交后立即停止员工逾期提醒，并开放主管月度评分。

HR 不接收逐人逾期通知。具备相应数据范围的 HR 在周期管理页查看月度逾期名单和数量。

每条提醒必须以 `periodId + reminderType + reminderDate` 保证幂等。周期通知关闭时不发送外部消息，但系统内待办和逾期状态仍正常显示。

过期只提醒，不自动提交、不自动推进到主管评分、不自动把月份标为无结果，也不自动归档。

## 13. 主管退回与 HR 重新开放

### 13.1 主管退回

员工提交、主管尚未提交时，冻结的绩效直属上级可以退回该月：

- 月份回到“待员工月度自评”；
- 员工上次提交版本保留；
- 当前内容作为可修改初始值展示；
- 已保存但未提交的主管评分草稿清除；
- 其他月份不受影响；
- 员工重新提交后主管重新评分。

### 13.2 HR 重新开放

主管评分已经提交且月份已经锁定时，可由以下业务角色填写原因后直接重新开放：

- 具备 `cycle_plan_edit` 周期管理权限的 HR；
- HR 管理员。

系统管理员沿用平台全局管理能力，但不作为新的业务角色名称展示。重新开放不走申请审批。

重新开放原因必填。服务端必须在一个事务中：

1. 校验结果尚未公示；
2. 以版本条件锁定月份，防止重复重开；
3. 保留原员工和主管正式提交修订；
4. 将该月份恢复为 `self_eval`；
5. 清空当前 `employeeSubmittedAt`、`managerSubmittedAt`、`lockedAt`、员工参考总分和主管月度总分；
6. 清空当前主管评分和主管评语；
7. 将原员工月度自评内容作为员工可修改的初始值；
8. 撤销由旧季度汇总产生的当前总分、等级及未公示后续处理状态；
9. 将任务恢复到月度自评阶段；
10. 写入操作者、原因、时间、旧状态和新状态的流程及审计记录；
11. 通知员工重新提交该月月度自评。

如果任务已经进入部门复核、HR 校准或审批但尚未公示，重新开放会撤回这些当前处理结果。历史流程和审计记录不删除。

员工重新提交后，主管必须重新提交该月评分。系统重新检查所有月份，只有全部完成后才重新生成季度总分并进入后续审核链。

### 13.3 公示后边界

结果公示后禁止重新开放月份。

现有“申诉处理”只支持由 HR 或系统管理员录入申诉，并选择“维持原结果”或“改判最终绩效等级”。改判只调整最终等级和系数，不修改月度自评、主管月度评分、月度总分或季度总分。

本次不把该入口扩展为月度评分更正。以后如确需修改公示后的月份分数和总分，必须作为独立需求重新设计权限、审批、版本和对外通知。

## 14. 接口边界

### 14.1 目标跟进接口

目标跟进列表和详情需要返回：

- 当前业务月份；
- 当前状态、进度和描述；
- 本月主动更新目标数；
- 每条历史记录的业务月份和来源；
- 当前是否允许更新进展。

更新进展接口只接收状态、进度、描述和并发版本。旧附件数据保留，但新页面不再提交附件。

### 14.2 月度自评接口

获取详情时同时返回当前月草稿、当月最新主动进展、历史月度自评结果和字段来源。提交接口允许状态、进度和描述为空，只对有效权重指标校验自评分。

### 14.3 主管评分接口

主管草稿和正式提交只接收有效权重指标评分；服务端不能信任前端过滤结果，必须按冻结指标版本重新校验权重和完整性。

### 14.4 重新开放接口

新增月份级重新开放接口，至少接收：

- 月份 ID；
- 必填原因；
- 预期版本或更新时间。

接口必须校验周期管理权限、月份已完成、结果未公示和并发版本。重复请求不能重复撤回流程或重复发送通知。

## 15. 兼容与数据迁移

### 15.1 历史记录

- 已存在的主动目标进展全部保留；
- 已存在的月度自评提交通过 `periodId` 和正式修订继续识别；
- 旧月份补交记录重新按业务月份排序，不改写其创建时间；
- 旧扩展说明和附件不删除，可在历史详情中只读查看；
- 不把草稿或自动保存补写成正式历史。

### 15.2 当前工作数据

`AssessmentPeriodIndicatorReview` 继续作为月份当前工作记录，正式事实以修订快照为准。重开和退回只能重置当前工作状态，不能删除已提交修订。

### 15.3 首个验收计划

`2026 Q3 季度考核（902LW测试）` 只作为首个真实闭环验收样本，不能在代码中硬编码。

该计划当前存在人工测试形成的异常排期，包括部分主管截止时间早于员工自评截止时间。开发和自动化测试不得通过修改生产数据来掩盖逻辑问题。需要修复该测试计划排期时，必须先向用户说明准确字段和影响，再单独获得数据修改确认。

## 16. 错误处理与并发

- 主动目标进展使用最新记录时间或版本进行乐观并发控制；
- 月度草稿、员工提交、主管提交、主管退回和 HR 重开均携带预期版本；
- 员工与主管正式提交使用幂等键；
- 过期页面提交时，服务端返回明确的“内容已更新，请刷新”错误；
- 历史月份重提后，当前展示重新按业务月份计算；
- HR 重开与主管提交并发时只能有一个操作成功；
- 重开事务任一步失败时，总分、月份状态和后续任务状态全部回滚；
- 通知失败不能回滚已经成功提交的业务事务，但必须可重试并保留失败状态。

## 17. 权限

| 操作 | 允许角色 |
| --- | --- |
| 更新目标进展 | 目标所属员工 |
| 保存、提交月度自评 | 期次员工本人 |
| 查看下属日常进展 | 按既有目标可见范围和冻结上下级关系 |
| 主管退回、评分 | 期次冻结的绩效直属上级 |
| 查看周期逾期名单 | 具备周期管理权限和对应数据范围的 HR、HR 管理员 |
| 主管提交后重新开放月份 | 具备 `cycle_plan_edit` 权限的 HR、HR 管理员 |
| 公示后录入和处理最终等级申诉 | 沿用现有 HR、系统管理员权限 |

绩效直属上级继续以已发起周期冻结的本系统关系为准，不从钉钉通讯录动态覆盖。

## 18. 验收标准

### 18.1 目标持续跟进

- 员工在整个考核执行期都可提交状态、进度和描述；
- 每次主动提交都保留，草稿不生成历史；
- 9 月提交的 7 月月度自评结果不会覆盖 8 月当前状态；
- 默认页面聚焦当前，历史折叠并按业务月份分组；
- PC 和手机均能完成更新，不出现横向溢出或被底部操作区遮挡。

### 18.2 月度自评

- 工作台显示明确月份、第几期和已提交进度；
- 月度自评自动带入当月最新主动进展，不沿用上月自评分；
- 状态、进度和描述可以全部为空；
- 只更新部分目标也能提交整月；
- 所有有效权重指标自评分必填；
- 零权重指标不要求自评分；
- 员工提交后冻结，主管退回后可修改并重提。

### 18.3 主管月度评分

- 员工未提交时主管不能评分；
- 员工逾期不会自动进入主管评分；
- 有效权重指标主管评分必须齐全，评语选填；
- 零权重指标不要求主管评分；
- 系统按权重计算月度总分并保留两位小数；
- 主管提交后锁定月份。

### 18.4 季度汇总

- 三个月全部完成后才生成季度总分；
- 缺一个月时不计 0、不按已完成月份平均；
- `no_result` 不会让季度结果提前生成；
- 季度总分是三个月月度总分的简单平均并保留两位小数；
- 未形成季度总分时不能进入周期级结果审核。

### 18.5 提醒

- 截止前 3 天和截止日只提醒员工；
- 逾期第 1 天及之后每 3 天提醒员工和绩效直属上级；
- 员工提交后停止员工逾期提醒；
- HR 通过周期页查看逾期名单，不接收逐人提醒；
- 重复调度不生成重复提醒；
- 截止后不自动提交、推进或归档。

### 18.6 重新开放

- 具备周期管理权限的 HR 和 HR 管理员都能填写原因后重开；
- 无权限人员、员工和主管不能重开已完成月份；
- 重开保留原员工及主管正式修订；
- 公示前后续处理会被撤回但历史审计不删除；
- 员工重提后主管必须重评；
- 公示后重开被服务端拒绝；
- 现有申诉改判不会修改月度分数和季度总分。

## 19. 发布与验证边界

本设计需要 API、Web、调度、通知和数据库兼容逻辑共同上线，不能只发布前端文案。

实施完成后至少需要：

- 目标当前状态业务月份排序单元测试；
- 月度自评可空跟进与零权重指标契约测试；
- 员工未提交时主管不可评分的服务测试；
- 三个月齐全才汇总的聚合测试；
- 月度提醒日期和幂等测试；
- HR 能力权限与 HR 管理员重开测试；
- 重开撤回未公示后续状态的事务测试；
- 公示后拒绝重开测试；
- 员工、主管、HR 三角色 PC 与手机端到端验收；
- `2026 Q3 季度考核（902LW测试）` 的线上只读状态核对和经授权后的闭环验收。

生产发布仍需单独获得“上线”授权。发布前必须核对最新 `main` 与生产基线、备份数据库、保留 API/Web 回滚镜像，并在发布后验证真实线上地址、任务状态、权限和提醒行为。
