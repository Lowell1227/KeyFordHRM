# 绩效审批与待办入口优化方案

> 状态：方案已进入实施；代码、提交、发布与业务验收状态分别以本轮验收记录和发布核验为准。基线为 2026-11-18 `main`/`origin/main` 的 `f5066940`；当时生产健康接口返回 `status=ok, db=ok`。

## 1. 目标与边界

本方案整合本次绩效代码审查、审批表单与办理记录审查、页面阅读层级审查，以及相邻会话《评审工作台待办关联与优化》的待办入口审查。目标是让用户一眼看清「我现在办什么、为什么轮到我、下一步到谁」，并从任一待办或通知准确进入同一事项。

- 保留现行目标计划、目标变更、月度评价、结果评估的业务环节与任务快照；页面优化不重新定义审批人或扩大数据范围。
- HR 对目标变更的授权与目标变更办理继续分开：授权页负责开通、撤销和查看授权状态；变更页负责发起、修改、审核和记录。
- 工作台、绩效待办、目标变更列表、通知是同一事项的不同入口；各自读取同一后端动作权限，不用菜单可见性代替鉴权。
- 已发起任务按冻结审批关系办理；岗位名、系统角色和当前组织负责人均不能单独推断审批权。钉钉通知仅作提醒和跳转。
- 不处理真实员工、组织、分数或审批结果数据；不清理历史记录。实施发布以用户明确授权、验证和生产核对为前提。本方案中涉及委托、转交、撤销授权后在办变更如何处置的政策，须另行确认。

## 2. 发现与优先级

| 编号 | 优先级 | 已发现的问题 | 本轮目标 |
| --- | --- | --- | --- |
| A1 | P1 | 最终定级服务允许非任务指定上级的系统管理员提交，绕过冻结审批人 | 仅当前任务指定人可办理；如将来需要代办，建立显式授权与审计 |
| A2 | P1 | 员工可能通过月度评价接口读到上级未提交的评分草稿 | 按读取者和提交状态遮蔽上级草稿；补员工权限负向验证 |
| A3 | P1 | 周期计划审核 UI 只有通过，退回与理由缺失；接口也不强制退回理由 | 补「通过 / 退回」及必填退回原因，详情可回看结论 |
| E1 | P1 | 目标变更与改进计划通知虽有路径信息，但通用通知解析器因无标准任务 ID 不跳转 | 按通知类型解析受控内部路由，直达可办理详情 |
| E2 | P1 | 兼任管理者点击本人目标确认通知可能误入团队页并被拒绝 | 依据通知对应的任务、动作和办理者选个人或团队目标页 |
| E3 | P1 | 目标未完成时，首页可能先提示更新目标进展 | 先显示目标制定/确认动作，目标生效后再显示进展 |
| E4 | P1 | 目标变更待办未汇入工作台；由上级代员工发起后退回，上级在现有分类中难找记录 | 汇集「当前由我修改/提交/审核」的目标变更，并直达事项 |
| U1 | P2 | 审批列表被大块图表和摘要压到下方；部门复核按钮在长证据之后 | 当前待办优先，重要依据其次，详细证据折叠，办理操作固定可见 |
| U2 | P2 | 审批表单、历史与按钮跨页位置和文案不一致 | 统一节点信息、意见表单、时间线和页脚动作规则 |
| U3 | P2 | 目标变更记录把员工确认显示为「审核通过」，原始逐字段对比难读 | 阶段化动作文案；先看变更摘要及有变化的项目 |
| R1 | P2 | 列表读失败可能呈现空白或无数据，退回意见在请求失败后丢失 | 失败明确提示和原位重试；意见直到成功才清除 |
| R2 | P2 | 目标变更全量拉历史并逐条补数据，前端本地分页 | 后端按权限过滤并分页，列表批量查询；保留原有可见范围 |
| R3 | P2 | 目标变更创建后跳详情失败无恢复入口；周期筛选可能出现请求竞态 | 可返回列表且能重试；旧请求不覆盖新选择 |
| R4 | P2 | 历史自任上级任务的结果读取存在潜在本人信息泄露风险 | 为本人任务遮蔽尚不可见的结果；检查历史数据和负向测试 |
| U4 | P3 | 终评等级选择和目标复核侧栏的键盘/读屏状态不完整，周期卡片回车可能触发两次动作 | 补选择状态、焦点、标签与事件隔离 |

P1 表示优先消除权限、隐私、审批不可达和核心入口错误；P2 是高频办理体验与稳定性；P3 是可用性收尾。以上是代码审查发现与静态推断，尚非真实角色全流程验收结论；R4、周期卡片键盘事件尤其需要实测确认。

## 3. 待办入口的职责与布局

| 位置 | 回答的问题 | 显示内容与点击结果 | 不承载的内容 |
| --- | --- | --- | --- |
| 总工作台「我的待办」 | 今天哪些事项轮到我？ | 只列当前办理者可执行的跨模块事项：常规绩效任务、目标变更、改进计划等。每条显示事项、员工、周期、当前节点、待办动作、更新时间；点击进对应详情与操作位 | 完整历史、静态统计、仅因参与流程而产生的非本人待办 |
| 绩效待办 | 常规考核当前办到哪？ | 按目标制定/审核、月度评价、结果确认等环节查看本人及授权团队的任务；按周期和动作筛选，直达任务 | 目标变更授权管理；完整变更历史可在变更页查看 |
| 目标变更 | 一项变更由谁办、变了什么？ | 顶部优先「待我处理」：包括我发起且被退回待修改、我需提交、我需审核；随后是「我发起的 / 团队相关 / 相关记录」。发起按钮仅对后端允许的任务显示 | HR 授权开通/撤销 |
| 目标变更授权（HR） | 谁可发起变更？ | HR 开通/撤销、有效期或状态（若现有模型支持）及授权记录；直达对应人的授权，不冒充业务审批待办 | 变更内容审查和员工办理 |
| 通知与钉钉卡片 | 哪个事件需要提醒？ | 明确事项名与目标节点，点击到具体个人或团队详情；到达后重新读取后端权限与最新状态 | 独立定义审批资格、代替待办清单 |

### 统一的快捷入口行为

1. 同一待办只有一个稳定业务标识；工作台和模块页可以同时链接它，但不重复创建任务或累加不同口径的数量。
2. 当前可办数量只计算当前登录人确实可以执行的动作。只读知情、已处理、历史参与计入「相关记录」，不计入待办。待办数由后端动作权限/状态派生，并与列表筛选一致。
3. 条目文字用动作词，例如「修改目标变更」「审核目标变更」「提交上级评价」；「查看」留给历史记录。发起人的草稿可从变更页继续编辑，但不把未提交草稿误称审批待办。
4. 点击后带业务 ID 定位详情、当前节点和相应操作。已被别人处理、撤销或失权时，仍可展示授权范围内的详情和明确的「事项已更新」提示；不能继续执行过期动作。
5. 个人和团队身份同时存在时，先判断该事项是否是本人任务，再判断当前动作是个人还是团队动作。不可只凭 `isManager` 跳团队页。
6. 菜单应保持正常可发现性：有授权/相关记录者可进目标变更；无授权也无记录者不显示入口，且后端路由独立拒绝越权访问。是否给所有人显示只读说明页不在本方案内。

### 建议页面骨架

```text
绩效工作台 / 当前待办                         待办数 · 按周期/事项筛选
┌ 轮到我：动作 + 员工 + 周期 + 当前节点 ────────────── 办理 ┐
└ 已处理 / 相关记录（次级入口）                         ┘

绩效待办：周期选择 → 我的事项 / 团队事项 → 环节 → 任务表
目标变更：待我处理 → 我发起的 / 团队相关 / 相关记录 → 详情
目标变更授权（HR）：授权对象 → 有效状态 → 开通/撤销 → 审计
```

PC 端固定周期和当前环节的基线位置，移动端把筛选收在同一栏，不让菜单切换使主内容左右跳动；快捷入口标题与详情标题保持同一业务名称。空状态区分「确无待办」「筛选无结果」「读取失败」。

## 4. 审批详情、表单、记录

统一阅读顺序：**当前待办 → 关键依据 → 可展开详情与办理记录 → 固定办理按钮**。

1. 首屏标题区只放员工、周期、当前节点、当前办理人和下一节点。当前动作最显眼；校准配额等会阻止决策的依据仍在首屏可见。校准分布图、最近驳回记录等辅助材料挪到折叠区或次级标签。
2. 审批依据先给摘要：目标变更显示增加/删除/修改项数及权重变化，先列有变化的指标；结果审核显示评分、等级、关键校准差异。完整原始字段、月度表、证据和历史仍可展开核验。
3. 办理记录统一按时间倒序，每项显示「节点 · 办理人 · 动作 · 时间 · 意见」。发起后无需把自动保存草稿逐次当成审批节点；保留后台审计。员工确认显示「员工确认」，不能显示「审核通过」。退回同时显示退回到谁和重走路径。
4. 审批按钮放在详情页或抽屉的固定底栏；PC 与手机均能在阅读证据时看到当前可执行动作。列表允许快速办理，但详情必须能完成同一动作。没有权限时只显示状态与阅读入口。
5. 按钮使用完整业务语义：「通过周期计划」「退回周期计划」「提交部门复核」「退回给绩效上级」「确认目标变更」。确认对话框只写当前决策、影响和下一步；移出与当前决策无关的公司负责人说明。
6. 退回原因在字段旁必填并提供多行输入；API 同样校验。网络失败保持弹窗、意见、选择和当前滚动位置，可原位重试；提交成功才清空。通过意见按现有业务规则可选时保留可选，不另加必填。
7. 周期计划详情能看到审核人、结论、时间及意见；被退回后知道下一步。目标复核侧栏与终评选择应满足键盘焦点、选中态和读屏标签。

主要涉及 `web/src/views/admin/CycleManageView.vue`、`web/src/views/approval/ApprovalView.vue`、`web/src/views/calibration/CalibrationView.vue`、`web/src/views/task/components/DepartmentReviewWorkspace.vue`、`web/src/views/task/components/GoalReviewWorkspace.vue`、`web/src/views/goal-changes/GoalChangeDetailView.vue`、`GoalChangeGoals.vue` 和共用证据/历史组件。尽量共用排版和交互规则，不为不同流程强行增加同一套冗余状态机。

## 5. 实施顺序与验收

### 第一批：权限与核心待办（必须先完成）

- 修 A1/A2/A3 与 R4；确认冻结审批人、员工草稿遮蔽、周期退回必填原因和历史本人任务的边界。
- 修 E1–E4：通知和首页路由、待办来源聚合及目标变更退回编辑归属。与钉钉「我的待办」采用同一动作口径，但不改钉钉人员主数据。
- 负向验收必须覆盖员工、兼任经理、绩效上级、部门负责人、分管领导、HR、系统管理员；管理员身份不能越过当前业务审批人。

### 第二批：页面阅读与操作

- 修 U1–U3：审批详情结构、按钮位置/文案、目标变更差异、办理记录与周期计划审核表单。
- 修 R1/R3：错误与重试、保留意见、导航/筛选竞态。
- PC 与 390px 手机都逐项查看长意见、抽屉滚动、固定底栏、列表宽度和键盘焦点。

### 第三批：规模与易用性

- 修 R2 后端分页和批量查询，验证旧可见范围、排序和总数不变；在有历史数据的隔离库测查询数与响应时间。
- 修 U4；改进计划暂停态可在 HR 监控中以「流程异常」呈现，但实际处置权限/转交规则先做业务确认。

### 完成标准

1. 每个真实可办目标变更，在工作台和变更页的「待我处理」都可找到，数量一致，且直达同一详情；退回给代发起上级的任务亦然。已办/只读不计入待办。
2. 员工兼经理的本人通知直达本人详情，目标未生效前不显示进展动作；变更/改进计划通知均能直达获授权页面。
3. 未授权员工、非指定审批人、仅有系统管理角色的人无法通过 URL 或接口办理；员工看不到上级未提交的月评草稿。
4. 周期审核可以通过或填写原因退回；失败不丢意见，详情可追溯结论和下一步。
5. 四类审批页面的首屏都能在不滚完整个证据区的情况下看到当前事项、关键依据与办理入口；记录中的节点、动作、角色准确。PC 与手机可完整阅读、办理、重试。
6. 数据加载失败不会伪装成空列表；后端分页和前端筛选结果一致。技术测试、隔离预览、线上只读冒烟和真实业务验收分别记录，不相互替代。
