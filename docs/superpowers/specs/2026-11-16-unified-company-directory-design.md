# 公司目录统一

## 已确认目标

2026-11-16 用户同意将公司选择统一为一套公司目录，旧代码兼容留在后台，日常维护不再填写“内部公司映射”。本轮开发及验证，不包含发布授权。

## 行为

- 基础资料公司目录只维护公司名称、启用状态；员工所属公司和每份合同的签约公司共用该目录，分别选择，互不覆盖。
- 所有启用公司都能作为员工所属公司，无需映射到固定四类。新建、再入职、档案修改、任职维护、草稿恢复、提交和到岗生效遵循同一规则。
- 员工公司的业务引用为现有 `contractSubjectId`，名称由服务器生成 `companyText` 快照。公司改名和停用不追溯改写历史；已停用的原值可保留，不能新选。
- 历史只有公司原文或旧代码的记录继续可读、可编辑无关字段，不强制重新分类，不自动推断关联，不默认为孚德。
- 花名册导出只展示一个“所属公司”，旧保存的 `organization` 导出选择兼容到公司字段并去重。
- 转正申请的员工核对信息及详情从有效任职读取公司名称快照，历史旧码只作显示兜底；不能用部门范围代码代替员工公司。
- 部门的组织分组、普通 HR 的既有数据范围和通知收件范围保持现状。本轮不根据任职或合同主体重新划分部门，不修改角色与已冻结绩效关系。

## 后续确认的公司范围

用户于本轮后续明确确认：普通有转正办理权限的 HR 按当前正式生效任职的公司目录 ID 管理同公司员工，通知保持同口径；HR 管理员全范围、已指派申请可见性不变。该确认取代本文初稿“保留部门公司授权范围”的限定，不修改部门树、角色能力或已冻结绩效关系。缺当前目录 ID 不猜测关联。

## 数据兼容

- `EmploymentRecord.company` 改为可空的旧组织分类兼容字段。保留已存在的代码；新目录选择不从名称、主体映射或部门推断代码，不再要求客户端提供。
- `ContractSubject.internalCompany` 数据库旧列保留便于回退，但不再作为日常维护、选择或验证规则；API 不再允许新写映射。
- 新迁移只解除旧任职公司代码 NOT NULL，不回填或重写真实员工、部门、主体、合同数据。实际生产迁移须在发布授权后备份执行。
- 回退边界：一旦新流程产生空旧代码，不能直接恢复要求该列非空的旧 API 或执行 SET NOT NULL。保留旧列不等于旧程序可安全回退；发布前须准备可读取空码的兼容回滚镜像，不能恢复整个数据库覆盖发布后业务。
- 旧导入当前关闭，保持关闭。遗留导入的组织建树分支继续只消费有效旧组织码，不能把空码默认到孚德；不得借本次统一重新开放导入。
- 原有入离职审核/到岗流程、档案直接生效、草稿并发与审计继续保留。
