# HRM 全功能与 100 人容量验收实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking. 只读场景盘点可并行，数据库与压力执行串行调度，不能用提高 Jest/Playwright workers 代替压测。

**Goal:** 用可复现的功能、并发和数据一致性证据回答“约 100 名员工能否日常使用、集中登录提交时要等多久”，优先定位用户反馈的登录、绩效入口和跨账号流转等待。

**Architecture:** 复用现有真实 HTTP/PostgreSQL 夹具和少量 PC/手机 Playwright 页面断言，新增受目标守卫保护的 k6 协议层负载。临时独占测试环境采用正式构建及同主版本数据库，只使用虚构资料；不压生产、不抢占共享固定预览、不复制生产库。

**Tech Stack:** NestJS、Prisma、PostgreSQL 14、Redis 7、MinIO、Vue 3、Element Plus、Playwright；拟用官方 k6 runner，执行前锁定版本及镜像摘要，不引入云端上传测试资料。

**Spec:** 用户 2026-11-26 请求“全功能压力测试安排一下，把我的疑虑打消”；约束见根目录 `AGENTS.md`、`docs/project-memory.md`、`docs/development-preview.md`。本计划不新增薪资、绩效或审批规则，也不授权生产发布。

## Global Constraints

- 权限来自明确能力、数据范围和任务快照，不能由姓名、岗位、角色标签猜测。
- 虚构身份、资料、工资、文件和审批源；不访问真实简历、工资明细或真实员工写接口。
- 钉钉、邮箱、AI、通知外送和日程使用测试替换且网络层禁外连；站内通知和业务状态仍由真实服务落库。第三方限流、真实扫码与网络容量另列，不能被本测试冒充验收。
- 不修改生产或钉钉配置；不重启、停止或清理 `kayford-deploy`、`hrm` 及不属于本轮的资源。
- 临时压力环境只监听 loopback，拥有独立数据库、角色、Redis、MinIO 桶及运行标识；不能只检查 URL 是 localhost 就判定安全。
- 原固定预览 `http://localhost:5173` 保留。压力不得指向该共享预览，也不能运行其重置/清表脚本。
- 不输出或持久化令牌、口令、完整手机号和工资内容；报告只存虚构标识、路由模板、计时和一致性计数。HAR/trace/请求体须脱敏，不能直接留存登录响应。
- 开始每批前现场重核源码、工作区、生产镜像、资源和并行任务；保留所有已有未提交工作。
- 测试缺陷与产品修复分开记录。没有新运行结果就写“未测”；不得将编译、单测数量或健康状态写成容量通过。

## Review Focus

1. 后端已流转但接收方页面没更新：同时记录提交落库、待办可查、页面可操作三个时间，不用手动刷新掩盖延迟。
2. 同一版本被多窗口/多人操作：一次生效、其他明确拒绝，本地输入不丢失，审计不重复。
3. 旧会话撤权或员工失效：排队写入和文件下载也要重新遵守权限，不能仅测菜单隐藏。
4. 假勤、解析、邮件任务中断：失败不能推进游标或被旧 worker 覆盖；重试不产生重复业务对象。
5. 同机资源争用：容量结果必须包含资源上限和生成器瓶颈；压测自身不得拖慢正在试用的生产。

### P2：100 人混合负载与集中峰值

**拟新增：** `scripts/capacity/scenarios/auth-scope.js`、`performance.js`、`personnel-recruitment.js`、`payroll-files.js`。共用少量鉴权/指标标签 helper，不重新实现调度器。

**工具依据：** k6 [scenarios](https://grafana.com/docs/k6/latest/using-k6/scenarios/) 控制不同业务负载，[thresholds](https://grafana.com/docs/k6/latest/using-k6/thresholds/) 明确达标/停止。版本在 P0 锁定，不能照最新文档臆造已安装能力。

- [ ] 各 scenario 先单用户一次：先验状态码、角色和数据变化，再加压。每个待写对象归属当前 VU/角色；重复和竞争留给 P3，不用随机撞库产生大量假失败。
- [ ] `baseline`：1 人，5 分钟，登录、列表、详情、保存、提交分组计时；随后执行 P1 浏览器测试获取端到端基线。
- [ ] `daily`：100 个有效登录身份，按用户思考间隔操作，活跃 VU 10 -> 30 -> 100，每档 5/10/15 分钟，档间等待后台队列归零且核对数据。一次只运行一个梯度，不在另一任务构建期间叠加。
- [ ] 混合业务初始配比：员工/主管绩效约 50%、人员资料 15%、招聘 15%、薪酬考勤 15%、目录/工作台 5%；每包同时包含列表/详情读取及合法状态写入，读写约 80:20。报告实际请求数/速率，不只报告计划 VU。
- [ ] `burst`：100 个不同身份在 10 秒内各真登录一次，进入工作台及绩效；另用 100 份独立可提交对象测试 10 秒内集中提交。两包均须计划 100/实际发起 100/合法业务成功 100；默认不重试，未启动、超时、意外拒绝和限流均不能计成功。含预期限流的保护性负向测试另开场景，不能用来抵扣正向成功分母。不要把 100 人日常使用说成人人每秒登录；不做真实账号口令探测。

## 预先设定的验收目标

以下是本轮拟采用的验收线，不是已经达到的 SLA；结果不达标就报缺陷，不能运行后降低阈值造绿。样本少时同时给样本数与最大值，不靠 p99 掩盖。

| 项目 | 验收线 |
| --- | --- |
| 正常混合负载普通 API | 读 p95 <= 1 秒/p99 <= 2 秒；登录和普通保存/提交 p95 <= 2 秒/p99 <= 4 秒，角色鉴权开销包含在内 |
| 集中登录/提交 | 分别报告峰值成功数、p95/p99；目标 p95 <= 5 秒、全部 <= 10 秒，无丢单、重复或不确定成功；不得拿 normal 平均值覆盖峰值失败 |
| 页面可用 | 本机正式构建冷进入主要页面目标 <= 3 秒，公网低频只读样本目标 <= 5 秒；冷/热缓存及设备单列。公网不做批量压测，外网容量仍不能据此证明 |
| 跨人流转 | 服务器提交后下一角色立即查询可见；活动页无强刷在 15 秒内出现可操作任务，回到页面 3 秒内重新核对；各阶段时间分别记录，不擅加产品轮询实现 |
| 批处理与文件 | 单列数据量、排队及完成时间、进度可见和取消/恢复；运行前用单用户基线固定各操作限时，不和普通 API 混算 |
| 正确性/安全 | 丢单、重复生效/占位/计发/扣缴、越权、泄密、静默覆盖、半提交均为 0；所有业务拒绝有准确反馈且可恢复 |
| 错误统计 | 意外 5xx/超时为 0；预期 401/403/409/限流独立计数并断言无副作用，不从报告里删除；正常业务的意外 4xx 同样失败 |
| 稳定性 | 无 OOM、死锁、持续连接/内存/队列泄漏；无资源保护停止。触发保护停止的档位标“未完成”，不能算通过 |
