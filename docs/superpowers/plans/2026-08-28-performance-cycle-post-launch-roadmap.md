# 绩效周期发起后工作流实施路线图

> 日期：2026-08-28
>
> 依据：[绩效周期发起后工作流设计](../specs/2026-08-28-performance-cycle-post-launch-workflow-design.md)
>
> 执行原则：六个阶段按顺序实施；每个阶段独立测试、独立提交、独立验收；全部阶段验收前不发布生产。

## 1. 为什么分阶段

现有系统以“一名员工 × 一个周期 × 一次评分 × 一个最终审批人”为主结构。确认后的方案新增月度记录、指标版本、人员变化、周期级审核批次、分管范围和结果修订。若把这些内容放进一次大改，会同时影响建表、发起、待办、评分、权限、报表和历史数据，无法定位问题，也无法安全回退。

本路线图把变化拆成六个连续阶段。阶段之间只通过已经明确的数据接口衔接，不在同一个提交中同时替换全部旧流程。

## 2. 历史兼容总原则

- 现有周期统一视为 `workflowVersion = 1`，继续走现有字段、接口和页面。
- 新流程使用 `workflowVersion = 2`，只影响新建且明确选择新流程的周期。
- `AssessmentTask` 继续作为“员工 × 周期”的参与任务，不拆成多条月度任务。
- 月度/整体评分使用新的期间记录，不覆盖现有 `IndicatorInstance`、`GradeResult` 和 `FlowRecord` 历史数据。
- 历史 `approverId` 继续表示原“最终业务审批人”，不迁移。
- 新流程全部验收通过前，生产环境不创建 `workflowVersion = 2` 周期。

## 3. 阶段顺序

### 阶段 1：评分频率、月度计划与发起快照

交付内容：

- 周期评分频率和固定“按周期审核”配置；
- 月度时间计划及特殊月份调整；
- 周期任务、考核期间、V1 指标版本壳和组织责任快照；
- 试用期员工和最高负责人在发起前正确排除/豁免；
- 创建、编辑、审核、发起检查和发起结果都能展示新配置。

验收结果：HR 可以创建季度/半年/年度计划并选择是否按月评分；发起后能看到正确的 3/6/12 个期间记录和责任快照，旧周期不受影响。

详细计划：[阶段 1 实施计划](./2026-08-28-performance-cycle-post-launch-phase-1-foundation.md)

### 阶段 2：月度自评、直属上级评分与周期汇总

变更设计：[月度复盘与评分一体化设计](../specs/2026-08-29-unified-monthly-review-and-scoring-design.md)。阶段 2 不再实现独立的“月度跟进”和“月度自评”两次填写，而是以一次“月度复盘并评分”任务同时形成进展与自评。

交付内容：

- V1 指标在目标确认后冻结；
- 月份按时间开放，逾期不关闭；
- 员工逐月一次完成进展复盘与自评；
- 直属上级逐指标评分并自动计算月度总分；
- PC 使用表格同屏填写，手机使用逐项卡片；
- 期间锁定、同周期月度选择器和分数可见提示；
- 有效月份等权汇总；
- 缺少主管正式评分时进入“收尾处理中”。

验收结果：一个季度周期可以从目标确认连续完成三个月评分并形成周期结果，现有绩效待办布局保持不变。

### 阶段 3：部门审核、HR 校准、分管总审核与最终审定

交付内容：

- 部门负责人周期级审核；
- HR 校准结果快照；
- 李宏、倪靖、郭志浩分管范围配置；
- 分管范围审核和定向退回；
- 李宏公司最终审定及发布；
- 李宏本人最高负责人豁免、部门负责人不得审核本人、李宏分管范围不重复审批；
- “结果审核”接入现有团队绩效待办。

验收结果：一个完整周期按照确认链路逐级流转，每一级只能看到和处理自己的范围。

### 阶段 4：员工结果确认、旧入口收口与通知日志

交付内容：

- 最终结果发布后员工只显示“确认”；
- 逾期不关闭、不自动确认，HR 可提醒；
- “结果公示”并入最终审定发布；
- “申诉管理”只保留历史只读；
- 审批日志跟随表单和结果详情展示；
- 责任变化、退回、临期和逾期通知。

验收结果：员工从绩效待办查看并确认正式结果，新流程不再出现申诉理由或重复公示入口。

### 阶段 5：人员变化、调岗交接与月份免评

交付内容：

- 转正加入当前周期的 HR 确认；
- 离职最后有效月；
- 长期病假、产假、停薪留职和复工任职状态记录；
- 整月/部分月免评建议与 HR 管理员确认；
- 组织调岗立即或指定未来月份生效；
- 新旧直属上级按是否正式评分完成任务交接；
- 全部 HR 查看调岗历史，业务人员只看交接结果。

验收结果：人员变化不会产生零分或错误逾期，主管变化不会覆盖已提交月份。

### 阶段 6：结果更正、历史版本与报表

交付内容：

- 员工或直属上级发起往月结果更正；
- HR 管理员审批；
- 旧指标、评分、周期结果和确认记录作废归档；
- 定向重新评分和 HR 更正复核；
- 员工重新确认；
- 报表默认使用最新有效版本并可查看历史；
- 周期保持“已结束”，增加“结果更正中”标签。

验收结果：单名员工单个月份可被安全重评，其他员工和周期主状态不受影响。

## 4. 设计覆盖矩阵

| 设计内容 | 实施阶段 |
| --- | --- |
| 保留绩效待办布局 | 2、3、4 |
| 月度/周期评分频率 | 1 |
| 月度默认时间和特殊月份 | 1、2 |
| 指标版本与生效月份 | 1、2、6 |
| 月度自评和主管逐指标评分 | 2 |
| 等权平均、缺失不记零 | 2 |
| 试用期、最高负责人豁免 | 1 |
| 转正、离职、长期缺勤 | 5 |
| 调岗和直属上级交接 | 5 |
| 部门审核、HR 校准 | 3 |
| 分管总、李宏最终审定 | 3 |
| 员工只确认、不申诉 | 4 |
| 结果更正和历史归档 | 6 |
| 状态、提醒和日志 | 1 至 6 分阶段补齐 |
| 报表最新有效结果 | 6 |

## 5. 每阶段共同验收门槛

每个阶段必须同时满足：

1. 对应 API 单元测试通过；
2. Prisma 迁移可在空库和已有数据副本上执行；
3. Web 类型检查通过；
4. 对应 Playwright 合同场景通过；
5. `workflowVersion = 1` 回归场景通过；
6. 新增写接口有责任人校验和数据范围校验；
7. 关键操作写入审计/流程日志；
8. 不发布生产，除非用户明确下达“发布”。

## 6. 最终端到端验收账号

最终验收必须准备并确认以下受控账号确实进入测试周期范围：

- 普通员工；
- 普通员工的当前直属上级；
- 部门负责人；
- 周期 HR 负责人；
- HR 管理员；
- 倪靖或郭志浩中的一个分管总；
- 李宏；
- 调岗后的新直属上级。

能够登录不代表进入了周期范围。验收前必须检查参与名单、责任快照、期间记录和待办归属。
