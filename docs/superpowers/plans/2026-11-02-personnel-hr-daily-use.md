# 员工档案日常使用优化交接与实施计划

> **For agentic workers:** Use superpowers:subagent-driven-development or superpowers:executing-plans for each assigned task. Checkboxes record verified work, not deployment or business acceptance.

**Goal:** 让约100人公司的HR从电子花名册迁移到系统后，能够信任档案、完成办理，并清楚每日应处理的事项。

**Architecture:** 保持NestJS/Prisma模块化单体和Vue 3/Element Plus前端。复用现有员工档案、任职、合同、草稿、能力授权、审核和审计服务。人事初始化与智能体提案进入同一人工确认流程，不建设第二份人员主库或平行审批。

**Tech Stack:** NestJS、Prisma、PostgreSQL、Vue 3、Element Plus、Jest、Playwright。

**Spec:** 2026-11-01本会话的HR第一天实测报告；2026-11-02用户要求交给技术架构师采取优化。本文将业务建议转成工程任务，未明确的提醒策略、数据导出边界不作为已批准政策。

## 后续建设清单

### 第二批：日常HR工作入口与可交付花名册

1. 先在既有UsersService查询投影、DTO和API中补公司/日期过滤，再建设花名册与最小字段白名单导出。公司来自当前已批准任职的`companyText/contractSubjectId`，不能用部门组织归属替代。列表与导出共用同源过滤及数据范围，不能只在前端本页过滤。
2. 花名册突出合同主体、部门、岗位、用工类型、入职日期和状态；账号权限、钉钉绑定按需展开。导出字段与数据范围同时校验；身份证、银行卡、薪酬和联系方式不因新增导出按钮而自动开放。验收过滤结果、分页全集、权限拒绝、中文列名和手机操作。
3. 先把既有来源问题整理成可分页的全局待核清单，再聚合今日待办。工作台按能力只读组合待补资料、草稿、待审核和已有入职/合同/转正事项；每个数字可进入同角色、同口径清单，读取失败不能显示为零。转正沿用其已有授权范围，不直接套用档案全量查看范围。
4. 合同到期台账复用合同记录；提前提醒窗口、接收人、发送渠道另行明确后实施，不将日期状态展示等同于自动通知。

### 第三批：统一待核清单的智能体提案接入

1. 在第二批同一待核清单上继续接入提案，复用当前来源问题、申请草稿、审核和审计，展示原值、建议值、来源、待确认原因和处理状态，不再新建一份确认页。
2. HR处理后准确消项，草稿与正式员工分别计数；冲突不得被“补建任意合同”误消除。
3. 钉钉、千问办公、Work Buddy等渠道只产生同一规范提案，HR在同一入口人工确认；重复投递、旧版本提案和身份歧义不得直接写正式档案。
4. 与“Agent 助手”会话保持既有分工：渠道整理与接入归智能体侧，权威档案、版本校验、确认、审核和审计归HRM。
5. 当前ArchiveAssistant属于姚瑶（312）的测试样例、仅草稿试点。正式员工提案和多渠道接入属于后续契约建设；本清单不把它描述成已具备正式写档案能力，也不扩大现有试点名单。
