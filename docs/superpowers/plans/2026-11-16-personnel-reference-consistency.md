用户已授权完整修复本轮审计所列问题，并确认公司权限口径及修改后上线。继续当前公司统一工作区，不覆盖其他批次修改；不猜测回填正式历史数据。完成严格验证后合并、推送并只发布相关 API/Web。

## 实现边界

1. 转正：新提交使用本次有效任职的花名册直属主管；已提交申请保持办理人快照。批准更新对应任职和当前账号投影，后续刷新不能退回试用期；防止旧申请影响再次入职，事务失败不能部分落库。
2. 岗位：新入职正式提交必须选择启用岗位；草稿仍可不完整。正式档案无关编辑允许保留未关联的旧岗位名称，真正换岗或重新选择时必须用目录。名称、职系由服务端按目录选取，不能被客户端伪造。
3. 基础资料：受控字段采用稳定 ID 加历史名称快照。接口采用 `字段名Id`，例如 `educationId`、`jobGradeId`；EmployeeProfile 存 educationId/maritalStatusId/politicalStatusId/householdTypeId/emergencyContactRelationId，EmploymentRecord 存 jobGradeId/jobFamilyId/workLocationId，Position 存 jobFamilyId。新增可空关联列，不按名字批量回填真实历史资料。
4. 新选值必须校验目录存在、类型正确且启用，由服务器写入名称。未改变的正式历史 ID/名称可保留，包括目录改名、停用或旧值没有 ID；草稿不能作为豁免校验的正式基线。清空必须同步清空 ID 与名称，不接受类型错配、伪造名称或仅凭名字猜关联。
5. 工作地点、职系纳入同一套前后端校验。开户银行、合同名称继续是允许手填的建议项目录。
6. 公司权限：用户已选择按员工所属公司统一，以当前正式有效任职的 contractSubjectId 为准，无 ID 不猜测匹配；HR 管理员全范围与本人被分配申请保持不变。列表、详情、待办、办理与通知使用同一当前公司来源；不额外扩大办理角色权限。
7. 旧申请的姓名/路径推断不得在审核时自动认人；缺少可靠 ID 时给字段级提示由维护者明确选择，历史已完成记录保持只读。

## 并行任务与文件所有权

- A：转正服务、转正测试。先复现批准后刷新回退，再修复并测试主管不同、历史申请、事务一致性、延后生效日期。公司权限相关通知与主任务协调。
- B：API 基础资料、岗位、档案/入职/审核服务、DTO、Prisma 模型和新增迁移、对应测试。提供稳定 ID 契约；覆盖目录改名/停用、草稿、清空、伪造、历史保留及岗位必选。
- C：Web 资料选择组件、资料 API 类型、所有人员/岗位表单与 payload、针对性 Playwright。保留名称快照，同时传 ID；新入职移除自由岗位录入，提供岗位管理入口。
- 主任务：权限口径、整合、完整测试、独立评审与固定预览。共享文件修改先沟通，不重写另一人的文件。

## 验证

严格档：各任务先写能复现缺陷的测试；最终 API 全量测试与构建、Web 类型检查/生产构建、直接覆盖字段选择和草稿恢复的 PC/手机 Playwright。隔离 PostgreSQL 迁移及真实接口验证转正批准后刷新、主管办理人、目录 ID 持久化、改名后无关编辑不重写历史、权限排除与允许路径。沿用已有隔离集成工具与固定预览，不导入真实资料、不触发外部通知。

## 评审重点

- 同一个人两次任职、未来生效日、已离职后旧申请批准。
- 新入职/再入职/正式档案/任职记录/旧草稿的规则一致。
- 按目录 ID 关联而非按名称暗中匹配，保留历史不会导致新输入绕过目录。
- 前端 ID 与名称不能因清空、切换、异步目录刷新而分离。
- HR 公司范围与被分配申请范围分开，缺资料时不扩大授权。
