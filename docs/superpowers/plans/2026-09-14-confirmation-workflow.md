# 员工发起转正申请 Implementation Plan

**状态：** 实施中。薪酬字段和提交前办理人配置方式待业务答复；不得据此自行扩大字段可见范围。钉钉 AI 纪要明确不在本轮。

**目标：** 以员工本人申请、花名册直属主管评价、指定 HR 记录线下评议、指定公司审批人最终决定的单一流程替代旧的 HR 代填转正申请。正式绩效保持独立且只作为权限内的只读参考。历史试用期评分和旧转正记录保留只读。

**代码边界：** `api/src/confirmation`、必要的 Prisma 增量迁移、`web/src/views/confirmation`、菜单/业务能力和直接相关测试。员工档案是人员及直属主管的权威来源；任何角色都不以钉钉通讯录确定。只在隔离工作区开发，不修改生产数据或发布。

## Task 1：数据与版本边界

- [ ] 审视存量数据结构，新增 `workflowVersion`（存量默认旧版）和新流程所需字段/附件/操作轨迹；迁移只增不删，不将旧 HR 草稿视作员工提交。
- [ ] 新流程进行中申请的唯一性用数据库约束保障，并覆盖并发创建。
- [ ] 给员工提交内容、主管评价、HR 结论、公司决定、退回补充与重新提交留下可审计的逐次事件，旧意见不得伪装成新版本批准。
- [ ] 日期使用 `date` 语义：HR 拟生效日期由公司审批人确认，同意后在同一事务写申请与花名册实际日期/正式状态；不得静默用审批当天。

## Task 2：服务端流程与权限

- [ ] 先写失败的业务用例：本人可建/保存/提交、他人和正式员工不可代建；直属主管来源于 HRM 档案；无有效审批链时能保存但不能提交。
- [ ] 实现员工草稿/提交；主管独立填写评价和建议，不能直接终止申请；HR 填评议结论、可选会议日期、文字和/或附件、拟生效日期；无结论不得送公司审批。
- [ ] 实现指定人员按状态处理、退回员工补充与重新流转、最终同意/不同意。校验操作者、当前状态与数据版本；不可重复审批。
- [ ] 服务端按字段过滤：内部评议附件仅指定 HR 办理人与公司审批人可见；员工与直属主管看到各自许可的内容；薪酬和未发布绩效结果不得因转正审批泄露。
- [ ] 附件上传和下载都校验该申请的指定身份，不能复用对所有登录者开放的通用 `/storage/download` 下载路径。
- [ ] HR 管理授权与被指定为 HR 办理人分开；系统管理员身份本身不赋予公司审批权。读写均受同一数据范围限制。
- [ ] 对存量旧版申请保持只读，保留原始审批、薪酬和试用期评分历史；新流程不生成第二套试用期分数。

## Task 3：前端菜单与页面

- [ ] 入口收敛为“我的转正申请 / 转正待办 / 转正管理”；旧试用期评分入口改历史只读入口，防止再发起独立评分。
- [ ] 员工页可发起、保存、提交、查看退回原因并修改重提；使用安静紧凑的工作台样式、字段下方校验和明确的下一步。
- [ ] 待办页按本人指定环节显示动作：主管评价、HR 记录评议和拟日期、公司审批人确认日期与决定。
- [ ] 管理页展示临期、逾期、未申请与各环节进度，只给授权 HR 配置/调整审批链；不得代员工写小结或代公司做决定。
- [ ] 绩效参考只读按现有绩效接口的本人可见范围展示，未发布等级不出现；无绩效记录不阻断申请。
- [ ] PC 与手机分别核对长文本、附件、列表和操作区；保持周期与计划页面的密度、层级和交互语言。

## Task 4：验证与交付

- [ ] API 相关用例先红后绿；共享流程/权限/模型改动扩大到 API 全量测试，并运行 `npm run build`。
- [ ] Web 运行 `npm run type-check` 与直接覆盖员工、主管、HR、公司审批人的 Playwright 路径；测试页面实际显示与服务端字段权限一致。
- [ ] `git diff --check`，仅核对本任务文件；交付时分别说明本地代码、提交、上线和真实业务验收状态。
