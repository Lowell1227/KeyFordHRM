# 孚德绩效系统 · 端到端验收清单（完整季度周期）

> 用法：按顺序逐步操作，每步对照 ✅ 预期。对不上的把「步骤号 + 实际现象 + 浏览器控制台/网络面板报错」发给 PM。
> ⚠ 标记的是最容易踩、且静态检查查不出来的点。

---

## 0. 前置环境

- [ ] 基础设施起来：`docker compose -f docker-compose.yml -f docker-compose.dev.yml up`（postgres + redis + minio 三个 healthcheck 通过）
- [ ] 后端：`cd api && npm i && npx prisma migrate deploy && npm run seed && npm run start:dev`
  - ✅ 出现 `Nest application successfully started` + `🚀 ... API 已启动`
  - ✅ `curl http://localhost:3000/api/v1/health` → `{"code":0,...,"data":{"status":"ok","db":"ok"}}`
- [ ] 前端：`cd web && npm run dev`，`VITE_API_BASE_URL` 指向后端（如 http://localhost:3000）

### 测试账号与数据（关键，缺了后面跑不动）
绩效流程要多个角色协作，至少准备：
- [ ] **system_admin / HR** 各 1（做管理后台与校准/公示）
- [ ] **员工 E** 1（被考核对象）
- [ ] **主管 M** 1（必须是 E 的「直属主管 directManagerId」）
- [ ] **部门负责人**（E 所在部门的 leader，做部门复核）
- [ ] **审批人 A**（设为 E 所在部门的「审批人 approver_id」，通常是分管总/VP）

> ⚠ 用户正常从钉钉同步。若没接钉钉，需在 seed 里造测试用户，或先跑一次钉钉同步。**E 必须有 directManagerId；E 的部门必须设了 approver_id**——否则主管评分、审批两步没人能做。

## 1. 主数据准备（用 HR / system_admin 登录）

- [ ] **1.1 指标库** `/indicators`：建至少 4 个指标，类型各覆盖 `kpi / attitude / bonus / penalty`（可再加 1 个 `veto`）
  - ✅ 列表能看到；可「下载导入模板」「导出」（下载到 xlsx）
  - ⚠ 试一次「导入」：上传刚下载的模板，应返回成功/失败条数
- [ ] **1.2 模板** `/templates`：新建模板，配 2 个维度
  - KPI 维度（权重 60%）下 2 个指标（各 50%）
  - 态度维度（权重 40%）下 1 个指标（100%）
  - 再加 1 个 bonus 项
  - ⚠ **故意把 KPI+态度权重设成 ≠100%**：应被拦截、不能提交（验决策4 权重校验）；改回 100% 才能存
- [ ] **1.3 部门审批人** `/users` → 部门 tab：给 E 所在部门「设审批人」= A
  - ⚠ 该操作**只有 system_admin 看得到**；HR 登录看不到「设审批人」按钮（验决策3 门控）
- [ ] **1.4 直属主管** `/users` → 用户 tab：给 E「设主管」= M（若同步已带则跳过）

---

## 2. 建周期 + 发起（HR / system_admin）

- [ ] **2.1 建周期** `/cycles` → 新建：填名称/类型/起止日/各节点截止日/四等级上限（如 A20% B30% C40% D10%）
  - ⚠ **公示可见字段**：确认「绩效系数」默认**未勾选**（员工默认不可见，D18）。其余按需勾。
- [ ] **2.2 发起** 列表里点「发起」（仅草稿态可点）→ 二次确认
  - ✅ 成功提示「已开始生成全员任务」，周期状态推进
  - ⚠ **豁免名单**：在岗天数 < 周期总天数 ⅓ 的人（含期中离职），任务应标记为「豁免」。准备 1 个临近入职/离职的人验证。

---

## 3. 指标确认（用员工 E 登录）

- [ ] **3.1** `/tasks` → 进入自己的任务详情
  - ✅ 看到指标快照（名称/权重/维度/评分标准）
- [ ] **3.2 退回**：点「退回」填意见
  - ⚠ **关键**：退回后任务应回到「待制定/退回」态，**不能变成"已确认"**（这是返工修过的 bug，必须确认真退回了）
- [ ] **3.3 确认**：重新点「确认指标」→ 任务进入自评态

---

## 4. 自评（员工 E）

- [ ] **4.1** 自评阶段逐指标填 自评分 + 说明，填自评总结，提交
  - ✅ 提交成功，任务进入「主管评分」
  - ⚠ 此时页面**不应出现任何主管评分/总分/等级**（公示前遮罩，D18）
- [ ] **4.2 豁免任务**：打开一个豁免人的任务 → 应只读、显示豁免原因、无录入控件

---

## 5. 主管评分（用主管 M 登录）

- [ ] **5.1** `/manager/scoring`：只看到 `managerId = 我` 的待评分任务
- [ ] **5.2** 进入评分：逐指标打主管分 + 评语
- [ ] **5.3 加/减分**：给 bonus 项加明细（如 +5），penalty 减（如 -2）
- [ ] **5.4 一票否决**（若有 veto 指标）：勾选 + 填原因，应有二次确认提示「等级将直接评为 D」
- [ ] **5.5** 提交 → 任务推进
  - ⚠ **不要在前端算总分**；总分以后端为准（提交后用后端返回刷新）

### 🧮 算分专项（决策4）——用一个具体例子核对
设：KPI 维度权重 0.6，指标A 权重0.5 主管分90，指标B 权重0.5 主管分80；态度维度权重0.4，指标C 权重1.0 主管分70；bonus +5，penalty −2。
- KPI 维度 = (90×0.5 + 80×0.5) × 0.6 = 85 × 0.6 = **51**
- 态度维度 = 70 × 0.4 = **28**
- 小计 = 79；+bonus5 −penalty2 = **82**
- [ ] ✅ HR 校准台看到的「计算分」应 = **82**（容差±0.01）
- [ ] ✅ 若该人被一票否决 → 原始等级直接 **D**（不看分数）

---

## 6. 部门复核（用部门负责人登录）

- [ ] **6.1** 进入待复核任务，「通过」或「退回」
  - ✅ 通过→进入 HR 校准；退回→回主管评分（按你们流程定义）

---

## 7. HR 校准（用 HR / system_admin 登录）

- [ ] **7.1** `/calibration`：选周期 → 看候选名单（姓名/部门/计算分/原始等级/主管分）
  - ⚠ **全程无「绩效系数」列**（D13）
- [ ] **7.2 强制分布预警**：把多人调成同一高等级，使某级超上限
  - ✅ 该等级**标红告警**，提交时弹「超上限，是否仍要提交」——但**仍可提交**（不强制阻断）
- [ ] **7.3 改判**：调某人 calibratedGrade + 填校准说明
- [ ] **7.4 一票否决**：勾选 → 等级强制 D
- [ ] **7.5** 提交校准 → 成功，名单刷新

---

## 8. 审批（用审批人 A 登录）

- [ ] **8.1** `/approval`：选周期
  - ⚠ **只看到「我能审」的任务**（后端按 approver_id 过滤）；用一个非审批人账号登录，列表应为空或无入口
  - ⚠ 列表**无绩效系数列**
- [ ] **8.2 批量通过**：勾选多条 → 批量通过 → 二次确认
- [ ] **8.3 单条退回**：填意见（必填）→ 退回，任务回到 HR 校准

---

## 9. 公示（用 HR / system_admin 登录）

- [ ] **9.1** `/publish`：选周期 → 看待公示任务（已审批的）
- [ ] **9.2** 多选 → 「发布公示」→ 二次确认（对外动作）
  - ✅ 成功，已公示项置灰
  - ⚠ 若选到**未审批**的任务发布 → 后端应拒（报错提示），不应公示成功

---

## 10. 员工确认 + D18 遮罩复验（用员工 E 登录）

- [ ] **10.1** `/tasks` → 打开已公示任务
  - ✅ **现在**能看到总分/等级（按周期 publishVisibleFields 配置）
  - ⚠ **绩效系数**：若 2.1 没勾系数，这里**不应出现系数**；勾了才显示
  - ⚠ 用浏览器开发者工具看 DOM/接口返回：未配置可见的字段**不应在数据里下发**（不是 CSS 藏）
- [ ] **10.2** 点「确认结果」→ 成功，任务进入已确认

---

## 11. 关周期 + 归档

- [ ] **11.1** 关周期：MVP 由 scheduler 自动跑（`0 3 * * *`，过公示截止日后）。要立即验，可临时改 cron 或在数据库把公示截止日改到过去再等一轮。
  - ✅ 周期 → closed；每个完成任务在 `performance_archive` 生成 1 条（grade + totalScore）
  - ⚠ 无等级的异常任务应**跳过归档**、不应硬塞 'D'（返工项）

---

## 12. 申诉记录（用 HR / system_admin 登录）

- [ ] **12.1** `/appeals` → 「录入申诉」：选一个已公示任务 + 事由 → 提交
- [ ] **12.2** 详情里处理：
  - 「维持原判」→ 只填处理说明
  - 「改判」→ 必填新等级；提交后该任务的校准等级应随之更新、档案同步
  - ⚠ 详情**不显示绩效系数**；**没有**部门处理/撤回/二次申诉等流程入口（决策5：纯记录）

---

## 13. 报表核对（HR 全部可见 / VP 仅汇总）

- [ ] **13.1** `/reports` 用 HR：汇总（等级分布图 + 部门维度）、进度、A/D 名单、导出 Excel、员工档案趋势
  - ⚠ **全程无绩效系数**（D13）
- [ ] **13.2** 用 VP 账号：**只看到「汇总」tab**，看不到进度/名单/档案/导出
- [ ] **13.3** 对照：报表里的等级分布人数应与 7.x 校准结果一致

---

## 14. 催办限频（可选专项）

- [ ] 触发同一节点的催办两次（或等 scheduler `0 9 * * *`）
  - ✅ 同一人同节点**每天最多催 1 次**（D19）；已完成该节点的人**不应**收到催办（返工项）

## 验收判定
- 上述步骤全部 ✅ → 端到端通过，MVP 可进入试运行。
- 任一 ⚠ 对不上 → 记下「步骤号 + 实际现象 + 报错」发 PM，定位是前端/后端/数据问题后开返工卡。
