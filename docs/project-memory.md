## 1. 如何使用本文

本文服务于后续接手本项目的智能体、开发者、测试人员和项目负责人。

- “长期规则”是已经反复确认的业务或工程边界，除非用户明确改变，不应自行推翻。
- “状态快照”只代表文档更新时间，开始新任务时必须重新检查代码、Git、数据库、容器、钉钉权限和正式页面。
- “规划中”不等于已实现，“代码存在”不等于已上线，“线上可打开”不等于业务验收完成。
- 真实员工数据、密码、AppSecret、Token、薪资数据和完整个人联系方式不得写入本文。

## 2. 项目目标

HRM 是杭州孚德品牌管理有限公司的人事与绩效管理系统。建设目标不是复制 Moka、合思或钉钉全部能力，而是：

1. 以公司自己的员工档案和花名册为主数据。
2. 复用钉钉的登录、入口和适合的通用办公能力。
3. 自建与公司制度紧密相关的绩效、人事档案、组织关系和后续薪酬专业能力。
4. 让员工、直属上级、HR、审批人和系统管理员在同一套数据上协作，并且权限、流程和留痕可解释。
5. 先形成可供一线真实使用和反馈的闭环，再逐步扩充模块。

## 3. 建设阶段回顾

### 阶段一：工程与部署基础（2026-06）

- 建立 NestJS、Prisma、Vue 3 和 Docker Compose 的单仓库基础。
- 建立可重放数据库迁移、生产构建和换机运行说明。
- 接入钉钉扫码登录、回调和外部身份绑定。
- 建设部门负责人、审批继承、指标、模板和基础绩效数据结构。

这一阶段的主要经验是：认证接通只是入口完成，组织主数据、权限和业务流仍需在 HRM 内明确建模。

### 阶段二：绩效工作台与主管协作（2026-08 上旬）

- 按成熟系统参考图重构绩效工作台、目标地图、目标跟进和绩效待办。
- 建设主管团队视图、目标审核、上级评价、绩效面谈、改进计划等协作入口。
- 将系统菜单从功能堆叠调整为工作台、绩效、人员、招聘、薪酬、系统管理等业务域。
- 引入指标可见范围、目标对齐和基于业务关系的动态能力。

这一阶段的主要经验是：主管权限不能仅由一个静态角色决定，必须结合员工直属关系、周期任务和数据范围。

### 阶段三：人员主数据与发布治理（2026-08 中下旬）

- 明确花名册和 HRM 员工档案为组织人员权威来源，停止钉钉组织树反向覆盖。
- 建设组织视图、人员名册、岗位目录、员工档案维护和变更审核。
- 梳理岗位、系统权限、直属主管、组织负责人和审批人的区别。
- 增加钉钉登录兼容、首次加载、跨组织授权和错误提示方面的修复。
- 建立更严格的生产预检、备份、回滚镜像、精确服务替换和外部验收流程。

这一阶段的主要经验是：界面上相似的“负责人/主管/审批人”如果不解释作用，会让管理员无法判断自己在设置谁的什么权力。

### 阶段四：周期化绩效闭环（2026-08 下旬至 2026-09）

- 完善考核周期、参与范围、排除人员、启动前检查、目标制定和目标确认。
- 强化正式指标基线、指标版本、可见范围和公司到个人的目标对齐地图。
- 将目标进展、月度员工自评、月度直属上级评价和周期汇总连成一条业务链。
- 增加月度整体 A/B/C/D 等级，分数与等级保持独立，末月直属上级等级作为进入后续校准的初评依据。
- 持续压缩重复提示，统一表单、详情抽屉、操作历史和移动端体验。

这一阶段的主要经验是：绩效状态必须来自真实月度记录和流程条件，不能只靠一个笼统任务状态推断。

## 4. 已确认的架构决策

### D-001：保持模块化单体

当前系统继续采用模块化单体，不拆微服务。

原因：

- 目标、评价、算分、校准、审批、发布和申诉共享大量事务数据。
- 权限和审计必须跨模块保持一致。
- 当前团队和系统规模更需要快速迭代、简单部署和统一排障。
- 过早拆分会引入分布式事务、接口版本、链路追踪和运维成本。

重新评估微服务的触发条件：独立团队长期负责、独立扩缩容明显、数据生命周期必须隔离、模块契约稳定，或单体已形成可测量的可靠性瓶颈。

### D-002：HRM 员工档案是主数据

公司、部门、人员、岗位、直属主管和任职状态以 HRM 员工档案及经确认的花名册为准。钉钉登录只建立外部身份到 HRM 用户的绑定，不得静默覆盖人事主数据。

### D-003：钉钉与 HRM 各司其职

| 能力 | 首选归属 | 说明 |
| --- | --- | --- |
| 企业入口、扫码登录、身份授权 | 钉钉 | HRM 保存外部身份绑定 |
| 通讯录展示 | 钉钉 | 不作为 HRM 主数据写入源 |
| 通用 OA 申请、考勤、消息、待办 | 钉钉 | HRM 按需读取结果或写入待办 |
| 员工档案、任职、合同、组织关系 | HRM | 经审核后成为正式记录 |
| 绩效周期、指标、目标、评价、校准 | HRM | 公司专属规则和审计 |
| 薪酬台账、调薪、专业分析 | HRM 规划 | 不采购 Moka/合思，需求先打磨 |
| 通用报销审批 | 钉钉 OA 优先 | HRM 不重复建设通用报销引擎 |

### D-004：角色、关系和权限解耦

| 概念 | 解决的问题 | 是否自动授予其他能力 |
| --- | --- | --- |
| 岗位 | 员工承担什么工作 | 否 |
| 系统权限 | 能否管理系统或 HR 数据 | 否 |
| 直属主管 | 谁管理和评价该员工 | 产生相应团队业务能力 |
| 组织负责人 | 谁负责部门及组织范围 | 不自动成为所有人的直属主管 |
| 上级审批人 | 谁处理指定审批环节 | 不自动获得员工管理权 |
| 绩效直属上级快照 | 周期内谁负责该任务 | 周期启动后保持稳定 |

页面和接口都应使用这些完整名称，避免统一写成“主管”或“负责人”。

### D-005：版本与发布分离

- 当前源码产品版本为 0.8，包版本为 0.8.0。
- 版本号提交、代码推送、生产部署和业务验收是独立事件。
- 系统概览中的版本显示只有重新发布 Web 后才会变化。

### D-006：验收证据分层

统一使用以下状态：

1. 已规划：仅有需求或设计。
2. 已实现未提交：工作区存在代码。
3. 已提交未推送：本地 Git 有提交。
4. 已推送未上线：`origin/main` 已包含提交。
5. 已上线未验收：生产资源已更新并通过技术检查。
6. 已验收：目标业务角色完成真实流程并确认结果。
7. 部分实现或暂缓：必须说明可用范围和缺口。

## 5. 当前技术结构

### 后端

- NestJS 应用，按业务域划分模块。
- Prisma 管理 PostgreSQL 数据模型和迁移。
- Redis 用于缓存或任务协作能力。
- MinIO 用于文件存储。
- 关键模块包括认证、用户、部门、岗位、员工档案、周期、任务、指标、目标、月度评价、校准、审批、发布、申诉、面谈、改进计划、试用期与转正、报表、通知、审计和存储。

### 前端

- Vue 3 + TypeScript + Element Plus。
- 路由和菜单根据系统角色、HR 能力和动态业务能力共同过滤。
- 主要业务域包括工作台、绩效、人员、招聘（暂缓）、薪酬（暂缓）和系统管理。
- 绩效工作台同时承担个人任务和团队任务，依靠业务关系决定可见内容。

### 部署

- Docker Compose 运行 PostgreSQL、Redis、MinIO、API 和 Web。
- 生产项目名历史上使用 `kayford-deploy`。
- 正式入口历史上使用 `https://1260cw31az927.vicp.fun`。
- 这些名称和地址属于易变化事实，发布前必须重新检查。

## 7. 绩效业务主链

推荐用下面的业务顺序理解系统：

`周期与范围 -> 模板与指标 -> 目标制定 -> 直属上级审核 -> 月度进展 -> 员工月度自评 -> 直属上级月度评价 -> 周期汇总 -> HR 校准 -> 上级审批 -> 结果发布 -> 申诉/面谈/改进`

关键约束：

- 周期启动前确认参与人、排除人、模板、时间和主管关系。
- 启动时冻结任务所需的主管、指标和模板快照。
- 正式指标基线与日常进展记录分开，进展更新不能污染指标版本历史。
- 员工自评和直属上级评价分别记录，不应互相代填。
- 月度整体等级由评价人选择，分数与 A/B/C/D 不自动换算。
- 后续组织层面控制等级分布，不强制把所有部门的分数尺度视为一致。
- 校准应同时提供全局分布、部门比较和个人评价依据。

## 8. 权限排查顺序

出现“看不到团队”“能看不能操作”“状态不对”时，按以下顺序排查：

1. 当前登录身份是否绑定到正确 HRM 用户。
2. 用户是否在职，员工档案和任职记录是否有效。
3. 直属主管、组织负责人、审批人是否设置在正确对象上。
4. 当前考核周期是否包含该员工。
5. 任务是否冻结了正确的绩效直属上级和审批人。
6. 动态业务能力和后端数据范围是否包含该动作。
7. 前端路由和按钮是否正确反映后端权限。
8. 使用真实请求和真实账号验证，不能只看数据库字段或菜单。

## 9. 需求打磨经验

- 每次只聚焦一个主题，先问真实工作怎么做，再设计页面。
- 先画清角色协作和状态流，再讨论字段和按钮。
- 明确正常流程后，再补调岗、离职、代理审批、跨部门、延期、撤回和并发等例外。
- 对成熟产品截图，应提取信息架构、列表密度、展开方式和操作节奏，不复制其品牌、无关功能或隐藏规则。
- 钉钉能满足的通用审批不重复造轮子；HRM 只建设需要公司专属数据和规则的部分。
- 薪酬、招聘等敏感大模块必须完成业务访谈、权限设计、审计和验收标准后才能进入开发。

## 10. UI 建设经验

- 业务系统第一屏应是可操作工作台，不是营销首页。
- 主管需要先看到团队待办和风险，再进入单个员工详情。
- 指标列表使用紧凑摘要，点击后展开描述、评分标准、进展和历史。
- 筛选应支持部门与员工，并明确当前数据范围。
- 相似概念必须在副标题中直接说明作用，不能靠用户猜测。
- 弹窗标题和字段需明确当前编辑的是哪名员工，以及角色设置作用于员工还是所选主管。
- 移动端不是桌面页面缩小版；需要重新安排列表、筛选、详情和底部操作。
- 真实页面验收必须检查加载首屏、回调后状态刷新、长文本、空状态和弱网络。

## 11. Git 与多智能体协作经验

- 本项目长期存在多任务并行和多个 worktree。任何任务开始和结束都要检查工作区归属。
- `git branch --no-merged main` 只能说明拓扑，不能说明分支值得合并；还要使用 `git cherry` 和差异检查识别重复或过时方案。
- 同一目录的智能体可能把业务提交直接推入 `main`，项目经理应先查提交图，避免制造无意义的 merge commit。
- 脏工作区中使用精确 `git add -- <files>`，提交前列出暂存与未暂存文件。
- 不清理来源不明的目录和 worktree，不强制删除含未提交工作的路径。
- 推送失败先判断网络、凭证或远端推进，不使用强推作为默认恢复方式。

## 12. 发布与回滚经验

### 发布前

1. 用户已明确授权上线。
2. `HEAD`、`origin/main` 和目标提交清楚。
3. 确认本次发布 API、Web 或两者。
4. 检查数据库迁移状态和真实生产数据库目标。
5. 备份数据库并标记当前镜像回滚点。
6. 确认测试快捷登录及演示数据开关符合环境要求。

### 发布中

- 只构建和替换必要服务。
- 先执行兼容迁移，再切换应用。
- 不用新镜像覆盖唯一回滚标签。
- 不在命令输出中打印敏感环境变量。

### 发布后

1. 外部 `/api/v1/health` 返回成功且数据库正常。
2. Prisma 显示迁移已应用。
3. 正式页面资源来自目标构建。
4. 原问题路径通过真实角色验证。
5. `ENABLE_TEST_QUICK_LOGIN=false`，除非处于明确受控验收窗口。
6. 记录提交、容器、备份、回滚点和剩余风险。

## 13. 反复出现的问题与教训

### 问题一：把钉钉组织关系当成 HRM 权限

教训：钉钉部门主管、HRM 直属主管、系统角色和周期任务主管不是同一字段。先确定业务关系，再推导权限。

### 问题二：登录成功但首屏不完整

教训：OAuth 回调完成后要等待身份和基础数据初始化，再进入业务页面；不能依赖用户手动刷新。浏览器兼容要分别验证 Chrome、Edge、Safari 和钉钉内嵌环境。

### 问题三：页面显示已完成，但业务步骤未完成

教训：状态必须由月度记录、提交时间、锁定和评价完成条件共同推导，不能用单一总任务状态代替。

### 问题四：测试通过却无法真实验收

教训：测试认证缓存、生产身份绑定和真实数据范围可能不同。构建、单测、E2E、线上健康和真实角色验收必须分开报告。

### 问题五：发布到错误的容器或看到旧页面

教训：本机可能同时存在开发栈和生产栈。必须核对 Compose 项目名、端口、镜像 ID、容器创建时间和正式域名返回的资源。

### 问题六：未合并分支数量多

教训：长期分支里可能包含已被其他提交重新实现的方案。先比较提交内容和当前业务结论，再决定合并、保留或归档。

### 问题七：概念和提示过多

教训：复杂业务需要渐进展开，不需要把所有解释同时放在主页面。保留决策所需信息，把背景说明放到详情或帮助中。
