## 已确认问题

### 1. 历史合同混入重复导入及修订版本（P1）

用户反馈样本A实际有15条合同记录，其中7条未停用、8条已停用，来自三个导入批次。按日期可归为五组，但不能未经核对就认定为五份唯一业务合同。

- 2026-08-01共3条，当前页面选1条为最新，另2条进入历史。
- 2025-10-01共3条，均进入历史。用户反馈的两个重复数量得到验证。
- 同组记录并不都完全相同，存在签订日期、签约公司缺失和期限原文不同的情况。
- 生产导出构建器在内存生成真实 XLSX 后由 ExcelJS 回读，历史合同工作表同样输出上述重复。不是 Excel 把一行自行复制，而是导出了多条数据库记录。

代码证据：`web/src/views/admin/UserManageView.vue:706` 和 `api/src/users/roster-export-data.ts:57` 都只剔除选中的一条“最新”，将其他记录全部当历史；`api/src/users/users.excel.ts:176` 按记录输出历史行。`isActive=false` 同时覆盖被替换/移除的数据记录，不等于一次真实历史签约。

全库只读统计：844条记录、399条未停用；按所选业务字段（类型、名称、主体、日期、期限、原/新公司、协议和材料等，排除ID、序号、批次和启停状态）分组，有261组完全相同、涉及111名员工，均跨批次；只看未停用记录则没有完全相同组。该统计不等于确认有261份应删除的业务合同，也不排除字段差异的语义重复。

### 2. “最新合同”不代表当前生效的合同（P1）

用户反馈样本B有两条未停用合同：首签签订于2026-11-12、生效于2026-08-01；转签签订并生效于2026-11-01。页面和生产导出都优先选择首签，因为当前算法优先比较签订日期。

代码证据：`web/src/utils/employee-contract-presentation.ts:21`、`api/src/users/roster-export-data.ts:58`。算法也没有将未来生效合同、非主合同材料和当前合同分开选取。不能简单改成生效日期倒序就认定已解决未来合同抢占问题。

建议先确认“续签/转签何时替代原合同、是否允许同一任职多份合同并行”，再统一页面和导出。缺少生效日期或存在冲突时应标记待核，不凭创建顺序或随机ID推断业务关系。

### 3. 同一内容仍可因顺序不同再次保存（P1）

调用生产已编译的 `reconcileRosterContracts`，使用纯内存事务桩和虚构合同：保留原合同，再提交业务内容完全相同、但无ID且序号不同的新行，最终得到两条未停用记录。

代码证据：`api/src/employee-archives/employee-data-reviews.service.ts:1345`。现有重复约束为“类型+序号”，不是业务合同身份。手工修改已有记录保留ID，但无ID新增不会校验业务内容重复。

历史初始化另有顺序依赖：`api/src/employee-archives/employee-roster-initialization.ts:207` 仅在序号及内容匹配时复用，替换也只停用相同类型/序号的旧记录。记录换序后可能保留旧记录并新增另一条，与样本A的跨批次序号变化吻合。这里是当前代码机制证据，不据此断言所有历史批次均由同一版本代码造成。

建议保留不可变合同ID用于修改；导入增加业务匹配预览与冲突核对；疑似重复提示用户确认，不能仅凭日期自动合并。历史数据清理必须独立审批执行。

### 4. 上传未完成也能提交合同（P1）

档案编辑上传成功后才写入附件数组，但提交函数不等待上传任务。产品专项助手使用真实 Vue 组件和内存上传桩复现：上传仍挂起时提交已发出，提交附件数为0；已有9个附件时并发上传2个，前端数组最终达到11个。

代码证据：`web/src/views/admin/components/EmployeeArchiveInlineEditor.vue:252`、`:311`。入职表单也有同类上传路径。后端另有附件数量/来源校验，因此前端出现11个不代表正式数据库已接受11个。

建议将上传中/失败状态纳入提交门槛，数量包含在途文件；支持重试，并处理关闭编辑、移除合同或切换员工后才返回的上传结果。无需新增审批步骤。

### 5. 日期与类型的后端边界不完整（P2）

- 档案编辑 DTO 的 `contracts` 只校验数组，不逐项约束合同类型和日期：`api/src/employee-archives/dto/employee-archive.dto.ts:251`。
- 使用真实已编译 DTO，在内存校验包含任意类型和 `2026-02-31` 的提案，返回0项错误；应用层日期转换把该日期转成 `2026-03-03`：`api/src/employee-archives/employee-data-reviews.service.ts:1522`。
- 入职入口已有逐字段合法日期校验，但没有合同到期日期不早于生效日期的联合校验：`web/src/utils/onboarding-validation.ts:49`。专项内存复现倒置起止日期未报错。
- 档案合同编辑没有对应字段级错误绑定：`EmployeeArchiveInlineEditor.vue:516`。

上述是 DTO/应用函数和组件证据，未通过生产 HTTP 写入验证。建议统一前后端日历及起止关系校验；不要自动滚动日期、交换起止日期，也不要把补签情形“签订日晚于生效日”一概拒绝。兼容历史缺项，不在无关编辑时静默补造值。

### 6. 类型、名称与条件字段混杂（P2）

用户已明确类型为“首签、续签、转签”。页面两个编辑入口仍把 `contract` 标为“劳动合同”，详情也是如此；导出却标为“首签”。

代码证据：`EmployeeArchiveInlineEditor.vue:513`、`EmployeeCreateDrawer.vue:863`、`UserManageView.vue:95`、`api/src/users/roster-export-data.ts:52`。

最小调整：类型与合同名称分别显示；“劳动合同”保留为名称，不自动覆盖历史名称。普通新增只突出类型、名称、签约公司、签订/生效/到期日期；转签时呈现原/新公司，协议和材料按需展开。旧数据中的附件、保密协议、待分类等类型须保留可读性，不直接改写成首签。

### 7. 变更记录不足以核对材料与日期（P2）

`web/src/views/admin/components/EmployeeApplicationDetail.vue:154` 在新增合同分支只输出标题与签约公司便返回，未完整展示期限、协议和材料；`:160` 使用原始 JSON 日期比较；`:163` 附件只比较数量，替换文件可能显示“1份 -> 1份”。专项组件内存复现确认这些表现。

建议复用 `employee-review-differences.ts` 的既有差异逻辑，展示日期归一化后的前后值，以及具体文件增删，不另建平行变更系统。记录入口沿用现有流程，不增加合同专属审核。

### 8. 正式记录移除缺少局部撤销（P2，交互风险）

`EmployeeArchiveInlineEditor.vue:511` 对空白新增行和正式记录都直接执行 `splice`。并非立即物理删除数据库，正式生效仍在提交时；但多条相似合同容易误选且缺少单条撤销。

建议空白新增行可直接删除；已保存记录标记待移除并允许撤销，提交前核对对象。不要擅自把“移除记录”解释成合同业务作废或终止。

## 推荐实施顺序

1. 先修表单防护：统一首签/续签/转签文案、日期和错误就近显示、上传门槛、待移除撤销、准确变更摘要。保持现有权限及显式提交生效规则。
2. 确认替代/并行规则后，统一当前/待生效/历史合同的页面与导出口径；修订和导入来源在详情追溯，不作为新的签约混入主列表。不要增加新的一级菜单或大段说明。
3. 修保存及导入的身份匹配防止新增重复；序号只用于顺序和源表定位，不单独证明是同一份业务合同。
4. 另出历史数据核对清单，展示候选记录、差异字段、材料和来源。先只读预览，由HR确认保留/关联规则；执行前备份，逐条留痕，可追溯回退。未获授权前不清理正式数据。
