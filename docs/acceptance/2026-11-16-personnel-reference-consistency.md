日期：2026-11-16。代码基线 `5956d9d3f824386a18c76c5eda0a189eb1f217ba`；在 `codex/unified-company-directory` 的公司目录统一修改上继续实施。

## 已实现范围

- 学历、婚姻状况、政治面貌、户籍类型、紧急联系人关系、职级、职系、工作地点使用稳定目录 ID，名称作为历史快照保存。岗位目录的职系也保存 ID。清空同时清除两项；新选择校验存在、类别和启用状态；客户端名称由服务器纠正。
- 未改动的正式历史值可继续保留，目录改名或停用不静默重写历史。草稿不能冒充正式历史基线；审核时只有服务器验证过的提交快照可保留提交时名称，仍需验证新关联有效。
- 新入职提交必须选启用岗位，草稿仍可不完整；再入职可保留未改动的正式历史岗位、职级和工作地点。岗位关联变化在变更明细中可见。
- 旧待办不再凭主管姓名、部门文字路径自动认人、创建部门或更换负责人。需要维护者明确选择对象后再提交；已完成的历史记录不改写。
- 只传新职级/地点 ID 的变更也同步采用对应目录名称；导入的正式基准包含资料 ID、岗位和主管 ID，未变的正式关系可保留，变化名称不猜关联。来源再入职草稿及旧空基准草稿从已审核的历史任职继承未显示的职级/地点，不以草稿自身作为正式依据。
- 转正新提交按有效任职的花名册主管流转，保留提交时任职身份及办理人；已启动绩效关系不变。最终批准形成对应的任职状态和生效日期，未来日期到期生效，后续刷新不能退回旧状态，也不能用于另一段再入职。
- 定时批量刷新与单人刷新使用相同的事务内重读路径；序列化冲突有界重试。历史重叠沿用稳定选取，避免重新添加历史重叠阻断。
- 转正草稿保存、提交、附件、会议日期、各环节审批/退回/不同意均校验客户端提交轮次，并在写入时校验轮次、任职身份和状态。旧页面失败保留输入，不自动套用新一轮申请。
- 公司审批人可使用原有退回权限在页面退回旧申请；无任职引用的旧申请须重新提交确认身份，不能猜测绑定。未新增 HR 审批权限。

## 已确认公司权限口径

用户已确认并授权修改后上线。普通有转正办理权限的 HR，按本人当前正式生效任职的公司目录 ID 查看同公司员工；HR 管理员保持全范围，明确指派的申请保持可见。列表、详情、待办、办理权限和 HR 通知共用当前公司判断，不再使用部门的旧公司分类。缺少当前公司 ID 不按旧代码或名称猜配；管理员仍可维护。当前任职按上海业务日及起始日、创建时间、ID 确定，历史重叠、未来任职和未审核记录不能扩大权限。指派可见性不等于可代办 HR 环节；没有增加 HR 管理员的普通 HR 节点办理权限。
